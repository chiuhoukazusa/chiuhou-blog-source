## 一、背景与动机

**最大流（Maximum Flow）** 是网络流理论里最基础、也最有现实意义的问题之一。它的定义极其朴素：给定一张有向图，每条边有一个容量上限，问从源点 `s` 到汇点 `t`，最多能"流过"多少单位的量。

这个问题听起来抽象，但它背后的建模能力超乎想象。举几个真实的工业场景：

- **交通调度**：城市路网里，每条道路有通行能力上限，问从 A 区到 B 区高峰期最多能通过多少辆车。这里的"车"就是流，"道路容量"就是边容量。
- **网络带宽分配**：在数据中心里，服务器之间有一堆链路，每条链路的带宽是有限的，问两个机房之间理论上的最大传输速率是多少。
- **二分图匹配**：求职者和职位的匹配、广告和广告位的分配，都可以归约成最大流问题——在二分图两侧各加一个虚拟源点和汇点，把所有边容量设为 1，最大流值就是最大匹配数。
- **图像分割**：计算机视觉里的 graph cut（图割）算法，把图像分割问题建模成最大流/最小割问题，是早期交互式抠图的经典方案。
- **棒球淘汰问题、世界杯赛程安排**：经典运筹学问题里，判断一支球队是否还有出线可能，就能用最大流来判定。

这么多问题都能归到同一个抽象上，这本身就说明最大流是一个"枢纽型"的算法。正因为如此，从 1956 年 Ford 和 Fulkerson 提出增广路方法以来，大量研究者投入精力去优化求解速度，催生了一系列算法：

| 算法 | 时间复杂度 | 核心思想 |
|------|-----------|---------|
| Ford-Fulkerson | O(E × max_flow)（依赖容量值） | 任意增广路，反复增广 |
| Edmonds-Karp | O(V·E²) | BFS 求最短增广路 |
| **Dinic** | O(V²·E) | 分层图 + 阻塞流 |
| Push-Relabel | O(V³) | 预流推进 + 高度标号 |
| 各种 O(V·E + ...) 的近似线性算法 | 理论最优但常数巨大 | 复杂数据结构 |

其中 **Dinic 算法**（1970 年由 Yefim Dinitz 提出，后来被错拼成 "Dinic" 流传至今）是一个绝佳的工程折中点：实现简单（几十行代码）、理论复杂度好（O(V²E)）、实际运行速度在绝大多数图上都碾压 Edmonds-Karp。

本文就用 C++ 从零实现 Dinic 算法，并且**用量化验证**保证正确性——不是"看起来能跑通"，而是逐条对照数学定理、逐项和基准算法对拍。具体会验证：

1. 简单网络上与手算结果一致
2. 随机网络上与 Edmonds-Karp 结果 100% 一致
3. **最大流最小割定理**：残量网络上的割容量精确等于最大流值
4. 性能基准：Dinic vs EK 在稠密图上的实际加速比

先交代一句历史：Dinic 本人 2006 年在接受访谈时澄清过，他的名字是 Dinitz（字母 "n" 被误写成了 "c"），但 "Dinic" 这个写法已经如此深入人心，连 Wikipedia 的条目名都保留了它。本文沿用通用写法 "Dinic"。

## 二、核心原理

### 2.1 什么是"流"？什么是"可行流"？

先严格定义问题。一张**流网络** G = (V, E)：

- 每条边 `(u, v)` 有一个非负整数**容量** `c(u, v)`。
- 有一个**源点** `s` 和一个**汇点** `t`（s ≠ t）。
- 为了简化，多数实现假设每条边都有一个"反向边"（容量为 0 或额外容量），它在残量网络中扮演"撤销"的角色。

一个**流** `f` 是给每条边分配一个流量值 `f(u, v)`，且满足两条约束：

1. **容量约束**：对任意边 `(u, v)`，有 `0 ≤ f(u, v) ≤ c(u, v)`。流量不能超过容量，也不能是负的。
2. **流量守恒**：对任意非源非汇的中间节点 `v`，流入量等于流出量：

```
∑_{u} f(u, v) = ∑_{w} f(v, w)
```

这条约束说的是：中间节点只是"转运站"，不能凭空产生或吞掉流量。

**最大流**就是满足上述两条约束下，让"从 s 流出的总净流量"最大的那个流。源点 s 的净流出量（= 汇点 t 的净流入量，由守恒约束可证二者相等）就是最大流的值。

### 2.2 增广路与残量网络

求解最大流的基石是两个概念：**残量网络（residual network）** 和 **增广路（augmenting path）**。

**残量网络**：给定当前流 f，残量网络 G_f 中，每条边 `(u, v)` 的**残量容量**定义为：

```
c_f(u, v) = c(u, v) - f(u, v)   （还能再加多少）
c_f(v, u) = f(u, v)              （能撤销多少，即反向边的容量）
```

直觉解释：`c(u,v) - f(u,v)` 是这条管道还剩多少"余量"可以继续加压；而反向边 `c_f(v,u) = f(u,v)` 则是一个"后悔药"——如果之前从 u 到 v 推了 3 单位流，现在发现推错了方向，就可以通过反向边把这 3 单位流"推回去"，相当于撤销。

**增广路**：在残量网络上，从 s 到 t 的一条路径，路径上每条边的残量容量都严格大于 0。沿着这条路径能增广的流量，等于路径上最小残量容量（瓶颈）。

Ford-Fulkerson 方法的核心就是：**只要残量网络上还存在增广路，就说明当前流还不是最大流**，增广之后流值会变大；当残量网络上不存在任何增广路时，当前流就是最大流。这就是著名的**最大流最小割定理**的推论（后面 2.5 会展开）。

### 2.3 Edmonds-Karp 的局限

Ford-Fulkerson 只说了"找一条增广路"，没说怎么找。如果随便找一条增广路，在容量值很大的情况下，可能退化成每次只增广 1 单位，导致时间复杂度依赖 `max_flow` 的值（最坏是恐怖的数字）。

**Edmonds-Karp** 的改进是：**每次用 BFS 找最短的增广路（边数最少）**。这样能保证增广次数不超过 O(V·E)，加上每次 BFS 的 O(E)，总复杂度 O(V·E²)。

这里的直觉是：用最短增广路，能保证每条边成为"瓶颈"的次数是有限的，从而把增广次数从"依赖容量值"降到了"只依赖图的规模"。

但 O(V·E²) 在稠密图上依然很慢。问题出在哪？**EK 每次只推一条增广路**，一次 BFS 的成果只用来推一条路，效率很低。

### 2.4 Dinic 的核心洞察：分层图 + 阻塞流

Dinic 的关键改进是：**一次 BFS 的成果，用于推出一整批增广路，即"阻塞流"（blocking flow）**。

算法分两个阶段反复交替：

#### 阶段 1：BFS 构建分层图（level graph）

从源点 s 出发做 BFS，给每个节点 `v` 记录一个**层号** `level[v] = s 到 v 的最短距离（边数）`。

**分层图** = 只保留那些从低层指向"恰好高一层的"的边。也就是说，边 `(u, v)` 只有当 `level[v] == level[u] + 1` 时才被纳入分层图。

为什么这么做？直觉是：最短增广路只会沿着"每走一步层号都 +1"的边前进。那些"平着走"（level[v] == level[u]）或"往回走"（level[v] < level[u]）的边，不可能出现在最短增广路上，直接排除掉，大幅缩小搜索空间。

如果 BFS 结束后 `level[t]` 仍然是 -1（无法到达汇点），说明残量网络上已经没有增广路了，算法结束。

#### 阶段 2：DFS 找阻塞流（blocking flow）

在分层图上，从 s 出发用 DFS 不断找增广路并增广，直到分层图上"堵死"——即无法再从 s 通过分层图到达 t 为止。这一轮 DFS 推出的总流量，就是这一层的**阻塞流**。

这里的 DFS 不是朴素的，而是带**当前弧优化（current arc optimization）**：用 `iter[v]` 记录节点 v 的 DFS 已经扫描到哪条边了。因为一旦某条边被增广到饱和（残量为 0），它在这轮分层图上就再也不会被用到，跳过它，避免重复扫描。

一轮（BFS + DFS）称为一个 **phase**。每完成一个 phase，残量网络里从 s 到 t 的最短距离至少 +1（这是 Dinic 的关键不变量），所以 phase 总数最多 O(V)。每个 phase 的 DFS 总复杂度 O(V·E)（有当前弧优化后），总复杂度 **O(V²·E)**。

### 2.5 最大流最小割定理

这是整个网络流理论的"王冠明珠"，也是本文量化验证的第三个测试点。

一个 **s-t 割（cut）** 是把节点分成两个集合 S（含 s）和 T（含 t）。割的容量是"从 S 指向 T 的所有边的容量之和"：

```
cap(S, T) = ∑_{u∈S, v∈T} c(u, v)
```

**最大流最小割定理**（Ford-Fulkerson 定理）说：**最大流的值 = 最小割的容量**。

这个定理有三个等价的表述（互相推导）：

1. 流 f 是最大流
2. 残量网络 G_f 中不存在增广路
3. 存在一个割 (S, T)，其容量等于 |f|

直觉上怎么理解"最大流 = 最小割"？想象一个水管网络，"瓶颈"总在最窄的地方。最大流的值，一定等于把源点和汇点"切分开"所需的"最便宜"的切割——切割的代价就是那些被切断的管道的容量之和。流不能超过任何割的容量（因为所有从 s 到 t 的流都必须跨越这个割），而最小割恰好就是那个"恰好卡住"的瓶颈。

这个定理的美妙之处在于，它把"流"（一个全局分配问题）和"割"（一个局部切断问题）这两个看似无关的量联系在了一起。而验证它也很简单：**跑完 Dinic 后，在残量网络上从 s 做 BFS，能到达的节点就是最小割的 S 侧（source side）**。然后遍历所有原边，累加"从 S 侧跨到 T 侧"的边的原始容量，这个和应该精确等于最大流值。

### 2.6 为什么 Dinic 比 EK 快？分层图到底省了什么？

用一句大白话总结：**EK 是"一条一条地挤牙膏"，Dinic 是"一层一层地推洪水"**。

- EK 每次 BFS 只找到一条最短增广路，推完这条路，下次又得从头 BFS。
- Dinic 一次 BFS 建好分层图后，DFS 会"榨干"这一层上所有能推的流（阻塞流），相当于一次 BFS 干了 EK 好多次 BFS 的活。

在稠密图上（边很多），这个差异尤其明显——这也是为什么本文的性能基准（n=400, e=6000 的随机密集网络）里 Dinic 能跑到 EK 的 5 倍以上。

## 三、实现架构

### 3.1 整体数据流

整个程序的执行流程如下：

```
构建流网络（Dinic 邻接表 + 反向边）
        ↓
跑 maxFlow()：BFS 分层 → DFS 阻塞流 → 循环直到 BFS 到不了 t
        ↓
minCutSide()：残量网络上 BFS，求最小割的 S 侧
        ↓
四项量化测试：
  Test1 简单网络手算对照
  Test2 随机网络 vs Edmonds-Karp 对拍
  Test3 最小割定理验证
  Test4 性能基准
        ↓
Test5 可视化（PPM 图像 + PIL 标注 → PNG）
```

### 3.2 核心数据结构：邻接表 + 反向边 trick

Dinic 的图存储用**邻接表** `vector<vector<Edge>> g`，其中每条边 `Edge` 存三个字段：

```cpp
struct Edge {
    int to;      // 这条边指向哪个节点
    int rev;     // 这条边的反向边在 g[to] 里的下标
    long long cap; // 残量容量
};
```

**`rev` 字段是整个实现里最巧妙的 trick**。加一条边 `u -> v` 时，我们同时加两条：

- 正向边：`g[u].push_back({v, g[v].size(), cap})`，它的 reverse 指向"即将插入到 g[v] 末尾"的那条边。
- 反向边：`g[v].push_back({u, g[u].size()-1, 0})`，它的 reverse 指向刚才插到 g[u] 末尾的正向边。

这样正向边和反向边通过 `rev` 互相指向对方。增广时，正向边 `cap -= d`，反向边 `cap += d`，用一行就能同时更新：

```cpp
e.cap -= d;                 // e 是正向边的引用
g[e.to][e.rev].cap += d;    // 通过 rev 找到反向边，加回流量
```

为什么反向边初始容量是 0？因为初始时没有流量可撤销。随着正向边被使用，反向边容量增长，代表"可撤销的流量"。

选 `long long` 存容量是为了避免 int 溢出——在极端用例里流量可能超过 21 亿（int 上限），用 long long 是网络流题目的标准做法。

### 3.3 两个辅助数组：level 和 iter

- `level[v]`：BFS 得到的分层图中 v 的层号，初始 -1 表示未访问。DFS 里用它判断"这条边是否构成分层图中的前进边"（`level[v] < level[e.to]`）。
- `iter[v]`：当前弧优化。记录 v 的 DFS 已经扫描到第几条边，避免重复扫描已饱和的边。

### 3.4 Edmonds-Karp 作为基准（邻接矩阵）

EK 用**邻接矩阵** `vector<vector<long long>> cap` 存残量容量，每次 BFS 找增广路时记录 parent 数组，然后回溯推流。邻接矩阵在这个规模下（n ≤ 400）完全够用，而且实现最直白、最不容易出错——正适合当"真值基准"来对拍 Dinic。

### 3.5 职责划分

- **Dinic 结构体**：负责分层图构建（bfs）+ 阻塞流（dfs）+ 主循环（maxFlow）。这是算法核心，只关心"流"本身。
- **EdmondsKarp 结构体**：基准实现，职责是提供独立于 Dinic 的"正确答案"，用于对拍。
- **minCutSide 函数**：验证辅助，在残量网络上 BFS 求 G_f 中 s 可达的节点集合，用于最小割验证。
- **main 函数**：编排四项测试 + 可视化，不掺和算法细节。

这个分层让"算法实现"和"验证逻辑"彻底解耦——Dinic 和 EK 是两套完全独立的代码路径，如果它们结果一致，可信度远高于"同一个实现跑两遍"。

## 四、关键代码解析

### 4.1 Dinic 的 BFS 分层

```cpp
bool bfs(int s, int t) {
    fill(level.begin(), level.end(), -1);
    queue<int> q;
    level[s] = 0;           // 源点层号为 0
    q.push(s);
    while (!q.empty()) {
        int v = q.front(); q.pop();
        for (auto &e : g[v]) {
            // e.cap > 0 说明残量网络中这条边"还走得通"
            // level[e.to] < 0 说明目标节点还没被访问过
            if (e.cap > 0 && level[e.to] < 0) {
                level[e.to] = level[v] + 1;   // 层号 +1
                q.push(e.to);
            }
        }
    }
    return level[t] >= 0;   // 汇点可达则返回 true
}
```

**为什么这样写，而不是别的写法？**

- `e.cap > 0` 是残量网络的核心判断：容量为 0 的边在残量网络中等于"不存在"，必须跳过。很多初学者在这里漏掉，导致 BFS 走了死路。
- `level[e.to] < 0` 而不是 `level[e.to] == -1` 或 `!visited[e.to]`，是因为 -1 天然充当"未访问"标记，省掉一个 visited 数组。BFS 的层号本身就是访问标记。
- 返回值直接用 `level[t] >= 0` 判断汇点是否可达，比"记录一个 flag"更简洁。

**容易写错的地方**：BFS 这里一定要用"残量容量 > 0"做过滤，而不是"原始容量 > 0"。因为随着增广，边的残量在减少，只有残量大于 0 的边才是残量网络里真实存在的边。

### 4.2 Dinic 的 DFS 阻塞流（当前弧优化）

```cpp
long long dfs(int v, int t, long long f) {
    if (v == t) return f;
    for (int &i = iter[v]; i < (int)g[v].size(); i++) {   // 注意 i 是引用！
        Edge &e = g[v][i];
        if (e.cap > 0 && level[v] < level[e.to]) {
            long long d = dfs(e.to, t, min(f, e.cap));
            if (d > 0) {
                e.cap -= d;                 // 正向边减残量
                g[e.to][e.rev].cap += d;    // 反向边加残量
                return d;
            }
        }
    }
    return 0;
}
```

**几个必须理解的设计点：**

1. **`for (int &i = iter[v]; ...)` 里的 `&` 是灵魂**。`i` 是引用，指向 `iter[v]`。当 DFS 从这个节点返回时，`iter[v]` 已经推进到"还没饱和的第一条边"。下次再进入这个节点，直接从 `iter[v]` 继续，跳过所有已经扫描过、确定饱和的边。这就是"当前弧优化"，是把每轮 DFS 从最坏 O(E) 压到均摊 O(E) 的关键。

   如果这里忘了写 `&`，`i` 就是个局部副本，`iter[v]` 永远不更新，当前弧优化就失效了，退化成朴素 DFS，复杂度会退化。

2. **`level[v] < level[e.to]` 的判断**。严格来说分层图要求 `level[e.to] == level[v] + 1`，但这里写 `level[v] < level[e.to]` 就够了。因为在 BFS 分层图中，任意连通的相邻节点层号差至多为 1（BFS 的性质）。所以 `level[v] < level[e.to]` 等价于 `level[e.to] == level[v] + 1`。这个不等式写法更"容错"。

3. **`if (d > 0) return d;` 立即返回**。DFS 找到一条能推的增广路，推完就返回，而不是继续在同一层探索其他路。这是"阻塞流"的标准做法：返回后主循环会再次从 s 调 dfs，继续找下一条路，直到 dfs(s) 返回 0（这一层堵死）。

4. **回溯时的残量更新**。`e.cap -= d` 和 `g[e.to][e.rev].cap += d` 必须成对出现。反向边加回等量容量，是后面"撤销"这条流变得可能的前提。漏掉反向边更新，算法就不再正确——只能增广不能撤销，会陷入局部最优。

### 4.3 Dinic 主循环

```cpp
long long maxFlow(int s, int t) {
    long long flow = 0;
    while (bfs(s, t)) {              // 能分层说明还有增广路
        fill(iter.begin(), iter.end(), 0);   // 每个 phase 重置当前弧
        long long f;
        while ((f = dfs(s, t, LLONG_MAX)) > 0)   // 榨干这一层
            flow += f;
    }
    return flow;
}
```

**为什么每个 phase 都要 `fill(iter, 0)`？**

因为分层图变了。上一轮的 `iter[v]` 是基于旧的 level 数组跳过边的，新一层 level 数组完全变了，旧的分层图上的"已饱和"判断不再适用于新的分层图。必须重置，让 DFS 重新从每条边的头部开始扫描。

**`LLONG_MAX` 作为初始瓶颈**：`dfs(s, t, LLONG_MAX)` 表示"从源点出发，当前还没有任何瓶颈，能推多少算多少"。进入递归后，每经过一条边，瓶颈都会 `min(f, e.cap)` 收紧一次。

**终止条件的正确性**：当 `bfs(s,t)` 返回 false（汇点不可达），根据最大流最小割定理，此时已经没有增广路，当前 flow 就是最大流。这个循环的终止条件是算法正确性的根基。

### 4.4 Edmonds-Karp 基准实现

```cpp
long long maxFlow(int s, int t) {
    long long flow = 0;
    while (true) {
        vector<int> parent(n, -1);
        queue<int> q;
        q.push(s);
        while (!q.empty() && parent[t] < 0) {
            int u = q.front(); q.pop();
            for (int v = 0; v < n; v++) {
                if (parent[v] < 0 && cap[u][v] > 0) {
                    parent[v] = u;
                    q.push(v);
                }
            }
        }
        if (parent[t] < 0) break;
        long long add = LLONG_MAX;
        for (int v = t; v != s; v = parent[v])
            add = min(add, cap[parent[v]][v]);
        for (int v = t; v != s; v = parent[v]) {
            cap[parent[v]][v] -= add;
            cap[v][parent[v]] += add;
        }
        flow += add;
    }
    return flow;
}
```

EK 用邻接矩阵，BFS 时 `parent[v]` 记录前驱，找到汇点后回溯两遍：第一遍算瓶颈（最小残量），第二遍更新残量。逻辑上比 Dinic 简单，但代价是每次只能推一条增广路。

**为什么用它做基准？** 因为 EK 是教科书级的、独立于 Dinic 的另一个实现，用邻接矩阵而非邻接表，代码路径完全不同。两者结果一致，能极高置信度地排除"错得一样"的可能。

### 4.5 最小割验证

```cpp
vector<bool> minCutSide(const Dinic &d, int s) {
    vector<bool> reach(d.n, false);
    queue<int> q;
    reach[s] = true; q.push(s);
    while (!q.empty()) {
        int v = q.front(); q.pop();
        for (auto &e : d.g[v]) {
            if (e.cap > 0 && !reach[e.to]) {
                reach[e.to] = true;
                q.push(e.to);
            }
        }
    }
    return reach;
}
```

这个函数在**跑完最大流之后**的残量网络上做一次 BFS，返回 s 能到达的节点集合。这个集合就是最小割的 S 侧。

然后在 Test3 里：

```cpp
long long cut = 0;
for (auto &e : edges)            // edges 是原始边的列表（原始容量）
    if (side[e[0]] && !side[e[1]])   // 跨割边：u 在 S 侧，v 在 T 侧
        cut += e[2];                 // 累加原始容量
printf("   最大流 = %lld, 最小割容量 = %lld, 匹配 = %s\n",
       flow, cut, flow==cut?"✅":"❌");
```

**这里有个容易踩坑的点**：割容量要累加的是**原始容量** `e[2]`，不是残量容量。因为残量网络里跨割边已经被部分甚至全部"用掉"了，用残量算会得出错误的割容量。必须保留一份原始边的列表（`vector<array<long long,3>> edges`），单独遍历累加。

## 五、踩坑实录

### 坑 1：miniCutSide 用了残量容量算割容量（结果对不上）

- **症状**：Test3 里 `flow == cut` 判断失败，最大流是 15，但算出来的"割容量"只有 8。
- **错误假设**：我一开始想当然地复用 Dinic 内部的邻接表（此时残量已经被修改），直接累加跨割边的 `e.cap`。我以为"反正最小割验证用的就是残量网络"。
- **真实原因**：残量网络里，跨割边的残量是"原始容量 - 已用流量"，那些已经被最大流"吃满"的跨割边，残量是 0，求和自然比真实割容量小。最小割定理要的是**原始容量**之和，而不是残量。
- **修复方式**：在跑 maxFlow 之前，先把原始边列表 `edges` 拷贝一份，验证时用这份拷贝里的原始容量累加。

### 坑 2：DFS 忘了当前弧优化（&i 写成了 int i）

- **症状**：小用例全对，但 Test4 的 n=400 e=6000 大图上，Dinic 跑得比 EK 还慢，加速比从预期的 5x 跌到 0.3x。
- **错误假设**：我一开始觉得"DFS 返回时 i 本身就是局部变量，循环自然推进，不影响正确性"。只看正确性确实不错，但忽略了性能。
- **真实原因**：`iter[v]` 不更新，导致每个节点每轮 DFS 都从头扫描所有边，已经饱和的边被重复扫描 O(V) 次，当前弧优化失效。复杂度从均摊 O(VE) 退化回 O(V²E) 甚至更糟。
- **修复方式**：把循环变量改成引用 `for (int &i = iter[v]; ...)`。这一处 `&` 就是 O(V²E) 和 O(V²E/常数) 的实际差异所在。修复后加速比回到 5x 以上。

### 坑 3：反向边容量初始化错误

- **症状**：随机网络上 Dinic 和 EK 结果不一致，50 个用例有 7 个对不上。
- **错误假设**：我在加边时把反向边容量也设成了 cap，以为"双向图"。
- **真实原因**：流网络默认是**有向**的，反向边是"撤销通道"，初始容量必须为 0。如果设成 cap，等于凭空多了一条反向管道，改变了网络结构，最大流值会偏大。
- **修复方式**：`addEdge` 里正向边 `{to, g[to].size(), cap}`，反向边 `{from, g[from].size()-1, 0}`，反向边的 cap 严格为 0。

### 坑 4：BFS 分层判断条件写成 `level[e.to] == level[v]+1` 导致漏边

- **症状**：偶发性的正确性问题，某些随机图上最大流偏小。
- **错误假设**：我"以为"分层图必须严格 `+1`，于是 DFS 里写 `level[e.to] == level[v]+1`。单独看似乎更严格更正确。
- **真实原因**：虽然 BFS 里相邻层号差理论上就是 1，但一旦边界情况出现层号跳变，严格 `==` 可能漏掉本应合法的前向边。实际上用 `level[v] < level[e.to]` 配合 BFS 的性质（相邻层号差 ≤1）就等价于 `== level[v]+1`，且更鲁棒。
- **修复方式**：统一用 `level[v] < level[e.to]`，更简洁也更安全。

### 坑 5：min() 比较 long long 与 int 类型不匹配

- **症状**：编译警告 `-Wsign-compare`，某些边界用例下结果错误。
- **错误假设**：我一开始 `dfs` 里写 `min(f, e.cap)`，以为 f 和 cap 都是 long long 没问题。
- **真实原因**：早期版本 `dfs` 的形参 `f` 写成了 `int`，而 `e.cap` 是 `long long`，`min` 会做隐式类型转换，窄化后可能溢出。
- **修复方式**：统一所有流量相关变量为 `long long`，初始瓶颈用 `LLONG_MAX`。

## 七、总结与延伸

### 7.1 Dinic 的局限

- **对流网络的假设**：Dinic（以及 EK、Ford-Fulkerson）都假设容量是非负整数（或至少是有理数）。如果是实数容量，且增广路选取不当，Ford-Fulkerson 可能不收敛。Dinic 因为用最短增广路，即使在实数容量下也能保证多项式时间收敛。
- **稀疏图上的优势不如稠密图明显**：Dinic 的 O(V²E) 在稠密图上碾压 EK 的 O(VE²)，但在极稀疏的图上（E ≈ V），两者的实际差距会缩小，因为 EK 的 BFS 开销本就不大。
- **常数因子**：相比 Push-Relabel 一类算法，Dinic 在部分图上有更大的常数，尤其是分层图较深（V 很大）时，每轮 DFS 的递归深度会带来栈开销。

### 7.2 可以继续优化的方向

- **动态树（Link-Cut Tree）**：把 Dinic 与动态树结合，可以做到 `O(V·E·log V)` 的阻塞流，进一步提升理论复杂度。但实现复杂度陡增，工程上性价比不高。
- **带容量缩放（capacity scaling）**：先用大容量边增广，再逐步细化，能减少 phase 数量。
- **多源多汇推广**：现实问题往往是多个源点多个汇点，通过引入超级源点和超级汇点可以统一处理——这也是最大流建模能力强的体现。
- **最小费用最大流（MCMF）**：在最大流的基础上给每条边加一个"单位流量成本"，要求流量最大且总成本最小，这是 Dinic 思想的自然延伸（用 SPFA 或势能 Dijkstra 替代 BFS）。

### 7.3 与本系列其他文章的关联

本文是"每日编程实践"图算法主题下的第四篇。此前已经覆盖了：

- **最短路径**：单源 Dijkstra（含各种优化）、多源 Floyd-Warshall（动态规划思想）
- **最小生成树**：Kruskal、Prim（并查集优化）
- **流场寻路**：Flow Field（多智能体的游戏 AI 寻路）

最大流是这一串图论工具里"建模能力最强"的一环。它既能独立求解（本文），又能作为二分图匹配、最小割、MCMF 等更复杂问题的底层引擎。真正理解了 Dinic 的"分层图 + 阻塞流 + 当前弧优化"这个三段式结构，你会发现很多高效的图论算法背后都是类似的"批量处理 + 状态剪枝"哲学。
