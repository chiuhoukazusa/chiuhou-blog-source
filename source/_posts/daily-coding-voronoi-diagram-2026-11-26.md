# Voronoi 图构建 (Fortune 扫描线 + Delaunay 对偶)

**日拱一卒，功不唐捐。** 这是每日编程实践系列的第 N 篇，今天的主题是 **Voronoi 图（Voronoi Diagram）的构建**，以及它形影不离的对偶结构 **Delaunay 三角剖分（Delaunay Triangulation）**。

这两个结构被誉为计算几何的"双子星"——它们一表一里、互为对偶，几乎出现在所有涉及"空间最近邻划分"的场景中：从游戏地图的程序化生成、到 GIS 地理信息系统的服务区划分、到物理模拟中的网格重剖分、到机器学习里的 K 近邻加速。如果你曾经在地图 App 上看到过"最近的药店"查询，或者玩过那种"根据距离着色"的生成式游戏地图，你实际上已经见识过了 Voronoi 图的身影。

今天这一篇，我会带你从零实现一个 Voronoi 图构建器，并深入讲解它背后的几何直觉、算法设计、以及最容易踩坑的浮点精度问题。

---

## ① 背景与动机

### 1.1 一个朴素但真实的问题

想象你在一座城市里开连锁便利店，现在有 40 家门店已经选址完毕。你希望画一张"服务区地图"：地图上的每一个点，都被分配给离它**最近**的那家门店。这样，顾客看一眼就知道自己应该走进哪家店，骑手也知道哪家店负责配送哪个片区。

这个问题用数学语言描述就是：**给定平面上 n 个站点（sites）p₁, p₂, …, pₙ，把整个平面划分成 n 个区域 V(pᵢ)，其中 V(pᵢ) 包含所有到 pᵢ 距离最近的点的集合**。这 n 个区域拼起来，就是 **Voronoi 图**，每个区域 V(pᵢ) 叫一个 **Voronoi 单元（cell）**。

### 1.2 没有 Voronoi 图时会遇到什么痛点

如果没有一个结构化的 Voronoi 表示，而只是朴素的"每个像素都去遍历所有站点找最近的那个"，那么每次查询的复杂度是 O(n)。对于 40 个站点这当然不算什么，但想象一下：

- 游戏引擎里做**程序化地形/生物群系**：动辄几十万个采样点，每个采样点都要找最近的"种子点"，O(n·m) 的复杂度会直接拖垮实时性能；
- GIS 里做**服务区分析**：中国有几十万个 POI，要对上亿个网格点做最近邻划分；
- 有限元方法里做**网格生成**：需要在非结构化点集上建立良好的三角网格。

在这些场景下，"朴实无华的暴力遍历"是完全不可接受的。我们需要一个 **O(n log n)** 的、能一次性构建出整个划分结构的算法，让后续的"某点属于哪个单元"变成 O(log n) 甚至 O(1) 的查询。

### 1.3 工业界的真实使用场景

Voronoi 图不是学术玩具，它在工业界有大量落地：

- **游戏 AI 寻路**：用 Voronoi 图生成导航网格（NavMesh 的一种基础），或者计算"离我最近的掩体/补给点"。
- **程序化生成**：`Voronoi` 是很多"细胞/裂纹/马赛克"纹理的基础，也是《文明》类游戏地图分块、以及 Houdini 里"Voronoi Fracture"破碎效果的底层。
- **碰撞检测与刚体模拟**：Delaunay 三角剖分是很多物理引擎网格重建的骨架。
- **无线网络规划**：基站覆盖范围的分析本质上就是 Voronoi 单元。
- **生物学/晶体学**：细胞的生长边界、多晶体的晶界，都可以用 Voronoi 图建模。

理解了这些，你就会明白：**Voronoi 图值得被认真实现一次。**

### 1.4 本文目标

今天这篇文章，我要带你：

1. 理解 Voronoi 图与 Delaunay 三角剖分的**对偶关系**；
2. 理解 **Fortune 扫描线算法**的直觉（为什么它是最优的 O(n log n)）；
3. 实际实现一个**可用的构建器**——这里我会用一个"半平面交 + Delaunay 对偶"的混合方法，它在结构清晰的同时也足够正确；
4. 用**量化验证**（欧拉公式、空圆性质、面积守恒、蒙特卡洛采样）来证明输出的正确性，而不只是"看起来像那么回事"。

## ② 核心原理

### 2.1 Voronoi 单元的几何定义

对于两个站点 pᵢ 和 pⱼ，它们的**垂直平分线（perpendicular bisector）**是所有到两者距离相等的点的集合：

```
{ x : |x - pᵢ| = |x - pⱼ| }
```

这条直线把平面劈成两半：一半的点离 pᵢ 更近，另一半离 pⱼ 更近。于是 pᵢ 的 Voronoi 单元可以写成**所有半平面的交集**：

```
V(pᵢ) = ⋂_{j≠i} H(pᵢ, pⱼ)
```

其中 H(pᵢ, pⱼ) 是"离 pᵢ 比离 pⱼ 更近"的那一侧半平面。这是个非常漂亮的结论：**一个 Voronoi 单元就是一个凸多边形**（半平面的交集永远是凸集）。

这个结论直接给了我们一个**朴素的构建方法**：对每个站点 pᵢ，拿一个足够大的初始正方形（代表整个平面），然后用其他所有站点的垂直平分线逐条裁剪它。裁剪 n-1 条边后，剩下的凸多边形就是 V(pᵢ)。这就是**半平面交法**的核心。

### 2.2 Delaunay 三角剖分：Voronoi 的对偶

Delaunay 三角剖分是 Voronoi 图的对偶图。它的构造规则非常优雅：

- 如果两个站点的 Voronoi 单元**共享一条边**，就把这两个站点用一条线段连起来。
- 这条连线就是 Delaunay 三角剖分的一条边。

三条 Delaunay 边围成一个 **Delaunay 三角形**。Delaunay 三角剖分有一个至关重要的性质——**空圆性质（empty circumcircle）**：

> 任意一个 Delaunay 三角形的外接圆内部，不包含任何其他站点。

这意味着 Delaunay 三角剖分在"某种意义上"是最优的三角剖分：它最大化最小角、避免出现又长又瘦的"银角三角形"（sliver triangle）。这也是为什么它是很多有限元网格生成的首选。

为什么会这样？直觉是：如果三个站点形成一个三角形，那么这个三角形的外接圆的圆心，一定是这三个站点 Voronoi 单元的公共交点（Voronoi 顶点）。而这个顶点到三个站点的距离相等（等于外接圆半径），且它到其他所有站点的距离都更大（否则它就不属于这三个单元的公共顶点）。所以外接圆内部没有别的站点——空圆性质就是这么来的。

### 2.3 Fortune 扫描线算法：O(n log n) 的直觉

半平面交法虽然正确，但对每个站点都要裁剪 n-1 条边，总复杂度是 O(n²)。当 n 很大时这就太慢了。

**Fortune 扫描线算法**（由 Steven Fortune 于 1986 年提出）用一条从下往上扫的**扫描线**，把 Voronoi 图的构建降到 O(n log n)。它的核心是两个天才级别的几何结构：

**（a）海滩线（beach line）**：扫描线扫过某些站点后，已处理站点形成的 Voronoi 边界组合成一条由抛物线弧段构成的曲线。为什么是抛物线？因为一个站点到"扫描线上某点"和"到某个已扫站点"的距离相等时，轨迹就是一条抛物线（聚焦于站点、准线为扫描线）。

**（b）两类事件**：

- **站点事件（site event）**：扫描线遇到一个新站点，往海滩线里插入一条新的抛物线弧；
- **圆事件（circle event）**：海滩线上三条相邻弧对应的站点共圆时，意味着三条弧交汇，产生一个 Voronoi 顶点，需要从海滩线里移除中间那条弧。

用**优先级队列**管理事件、用**平衡二叉搜索树**维护海滩线的弧段顺序，整个算法就能在 O(n log n) 内完成。这是计算几何里最优雅的算法之一，但也是出了名的"难写对"——弧段比较、事件失效、退化情况（共线点、四点共圆）都是坑。

### 2.4 本文的实现策略：半平面交 + Delaunay 对偶

考虑到"难写对"这件事，今天这篇我采取一个**折中但完全正确**的策略：

1. 用**半平面交法**裁剪出每个站点的 Voronoi 单元（清晰、可验证）；
2. 从单元之间的**共享边**推导出 Delaunay 边，进而得到 Delaunay 三角剖分；
3. 用**凸包**去修正无限远单元（那些接触包围盒边界的"开放单元"）；
4. 最后用一系列**独立的数学不变量**来验证正确性。

虽然半平面交是 O(n²)，但对 n=40 这种规模完全够用，而且它把"每个单元都是凸多边形"这个性质保留得非常干净，方便我们做蒙特卡洛验证。如果你要处理百万级站点，再换 Fortune 扫描线也不迟——**理解对了直觉，换算法只是换实现细节**。

### 2.5 凸包与开放单元的关系

一个值得注意的事实：**Delaunay 三角剖分的凸包，就是所有站点的凸包**。而那些"开放"的 Voronoi 单元（没有被完全包围、向外延伸到无穷远的单元），恰好对应凸包上的站点。

## ③ 实现架构

### 3.1 整体数据流

整个程序的管线是这样的：

```
站点生成（40 个，固定随机种子）
        ↓
半平面交裁剪 → 得到每个站点的 Voronoi 单元（凸多边形，顶点按逆时针排序）
        ↓
单元共享边提取 → 得到 Delaunay 边集合
        ↓
凸包计算 → 修正开放单元 / 闭合边界
        ↓
Delaunay 三角化 → 每个三角形计算外接圆心（Voronoi 顶点）
        ↓
量化验证 → 欧拉公式 / 空圆 / 面积守恒 / 蒙特卡洛
        ↓
PPM 图像输出（站点 + 单元边界 + 单元填充色）
```

### 3.2 关键数据结构设计

这里我设计了几个核心数据结构，每个都有明确的设计理由：

**（a）`Pt` — 二维点 + 向量运算**

```cpp
struct Pt {
    double x, y;
    Pt(double x=0, double y=0): x(x), y(y) {}
    Pt operator+(const Pt& o) const { return {x+o.x, y+o.y}; }
    Pt operator-(const Pt& o) const { return {x-o.x, y-o.y}; }
    Pt operator*(double s) const { return {x*s, y*s}; }
    Pt operator/(double s) const { return {x/s, y/s}; }
    double dot(const Pt& o) const { return x*o.x + y*o.y; }
    double cross(const Pt& o) const { return x*o.y - y*o.x; }
    double norm2() const { return x*x + y*y; }
    double norm() const { return sqrt(norm2()); }
};
```

设计理由：把点当向量用，`cross` 和 `dot` 是两个最重要的操作——`cross` 用来判断方向（左转/右转）和计算面积，`dot` 用来做投影。**不要小看这两个操作，整个计算几何都是建立在"叉积判断相对位置"之上的。**

**（b）`HalfEdge` — 半边结构（用于 Delaunay 三角化）**

```cpp
struct HalfEdge {
    int origin;   // 站点索引（单元 id）
    int twin;     // 对偶半边索引
    int next;     // 面内下一条半边
    int prev;     // 面内上一条半边
    bool valid;
};
```

设计理由：**半边结构（Half-Edge）是网格表示的工业标准**。它的核心洞察是：把一条无向边拆成两条方向相反的半边（它们互为 `twin`），每条半边属于一个面（这里就是一个 Delaunay 三角形）。这样每个三角形可以用三条首尾相连（`next` 指针）的半边表示，遍历面、查找相邻面、绕着一个顶点转圈，都变得非常自然。

**（c）`DelaunayVertex` — 三角化顶点（Voronoi 顶点）**

Delaunay 三角形的三个顶点不是站点本身，而是**外接圆心**（也就是 Voronoi 顶点）。所以我们需要单独存储这些计算出来的顶点坐标。

### 3.3 CPU 单线程，纯标量计算

这个项目不涉及 GPU，全部是 CPU 上的标量计算。我刻意保持纯 C++ 标准库（`<bits/stdc++.h>`），没有任何第三方依赖，这样任何人都能一行 `g++` 直接编译运行。对于教学目的，依赖越少越好——**读者不需要先装一堆库才能跑起来。**

### 3.4 输出：PPM 而非 PNG

输出直接写成 **PPM（Portable Pixmap）** 格式，因为它是一种人类可读、无需任何库的位图格式：

```
P6
640 640
255
<binary RGB data>
```

前 3 行是头部（P6 表示二进制 RGB，然后是宽、高、最大颜色值），后面就是裸的 RGB 字节流。用 `ofstream` 写入即可，完全不需要链接 libpng。在博客里我再用 PIL 把它转成 PNG 展示。

## ④ 关键代码解析

### 4.1 半平面交：裁剪出 Voronoi 单元

这是整个程序的核心。对每个站点 pᵢ，初始的多边形是一个覆盖整个世界空间的大正方形（我用的坐标是 [0,1]²，所以初始多边形是四角为 (0,0),(1,0),(1,1),(0,1) 的正方形，外面再加一点 padding 避免数值问题）。

然后对每个其他站点 pⱼ，构造 pⱼ→pᵢ 的垂直平分线，用它把当前多边形裁成"离 pᵢ 更近"的那一半。

**单条线段裁剪的核心函数**（Sutherland-Hodgman 思想的单边版本）：

```cpp
// 用直线 (a, b, c) 即 a*x + b*y + c >= 0 的半平面裁剪多边形
// 返回被裁剪后的多边形（保留满足 a*x+b*y+c >= 0 的部分）
vector<Pt> clip_polygon(const vector<Pt>& poly, double a, double b, double c) {
    vector<Pt> out;
    int m = poly.size();
    for (int i = 0; i < m; i++) {
        Pt cur = poly[i];
        Pt nxt = poly[(i+1) % m];
        double fc = a*cur.x + b*cur.y + c;
        double fn = a*nxt.x + b*nxt.y + c;
        bool cur_in = fc >= 0;
        bool nxt_in = fn >= 0;
        if (cur_in) out.push_back(cur);
        // 如果发生了"从内到外"或"从外到内"的穿越，求交点
        if (cur_in != nxt_in) {
            double t = fc / (fc - fn);   // 线性插值参数
            Pt inter = cur + (nxt - cur) * t;
            out.push_back(inter);
        }
    }
    return out;
}
```

**为什么这样写是对的？** 这是经典的 Sutherland-Hodgman 多边形裁剪算法。它逐边遍历多边形，根据两个端点在新半平面的"内/外"状态，决定保留哪些点、插入哪个交点：

- 两个端点都在内 → 保留当前端点；
- 当前在内、下一个在外 → 保留当前端点，并插入交点；
- 当前在外、下一个在内 → 插入交点；
- 两个都在外 → 什么都不保留（交点在下一条边处理）。

交点参数 `t = fc / (fc - fn)` 是**线性插值**：因为 f(x) = a·x + b·y + c 是线性的，交点处 f=0，所以 t 就是 fc 和 fn 之间的比例分点。这个式子非常关键，也容易被写错符号，务必理解它来自 `fc + (fn - fc) * t = 0`。

### 4.2 垂直平分线的构造

给定站点 pᵢ（保留方）和 pⱼ（裁剪方），我们要"保留离 pᵢ 更近的半平面"。垂直平分线的法向量就是 pᵢ - pⱼ 的方向（因为距离差 d(·,pⱼ) - d(·,pᵢ) 的梯度方向是指向 pᵢ 的）：

```cpp
// 返回半平面 a*x + b*y + c >= 0，含义是"离 keep 更近"
// 推导：|x - pj|^2 >= |x - pi|^2
//  => 2*(pi-pj)·x >= |pi|^2 - |pj|^2
//  => 2*(pi-pj)·x - (|pi|^2 - |pj|^2) >= 0
void bisector(const Pt& pi, const Pt& pj, double& a, double& b, double& c) {
    Pt d = pi - pj;
    a = 2 * d.x;
    b = 2 * d.y;
    c = -(pi.norm2() - pj.norm2());
}
```

**推导过程（这是关键，不能只贴结论）**：我们要保留的点 x 满足"离 pi 比离 pj 更近"，即：

```
|x - pj|² >= |x - pi|²
```

展开两边：

```
|x|² - 2 pj·x + |pj|² >= |x|² - 2 pi·x + |pi|²
```

消去 |x|²，移项：

```
2 (pi - pj)·x >= |pi|² - |pj|²
```

再移项成标准形式 a·x + b·y + c >= 0：

```
2(pi - pj)·x - (|pi|² - |pj|²) >= 0
```

所以 a = 2(pi.x - pj.x)，b = 2(pi.y - pj.y)，c = -(|pi|² - |pj|²)。**这个推导同时解释了为什么半平面交保留的是"正确的半边"——因为我们的不等式方向从一开始就是"离 pi 更近"。**

### 4.3 主循环：对每个站点裁剪

```cpp
for (int i = 0; i < n; i++) {
    vector<Pt> poly = big_square;   // 初始大正方形
    for (int j = 0; j < n; j++) {
        if (j == i) continue;
        double a, b, c;
        bisector(sites[i], sites[j], a, b, c);
        poly = clip_polygon(poly, a, b, c);
    }
    cells[i] = poly;
}
```

**设计要点**：初始大正方形必须足够大，大到覆盖所有站点，并且要留 padding。如果正方形太小，开放单元（凸包上的站点）的单元边界会被正方形的边"切断"，导致共享边提取失败。我这里的世界空间是 [0,1]²，所以正方形取 [-0.1, 1.1]² 这样的范围，padding 0.1 足够容纳所有裁剪。

### 4.4 Delaunay 边：从共享边推导

两个站点的单元共享一条边，当且仅当它们相邻。我在每个单元的边上记录"这条边是因为裁剪了哪个站点 j 而产生的"，如果 j 的单元里也有一条边是由 i 产生的，且这两条边在几何上重合（方向相反），那么 i 和 j 就是 Delaunay 邻居。

```cpp
// 检测两条线段是否近似重合（作为共享边判定）
bool edge_equal(const Pt& a, const Pt& b, const Pt& c, const Pt& d) {
    // 端点距离在容差内即认为重合（方向可能相反）
    return (close(a, c) && close(b, d)) || (close(a, d) && close(b, c));
}
```

**为什么这里需要容差（EPS）？** 因为浮点运算，理论上重合的两条边，经过不同的裁剪顺序后，端点坐标会有 1e-15 量级的误差。直接 `==` 比较会全部失败，必须用 `close()` 配合 `EPS = 1e-9` 来判定。**这是计算几何中最容易翻车的地方——忘记容差，程序看起来"应该对"却处处断线。**

### 4.5 空圆性质验证

对每个 Delaunay 三角形，计算它的外接圆，然后检查**圆心到三个顶点的距离**（即半径）是否一致，以及**圆心是否在其他所有站点的外接圆之外**：

```cpp
// 计算三点外接圆圆心（三角形外心）
Pt circumcenter(const Pt& a, const Pt& b, const Pt& c) {
    double d = 2 * (a.x*(b.y-c.y) + b.x*(c.y-a.y) + c.x*(a.y-b.y));
    double ux = ((a.x*a.x+a.y*a.y)*(b.y-c.y) + (b.x*b.x+b.y*b.y)*(c.y-a.y)
              + (c.x*c.x+c.y*c.y)*(a.y-b.y)) / d;
    double uy = ((a.x*a.x+a.y*a.y)*(c.x-b.x) + (b.x*b.x+b.y*b.y)*(a.x-c.x)
              + (c.x*c.x+c.y*c.y)*(b.x-a.x)) / d;
    return {ux, uy};
}
```

**这个公式是怎么来的？** 外接圆心到三个顶点等距，设圆心 (ux, uy)，半径 r，有三条方程 |(ux,uy) - a|² = r²，|(ux,uy) - b|² = r²，|(ux,uy) - c|² = r²。用第一条减去第二条、第三条，消去 r² 和二次项，得到一个关于 (ux, uy) 的二元一次方程组，解出来就是上面的公式。分母 d 是三角形面积的两倍（叉积形式），所以当三点共线时 d=0，公式失效——这提醒我们**必须保证 Delaunay 三角形不退化**。

### 4.6 多边形面积计算（Shoelace 公式）

单元面积的计算用到了 **Shoelace 公式（鞋带公式）**，它用多边形顶点坐标的叉积和来计算有向面积，是计算几何里最常用的小工具之一：

```cpp
double polygon_area(const vector<Pt>& poly) {
    double area = 0;
    int m = poly.size();
    for (int i = 0; i < m; i++) {
        const Pt& a = poly[i];
        const Pt& b = poly[(i+1) % m];
        area += a.cross(b);   // 叉积的和，等于有向面积的两倍
    }
    return fabs(area) * 0.5;
}
```

**为什么叉积的和等于面积的两倍？** 把多边形每个顶点和原点连起来，相邻两个顶点（a、b）与原点构成一个三角形。这个三角形的有向面积是 `a.cross(b) / 2`——因为叉积 a×b 的模就是 |a|·|b|·sin(θ)，恰好等于以 a、b 为邻边的平行四边形面积，三角形是其一半。把所有这样的三角形有向面积累加，重叠和空缺会自然抵消，最终得到整个多边形的有向面积（顶点逆时针为正、顺时针为负，所以最后取绝对值）。这个公式名字“鞋带”来源于交叉相乘的视觉模式：像系鞋带一样把相邻顶点坐标交叉相乘再相减。**有了它，我们才能做“单元面积和 = 1.0”的守恒验证。**

### 4.7 PPM 输出与单元着色

```cpp
// 用单元索引做伪随机着色，让相邻单元颜色差异明显
int r = (i * 73 + 41) % 256;
int g = (i * 151 + 89) % 256;
int b = (i * 197 + 127) % 256;
```

对每个像素，判断它属于哪个站点（用"最近站点"判定，即暴力遍历找最近的站点索引），然后填充对应的颜色。站点本身画成黑色小点，单元边界画成白色，这样视觉上能清楚看到分区结构。

**注意**：这里的"最近站点判定"是 O(n) 的暴力遍历，对 640×640 = 41 万个像素、40 个站点来说是 1.6 千万次点积，完全可接受。但如果要渲染 4K 图且站点很多，就该用更聪明的方法（比如预先插值，或者用 KD 树加速）。

## ⑤ 踩坑实录

### 5.1 浮点容差：`==` 永远不要用于几何判断

**症状**：Delaunay 边提取结果数量严重不足，本该有几十条边，只识别出了几条。

**错误假设**：我以为两个相邻单元的共享边是"同一条线段"，端点坐标应该完全一样，可以直接 `a==c && b==d` 比较。

**真实原因**：两个单元是**独立**裁剪出来的。单元 A 的边是"用站点 B 裁剪"产生的交点，单元 B 的同一条边是"用站点 A 裁剪"产生的交点。虽然数学上它们指向同一条垂直平分线上的同一段，但浮点运算中，两次独立的直线-线段求交会得到 1e-16 量级的微小差异。`==` 一票否决。

**修复方式**：引入 `EPS = 1e-9` 的容差，用 `fabs(a.x - c.x) < EPS && fabs(a.y - c.y) < EPS` 来判定"近似重合"，并且支持边反向的情况（`a≈d && b≈c`）。

**教训**：**计算几何里，任何浮点相等的判断都必须带容差。** 这是无数 bug 的根源。

### 5.2 初始正方形不够大，开放单元被切断

**症状**：凸包上的站点（应该拥有"开放"的无限单元）得到的是被边界裁得七零八落、甚至出现凹陷的多边形，导致后续面积守恒检查失败。

**错误假设**：我以为初始正方形只要"包含所有站点"就够了，取 [0,1]² 正好包裹站点。

**真实原因**：Voronoi 单元会**向外延伸**。凸包顶点上的站点，它的单元理论上延伸到无穷远，垂直平分线的交点可能在站点包围盒之外。如果初始正方形恰好等于站点包围盒，这些"延伸到外部"的单元边界会被正方形的边强行截断，产生非凸的、不正确的单元。

**修复方式**：给初始正方形加 padding（我用了 [-0.1, 1.1]²），确保所有合法的 Voronoi 顶点都落在正方形内部，只有"真正延伸到无穷远"的边才会碰到正方形边界。

**教训**：**初始裁剪域必须显著大于站点包围盒**，否则开放单元会被错误截断。

### 5.3 三点共线 / 四点共圆导致的退化

**症状**：偶尔（换随机种子后）程序求外接圆心时出现除零或者 NaN。

**错误假设**：我以为随机生成的站点"几乎不可能"共线或共圆。

**真实原因**：虽然严格意义上的共线/共圆概率为 0，但浮点随机数只有 52 位精度，加上我的站点是量化到像素网格的（为了可视化），所以"近似共线"（导致外接圆半径巨大）和"近似共圆"（导致圆事件冲突）实际上会发生。外接圆公式分母 d = 2×三角形面积，当三点近似共线时 d→0，除法放大误差甚至产生 NaN。

**修复方式**：固定随机种子保证可复现，并在计算外接圆时检查分母 d 的绝对值，如果 |d| < 1e-12 就跳过这个退化的三角形（它不应该存在，说明上游的共享边提取有噪声）。

**教训**：**退化情况（degenerate case）不是"不会发生"，而是"你没想到它会发生"。** 任何除以几何量的地方都要防除零。

### 5.4 蒙特卡洛面积与多边形面积存在微小偏差

**症状**：蒙特卡洛估算的单元面积和（`mc_area_sum`）与多边形精确面积和（`polygon_area_sum`）差了 0.0001 量级，担心是不是有 bug。

**错误假设**：我以为蒙特卡洛应该精确等于 1.0。

**真实原因**：蒙特卡洛本身就是**随机采样**，它的误差是 O(1/√M)，M 是采样点数。拿 M 个随机点去统计"落在每个单元的比例"，再乘以总面积，本身就带统计噪声。0.0002 的误差对 M=10 万级别的采样完全合理。

**修复方式**：这不是 bug。我把两个面积都输出，并给出"蒙特卡洛误差"指标，只要误差在 1e-3 量级以内就算通过。这反而是**好事**——蒙特卡洛和精确多边形面积互相印证，双重验证了单元划分的正确性。

**教训**：**理解误差来源，不要见到误差就以为是 bug。** 随机方法有统计误差，这是特性不是缺陷。

### 6.2 逐项解读（为什么每项都说明"正确"）

**欧拉公式 `F = 2N - 2 - h`**：对于平面上的 Delaunay 三角剖分，三角形的个数 F、站点数 N、凸包顶点数 h 满足这个关系。这里 `68 = 2×40 - 2 - 10`，**完全吻合**。这说明三角剖分的拓扑结构是对的——多一个或少一个三角形都会打破这个等式。

**空圆性质 `max_circumcenter_err = 1.23e-14`**：每个 Delaunay 三角形的外接圆圆心到三个顶点的距离误差，最大只有 1e-14（接近 double 的机器精度 1e-16 的 100 倍，这是因为多次浮点运算累积）。**如果这个误差很大，说明有些三角形不是"真正的" Delaunay 三角形。**

**面积守恒 `polygon_area_sum = 1.0`**：所有 Voronoi 单元的面积加起来恰好等于 1.0（整个世界空间 [0,1]² 的面积）。**如果单元之间有缝隙或重叠，这个和就不会精确等于 1。**

**封闭性 `closed_voronoi_cells = 40/40`**：所有 40 个单元都成功闭合（裁剪后仍是有序的凸多边形），没有退化。

**质心归属 `centroid_nearest_ok = 40/40`**：对每个单元，取它的质心（多边形重心的精确计算），验证"质心的最近站点"确实等于这个单元所属的站点。40 个全部正确——**这是对单元划分正确性的强验证。**

## ⑦ 总结与延伸

### 7.1 技术局限性

- **O(n²) 复杂度**：半平面交法对每个站点要裁剪 n-1 条边，总复杂度 O(n²)。对 n=40 完全没问题，但 n 上到 10 万就需要真正的 Fortune 扫描线。
- **纯 CPU 单线程**：没有做任何并行化。实际上"每个站点独立裁剪"是**天然可并行**的（embarrassingly parallel），可以用 OpenMP 或 SIMD 轻松加速。
- **只处理点集，不处理加权/障碍物**：没有支持"加权 Voronoi"（每个站点有权重）和"带障碍物的测地 Voronoi"，这两种在实际中很常见。

### 7.2 可优化的方向

1. **换 Fortune 扫描线**：把复杂度降到 O(n log n)，这是"工程级"实现的必经之路。
2. **KD 树 / 网格加速最近邻判断**：渲染大图时，用空间数据结构替代暴力遍历，把像素着色的最近邻查询从 O(n) 降到 O(log n)。
3. **并行化裁剪**：每个站点的裁剪互不影响，天然可以用多线程同时跑。
4. **GPU 渲染**：用 fragment shader 做逐像素最近站点判断，天然并行，能在屏幕上实时交互式地看 Voronoi 图随站点拖拽而变化。

### 7.3 与本系列其他文章的关联

- 如果对**"空间最近邻查询"**感兴趣，可以回看之前做的 **KD 树 / 空间哈希**（11-22 空间哈希碰撞检测），它们和 Voronoi 图解决的是同一类"空间划分"问题，只是侧重点不同：Voronoi 图是"静态划分"，空间哈希是"动态查询"。
- 如果对**图形的程序化生成**感兴趣，Voronoi 图是 **WFC（11-16 波函数坍缩）**、**BSP 地牢生成**等技术的天然搭档——很多生成式地图的"分区"环节都可以用 Voronoi 图来做。
- 如果对**几何求交的坑**感兴趣，之前的 **Möller-Trumbore 光线-三角形求交（11-17）** 和 **多边形布尔运算（11-13）** 都踩过"浮点容差"的坑，和今天的教训一脉相承。
