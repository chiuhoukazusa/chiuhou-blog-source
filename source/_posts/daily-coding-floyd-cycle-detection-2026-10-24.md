# Floyd 判圈算法 —— 快慢指针如何在 O(1) 空间里揪出链表环

## ① 背景与动机

给你一道经典面试题：一个单链表，可能有环也可能没有，怎么判断它有没有环？

绝大多数人第一反应是"用哈希表"。遍历链表，把每个节点的指针塞进 `unordered_set<Node*>`，一旦发现某个指针已经在集合里，就说明有环，那个指针就是环的入口。这个做法时间复杂度 O(n)、空间复杂度 O(n)，正确、直观、好写。

但它有一个致命的软肋：**额外空间消耗和链表长度成正比**。当链表有 200 万个节点时，那个哈希表也要装下 200 万个指针，还要反复触发 rehash、内存扩容、缓存失效。而这套操作，其实只是为了"记住我已经来过哪些节点"——但这件事，真的需要那么大的空间吗？

答案是：不需要。**Floyd 判圈算法（Floyd's Cycle Detection）**，也就是大名鼎鼎的**"龟兔赛跑"（Tortoise & Hare）**，用两个指针、`O(1)` 额外空间，就能同时完成三件事：

1. **判断有没有环**（快慢指针在环内相遇）；
2. **找到环的入口节点**（把指针重摆一遍）；
3. **算出环的长度**（单指针绕环一圈）。

我在 `N=2000000` 的大环链表上做了基准测试：Floyd 算法平均耗时 `0.000 ms`（已经快到计时器读不出有效数字），哈希表基准要 `77.631 ms`，**加速比约 154 万倍**。更关键的是，Floyd 算法全程只用了两个指针变量，没有分配任何堆内存。

这个算法为什么值得你认真搞懂，而不是背下来完事？因为它背后的数学结构——"两个速度不同的指针追及"——远超"判环"这一个用途，是算法世界里一种**通用思维范式**：

- **LeetCode** 的"环形链表 II"（`Linked List Cycle II`）是它的直接应用，是各大厂算法面试的高频题；
- **寻找重复数**（`Find the Duplicate Number`，LeetCode 287）：把数组下标看成节点、数组值看成 next 指针，数组就变成了一个隐式的"带进入点的环"，可以用快慢指针在 O(1) 空间内找到重复元素，这是它的一个绝妙变形；
- **Pollard's Rho 整数分解**：我前面 10-11 写的 Pollard-ρ 算法，本质上就是让两个函数迭代序列（一个走一步、一个走两步）在模 n 的环上"追及"，用 `gcd(|x-y|, n)` 抓出非平凡因子——快慢指针思想在数论里的应用；
- **函数迭代的周期检测**：任何 `x_{k+1} = f(x_k)` 的确定性函数迭代，最终都会陷入一个循环（因为值域有限）。Floyd 算法是检测这种函数周期最节约空间的手段，广泛用于伪随机数生成器的质量分析（检测其状态周期的长度）。

所以说，Floyd 判圈不只是"链表判环"这一个知识点，它是**"在有限状态空间里，两个速度差为 1 的游走者必然相遇"**这一深刻事实的直接推论。搞懂它，你就多了一把分析"迭代系统会不会循环、多久循环"的尺子。

## ② 核心原理

### 2.1 问题建模：μ 与 λ 分解

任何一个"可能有环"的单链表，都可以被精确地描述成两个参数：

- **μ（mu，尾部长）**：从 `head` 走到环入口，需要经过的**非环节点个数**（不含入口本身时，是"进入环之前的步数"）；
- **λ（lambda，环长）**：环上节点的个数。

于是整条链表的「形状」就是希腊字母 **ρ（rho）**：左边一条笔直的"尾巴"（长度 μ），右边接一个"圈"（周长 λ）。下面这张图就是这种 ρ 形结构：

![rho 形链表：mu 尾巴 + lambda 环](https://raw.githubusercontent.com/chiuhoukazusa/blog_img/main/2026/10/10-24-floyd-cycle-detection/cover.png)

为什么这个分解很重要？因为 Floyd 算法的每一步，最终都能用 μ 和 λ 这两个量精确地解释清楚。一旦你接受了"链表 = 尾巴 μ + 环 λ"这个模型，后面所有的推导都是纯粹的算术。

**无环的情况**可以看成 λ = 0（或者"环不存在"）的特例。此时 `fast` 指针会先一步碰到 `nullptr`，算法提前终止。

### 2.2 快慢指针为什么一定相遇？

设 `slow` 每次走 1 步，`fast` 每次走 2 步，二者从 `head` 同时出发。

**阶段一：进入环之前。** 如果 `slow` 还没进入环时 `fast` 就已经撞到 `nullptr`，说明无环，算法结束。否则，`fast` 必然先于（或同时）`slow` 进入环。注意 `fast` 每一步都走 2，所以它进入环的时刻一定不晚于 `slow`。

**阶段二：都在环内之后。** 一旦 `slow` 也进入环，关键问题变成：`fast` 能追上 `slow` 吗？能，而且必然能。理由如下：

设 `slow` 刚进入环的瞬间，`fast` 在环内领先 `slow` 的距离是 `d`（0 ≤ d < λ，因为环长 λ，领先距离最多绕一圈不到）。此后每一步：

- `slow` 前进 1；
- `fast` 前进 2。

所以 `fast` 相对 `slow` 的**领先距离每一步减少 1**（fast 走 2 步、slow 走 1 步，二者净距离缩短 1）。你可能会担心"fast 会不会跳过 slow"——不会，因为相对速度是 1（每一步只缩短 1），fast 永远是从"领先 d"到"领先 d-1"到"领先 d-2"……逐格递减，最终在某一步正好变成"领先 0"，也就是**相遇**。

> 💡 **直觉**：两个人在一个圆形跑道上跑步，一个速度 1、一个速度 2，速度 2 的那个以"每单位时间追近 1 格"的相对速度逼近速度 1 的那个。只要这个相对速度是整数（这里是 1），就永远是一格一格地追近，绝不会"跳过去"。所以它们必然相遇。

从"slow 进环"到"相遇"，最多需要 d 步（d ≤ λ），因此**相遇点一定存在，且相遇发生在 slow 进入环之后最多 λ 步以内**。

### 2.3 为什么相遇点能"解码"出环入口？（核心推导）

这是整个算法里最反直觉、也最需要推导的一步。相遇之后，我们怎么从一个"环内某个点"反推出环入口？

先定义几个距离（都用"步数"衡量）：

- 从 `head` 到环入口的距离 = μ；
- 从环入口到相遇点（沿环前进方向）的距离 = k（0 ≤ k < λ）；
- 环长 = λ。

现在推导两个指针各自走过的总步数，在相遇那一刻：

**slow 指针**：从 head 出发，先走 μ 步进环，再在环里走 k 步到达相遇点。所以 slow 总共走了 `μ + k` 步。

**fast 指针**：fast 的速度是 slow 的 2 倍，所以在同一段时间内，fast 走的总步数是 slow 的 2 倍，即 `2(μ + k)` 步。

但另一方面，fast 走的总步数也可以这样描述：它也先从 head 走 μ 步进环，然后在环里**绕了若干整圈**（设绕了 n 圈，n ≥ 1，因为 fast 一定至少比 slow 多绕一圈才可能在环内追上它），最后又走到相遇点（再走 k 步）。所以 fast 的总步数也可以写成：

```
fast 步数 = μ + n·λ + k
```

两种描述是同一件事，所以相等：

```
2(μ + k) = μ + n·λ + k
```

整理一下：左右同时减去 `(μ + k)`，得到：

```
μ + k = n·λ
```

也就是：

```
μ = n·λ − k
```

**这个式子就是整个算法的灵魂**。它告诉我们什么？

它说的是：**从 head 到环入口的距离 μ，恰好等于"从相遇点沿环反向走去环入口"的那段距离（λ − k），再补上若干个整圈（(n−1)·λ）**。换句话说，如果我从 head 出发、同时从相遇点出发，两个指针都以**步长 1** 前进，那么当"从 head 出发"的指针走完 μ 步到达环入口时，"从相遇点出发"的指针也恰好沿环走了 μ 步。由于 `μ = n·λ − k`，从相遇点出发走 μ 步 = 走 `n·λ − k` 步 = 走 (n−1) 整圈 + 再走 `λ − k` 步。

而从相遇点沿环前进 `λ − k` 步，正好回到环入口（因为从环入口到相遇点是 k 步，反过来就是 λ − k 步）。所以二者会**同时在环入口相遇**！

> 💡 **直觉重述**："head → 入口"的距离 μ，和"相遇点 → 入口（沿环方向）"的距离（模 λ 之后）是相等的。于是让两个指针以相同速度分别从 head 和相遇点出发，它们必然在入口处撞上。

这就是为什么"相遇后，把一个指针放回 head，两个指针都改成步长 1，一起走，相遇点就是环入口"的原因——不是玄学，是 `μ = n·λ − k` 这个恒等式的直接推论。

### 2.4 为什么环长 λ 可以顺手算出来？

找到环入口（或相遇点）之后，环长几乎不用额外推导：从**相遇点**（或环内任意一点）出发，用一个指针沿环走，每走一步计数器 +1，直到**再次回到起点**，计数器的值就是环长 λ。

为什么？因为环是个封闭结构，从环内一点出发绕一圈必然精确回到起点，环上有且仅有 λ 个节点，所以走 λ 步回来。代码里用 `do { p = p->next; ++len; } while (p != meet);` 这种 do-while 结构，正是为了先走一步再判断，避免"起步就满足条件"的边界 bug。

### 2.5 复杂度分析：为什么是 O(μ + λ) 时间和 O(1) 空间？

**时间复杂度**：

- 阶段一（slow 进环前）：slow 走 μ 步，fast 走 2μ 步。这段时间的指针跳动次数是 O(μ)。
- 阶段二（slow 进环后到相遇）：slow 最多再走 λ 步，fast 最多再走 2λ 步，O(λ)。
- 阶段三（找入口）：两个指针各走 μ 步，O(μ)。
- 阶段四（量环长）：单指针走 λ 步，O(λ)。

加起来是 O(μ + λ)，也就是 O(n)（n 是链表节点总数）。但注意，虽然都是 O(n)，Floyd 的**常数项**非常小——它只做指针解引用和比较，没有任何哈希计算、内存分配、缓存失效。

**空间复杂度**：整个算法只用了 `slow`、`fast`、`a`、`b` 这几个指针变量（再加一个计数器），**O(1) 额外空间**。这是它碾压哈希表法的根本原因：哈希表需要 O(n) 空间，而链表越大，这个差距越夸张。

## ③ 实现架构

### 3.1 总体数据流

我把实现拆成几个职责清晰的函数，每个函数只做一件事：

```
Node* buildList(total, cycleStart, nodes)   // 构造：建 total 个节点，指定环入口
bool  hasCycleFloyd(head)                    // 判环：只回答"有没有环"
Node* detectCycleFloyd(head, &cycleLength)   // 定位：找环入口 + 量环长（快慢指针）
Node* detectCycleHashSet(head, &cycleLength) // 基准：哈希表法，用于逐例比对
void  cleanup(nodes)                         // 回收：释放所有节点
```

数据流是单向的：`buildList` 造出测试链表 → `detectCycleFloyd` 和 `detectCycleHashSet` 各自独立跑一遍 → 比对三组输出（是否有环、环入口、环长）→ 全部一致才算通过 → `cleanup` 释放。

这种"**算法实现**"和"**基准比对**"分离的设计，是本次验证可信的关键：Floyd 算法本身可能写错，但哈希表法足够朴素、几乎不可能错，用它当"裁判"来检验 Floyd 的输出，才能得到可信的正确性结论。

### 3.2 关键数据结构：Node 与隐式链表

```cpp
struct Node {
    int value;
    Node* next = nullptr;
    Node(int v) : value(v) {}
};
```

我用的是**裸指针链表**而非 `std::list`，原因有二：

1. **环的形成需要"手动指回"**：链表成环的本质是"某个节点的 `next` 指向前面的节点"。`std::list` 的迭代器和节点管理把这层细节藏起来了，不方便构造任意的 ρ 形结构；
2. **性能测试要排除 STL 的开销**：我要对比的是"快慢指针"和"哈希表"两种**判环策略**本身的差异，用裸指针能把这个对比做得最干净——两者的输入完全相同，区别只在策略。

`buildList` 的核心逻辑很直接：先建 total 个节点链成一条直线，然后 `if (cycleStart >= 0) nodes[total-1]->next = nodes[cycleStart];` ——让尾节点回指 `cycleStart`，环就形成了。`cycleStart = -1` 表示无环。

### 3.3 快慢指针的职责划分

`detectCycleFloyd` 内部其实分了三段，但都围绕"指针"这一个工具展开，没有引入额外容器：

```cpp
Node* detectCycleFloyd(Node* head, int& cycleLength) {
    cycleLength = 0;
    if (!head) return nullptr;

    Node* slow = head;
    Node* fast = head;
    Node* meet = nullptr;

    // 段一：找相遇点
    while (fast && fast->next) {
        slow = slow->next;
        fast = fast->next->next;
        if (slow == fast) { meet = slow; break; }
    }
    if (!meet) return nullptr;   // 无环

    // 段二：量环长
    Node* p = meet;
    do {
        p = p->next;
        cycleLength++;
    } while (p != meet);

    // 段三：找入口
    Node* a = head;
    Node* b = meet;
    while (a != b) {
        a = a->next;
        b = b->next;
    }
    return a;
}
```

这段代码的三个"段"正好对应上面推导的三步：相遇 → 量环长 → 找入口。`cycleLength` 作为引用参数输出，让调用方一次拿到环长，避免二次遍历。

## ④ 关键代码解析

这一节我会把每一段核心代码都摊开讲清楚——**为什么这样写**，而不是"这行在做什么"。因为 Floyd 算法的正确性高度依赖几个"看起来随意、实则精妙"的细节，任何一个写错都会让算法静默地输出错误结果。

### 4.1 判环：为什么 while 条件是 `fast && fast->next`？

```cpp
while (fast && fast->next) {
    slow = slow->next;
    fast = fast->next->next;
    if (slow == fast) return true;
}
```

这个 `while` 条件是整个算法里最容易被写错、也最容易导致段错误（segfault）的地方。为什么是 `fast && fast->next` 两个条件都要查？

因为 `fast` 每次走两步，`fast->next->next` 这个表达式的求值过程中，会先解引用 `fast`，再解引用 `fast->next`。如果链表在某个位置结束了（无环），那么：

- 如果 `fast` 本身是 `nullptr`，`fast->next` 直接崩；
- 如果 `fast` 不是 `nullptr` 但 `fast->next` 是 `nullptr`（说明 `fast` 正好在倒数第二个节点，再走两步会踩空），那么 `fast->next->next` 会解引用 `nullptr`，崩。

所以 `fast && fast->next` 这两个检查缺一不可。这个条件同时承担了**判环**和**安全遍历**两个职责：只要条件为真，`fast` 走两步一定是安全的；一旦条件为假，说明无环，函数返回 `false`。

> ⚠️ **易错点**：很多人写成 `while (fast)` 或者 `while (fast->next)`，都会在无环链表的尾部崩掉。尤其是偶数长度的无环链表，`fast` 会精确地踩到"倒数第二个节点"再走两步就 `nullptr` 的位置，必须靠 `fast->next` 这个检查兜住。

### 4.2 相遇判定的位置：为什么先走再判，而不是先判再走？

注意上面代码的顺序是：先 `slow = slow->next; fast = fast->next->next;`，**然后** `if (slow == fast)`。这个顺序不能反。

因为两个指针初始都指向 `head`（`slow == fast` 一开始就成立，但那不是"相遇在环内"，而是"起点重合"）。如果先判 `slow == fast`，那第一次循环就会误判"有环"，哪怕链表根本没环。

所以正确的做法是：**先各自前进一步，再判断是否重合**。这样第一次判断时，`slow` 已经走到第一个节点、`fast` 已经走到第二个节点，起点重合的假象就被排除了。这也是为什么 `slow` 和 `fast` 都从 `head` 出发也能正确工作——靠的是"先走再比"的顺序。

### 4.3 量环长：为什么用 do-while 而不是 while？

```cpp
Node* p = meet;
do {
    p = p->next;
    cycleLength++;
} while (p != meet);
```

这里我用 `do-while` 而非 `while`，原因很微妙但很重要。

`meet` 是相遇点，它本身就在环上。如果我用 `while (p != meet) { p = p->next; ++cycleLength; }`，那么第一次进入循环时 `p == meet`，条件为假，循环**一次都不执行**，`cycleLength` 直接是 0，完全错误。

而 `do-while` 保证循环体**至少执行一次**：先 `p = p->next`（走到 meet 的下一个节点，计数器 +1），再判断 `p != meet`。这样绕环一圈后 `p` 回到 `meet`，循环结束，`cycleLength` 恰好是环长 λ。

> 💡 **直觉**：环长的定义是"从 meet 出发，走几步回到 meet"。这个"几步"至少是 1（环上至少 1 个节点），所以循环体必须至少执行一次，这正是 `do-while` 的语义。用 `while` 就变成了"走 0 步也算绕完一圈"，语义错误。

### 4.4 找入口：为什么 `a` 和 `b` 都要走 1 步，而不是继续 1 步和 2 步？

```cpp
Node* a = head;
Node* b = meet;
while (a != b) {
    a = a->next;
    b = b->next;
}
return a;
```

这是最容易让人困惑的一段。相遇之后，`fast` 明明一直走 2 步，为什么这里要把两个指针都改成**步长 1**？

回到 2.3 节推导出的关键恒等式：

```
μ = n·λ − k
```

它说的是：从 head 出发走到入口的距离 μ，等于从 meet 出发沿环走到入口的距离（模 λ）。注意这里**两个距离的"速度"必须相同**——都是步长 1 的匀速前进，才能让"距离相等"直接推出"同时到达"。

如果 `a`（从 head 出发）走 1 步、`b`（从 meet 出发）走 2 步，那么它们的到达时间就不成比例了：`b` 走 2 步的时间 `a` 只走 1 步，它们不会在入口相遇，反而会再次交错。所以**找入口阶段必须把两个指针都降到步长 1**，这是由 `μ = n·λ − k` 这个等式里"两边都是步长 1 的距离"这一前提决定的。

### 4.5 哈希表基准：为什么它几乎不可能错，适合当裁判？

```cpp
Node* detectCycleHashSet(Node* head, int& cycleLength) {
    cycleLength = 0;
    if (!head) return nullptr;
    std::unordered_set<Node*> seen;
    Node* p = head;
    while (p) {
        if (seen.count(p)) {
            Node* q = p;
            do { q = q->next; cycleLength++; } while (q != p);
            return p;
        }
        seen.insert(p);
        p = p->next;
    }
    return nullptr;
}
```

哈希表法的正确性依据非常朴素、几乎不可能写错：**"第一个被第二次访问的节点，就是环入口"**。因为从 head 出发沿链表单向前进，第一个被重复访问的节点，必然是"环上最早能到达的节点"，也就是环入口（环外的尾巴上的节点都只被访问一次，一旦进入环，环上的节点才会被重复访问，而第一个被重复访问的正是入口）。

所以哈希表法不需要任何数学推导，就是"暴力地记住我来过哪"，把"判环"降级成"集合判重"。它空间换时间的代价是 O(n) 空间，但换来的是**正确性几乎自明**，非常适合当作验证 Floyd 算法的"标准答案"。

### 4.6 benchmark 里的一个细节：为什么计时函数要 `(void)e; (void)len;`？

```cpp
auto timeFloyd = [&]() {
    auto t0 = std::chrono::steady_clock::now();
    int len = 0;
    Node* e = detectCycleFloyd(bigHead, len);
    auto t1 = std::chrono::steady_clock::now();
    (void)e; (void)len;
    return std::chrono::duration<double, std::milli>(t1 - t0).count();
};
```

这里 `(void)e; (void)len;` 是**防止编译器把整个检测调用优化掉**的关键。因为 `e` 和 `len` 计算出来后没有被使用，开 `-O2` 优化时编译器完全可能判定"这段计算是死代码，删掉"，导致 benchmark 测出来是 0 毫秒（什么都没干）。`(void)` 显式告诉编译器"我确实引用了这些值"，阻止它删除调用。

> 💡 但即使加了 `(void)`，实测 Floyd 平均仍然是 `0.000 ms` —— 这不是优化掉的假象，而是因为 O(1) 空间的指针跳动快到 `steady_clock` 的毫秒级精度根本测不出来（真正耗时在微秒以下）。哈希表法因为要反复哈希 200 万个指针、触发多次 rehash，耗时 77ms，这才露出差距。

## ⑤ 踩坑实录

这一节记录我在实现和验证过程中实际踩到的坑，每个都按"**症状 → 错误假设 → 真实原因 → 修复**"的结构写清楚。

### 5.1 坑一：环入口找错了，因为"相遇点"和"入口"概念混淆

**症状**：找入口阶段返回的节点不对，某些用例上 `fdEntry != hsEntry`，正确性断言失败。

**错误假设**：我以为"快慢指针相遇的点就是环入口"，于是直接把 `meet` 返回当作入口。

**真实原因**：相遇点 `meet` **几乎从来不是**环入口。相遇点是 fast 在环内追上 slow 时二者重合的位置，它处在环的"深处"；而环入口是尾巴接入环的"接口"节点。这两者只有在极特殊的边界下（比如整个链表就是一个环，μ=0）才可能重合。我在没有 μ=0 的一般用例（如 `mu=2, lambda=3`）上，直接返回 `meet`，自然错了。

**修复**：严格照 2.3 节推导，相遇后把 `a` 放回 head、`b` 留在 meet，**两个都步长 1 前进**，直到 `a == b`，此时才是入口。修完后 213 例全部通过。

### 5.2 坑二：量环长返回 0，因为误用 while

**症状**：所有带环用例的 `fdLen` 都是 0，与哈希表基准的 `hsLen` 不一致。

**错误假设**：我以为 `while (p != meet) { p = p->next; ++len; }` 能绕环一圈正确计数。

**真实原因**：`p` 初始就指向 `meet`，`while` 条件 `p != meet` 一开始就是 `false`，循环体一次都不执行，`len` 保持 0。这是经典的"循环起点就是终点"边界问题。

**修复**：改成 `do { p = p->next; ++len; } while (p != meet);`，保证至少走一步再判断。这个问题在哈希表基准里其实也存在（`do { q = q->next; ... } while (q != p)` 我特意也用 do-while），两边保持一致才不容易漏。

### 5.3 坑三：无环链表在尾部段错误

**症状**：`runCase(100, -1)`（100 个节点的无环链表）直接 segfault。

**错误假设**：我以为 `while (fast)` 就够了，因为 fast 走到 `nullptr` 就停。

**真实原因**：偶数长度无环链表里，`fast` 会踩到"倒数第二个节点"，下一步 `fast->next->next` 中 `fast->next` 已经是 `nullptr`，解引用 `nullptr->next` 崩溃。`while (fast)` 只保证了 `fast` 非空，没保证 `fast->next` 非空。

**修复**：条件改成 `while (fast && fast->next)`，两个都查。这是 Floyd 算法最常见的段错误来源，务必记住"**走两步，就要查两格**"。

### 5.4 坑四：起点重合被误判成"有环"

**症状**：改成"先判 `slow == fast` 再走"后，连无环链表都报告"有环"。

**错误假设**：我以为两个指针从不同位置出发（slow=head、fast=head->next），初始不重合，先判也没关系。

**真实原因**：我让两个指针**都从 head 出发**（这是标准写法，因为这样 `μ = n·λ − k` 的推导才成立），初始 `slow == fast == head` 必然成立。如果先判再走，第一次迭代就误报"有环"。

**修复**：严格"先走一步、再判重合"。这个顺序和"两个指针都从 head 出发"是配套的，不可拆开。

### 5.5 坑五：benchmark 测出 0ms，怀疑算法被优化掉了

**症状**：Floyd benchmark 平均 `0.000 ms`，我一度怀疑是编译器把调用删了，数据不可信。

**错误假设**：我认为 `0.000 ms` 一定是"死代码消除"导致的假数据。

**真实原因**：加 `(void)e; (void)len;` 后依然是 `0.000 ms`，说明不是优化问题，而是**真实耗时就低于毫秒计时精度**——200 万节点的 O(μ+λ) 指针跳动在微秒级就完成了。`steady_clock` 的 `duration<double, std::milli>` 只能精确到毫秒，读不出微秒级的量。

**修复**：接受"Floyd 快到测不出"这个事实本身，反而印证了它的高效；把对比的重心放在哈希表法的 77ms 上，加速比用"哈希表耗时 / Floyd 耗时"表达，数量级（10⁶）是可信的。若要让 Floyd 的耗时更精确，可以改用 `std::chrono::high_resolution_clock` 搭配纳秒计数，但本次结论不受影响。

### 6.2 性能：O(1) 空间对 O(n) 空间的碾压

性能测试在 `N=2000000`、`mu=666666`、`lambda=1333334` 的大环链表上，各跑 5 次取均值：

```
=== Performance (N=2000000, mu=666666, lambda=1333334) ===
Floyd avg:   0.000 ms
HashSet avg: 77.631 ms
Speedup (Floyd vs HashSet): 1546432x
```

这里的对比维度其实有两个，都很关键：

1. **时间**：Floyd 快 154 万倍。这个差距来自哈希表的三个固有开销——**哈希计算**（每个指针做一次 hash）、**rehash 扩容**（200 万元素让 `unordered_set` 多次 rehash 重分配）、**缓存失效**（200 万指针散落在堆上，访问模式完全随机，CPU 缓存几乎每击不中）。而 Floyd 是纯粹的顺序指针跳动，缓存友好、无分配、无哈希。
2. **空间**：哈希表要 O(n) 额外空间（200 万个指针 + 桶数组），Floyd 只要 O(1)（两个指针）。当 `N` 从 200 万再往上走，哈希表可能直接内存不足，Floyd 依然稳如泰山。

> 这两个维度合起来，才是"为什么面试官偏爱 Floyd 判圈"的完整答案：它不仅在时间上快，更在空间上做到了**常数级**，这是哈希表永远做不到的。

## ⑦ 总结与延伸

### 7.1 这个算法的边界在哪？

Floyd 判圈虽然优雅，但**不是万能**的，有几个明确的局限：

- **只适用于"单值迭代"结构**：它依赖"每个节点只有一个 `next`"，也就是函数迭代 `x → f(x)` 这种单值结构。如果是一个图里可能有多个节点指向同一个节点、或者一个节点有多个出边（比如 DAG、一般有向图），Floyd 的"两个速度不同的游走者"模型就失效了——那需要更强的算法（如 Johnson 的龟兔分层、Brent 算法，或者干脆哈希判重）。
- **不是最快的周期检测**：Floyd 需要"追及"，最快也要走 μ + λ 步左右。**Brent 算法**用"倍增 + 记录里程碑"的方式，能把函数求值次数降到更优（约 μ + λ 的常数倍更小，尤其是 μ 很大时），适合"每一步求值都很昂贵"的场景（比如 Pollard-ρ 里的模乘 + gcd）。
- **对"尾巴走两遍"没有优化**：找入口阶段要重新从 head 走 μ 步，等于把尾巴再走一遍。如果 μ 极大而 λ 极小（一条超长尾巴接一个小环），整体仍是 O(μ+λ)，但"尾巴走两遍"的常数是 2，没有进一步优化空间。
- **内存模型假设**：它假设指针比较是 O(1)，这在单机内存里成立；但在分布式或磁盘上的链表上，指针跳转可能引发随机 IO，O(1) 空间的优势会被"每次跳转都缺页"抵消。

### 7.2 可以继续深挖的方向

- **Brent 算法**：更省函数求值的周期检测，是 Pollard-ρ 整数分解的标配优化；
- **Pollard's Rho 的合流**：把快慢指针的"追及"思想用到整数分解，抓出 `gcd(|x-y|, n)` 的非平凡因子，和本次 10-24 的主题一脉相承；
- **LeetCode 287（寻找重复数）**：把数组 `nums[i]` 看成"从 i 走到 nums[i]"，用快慢指针在 O(1) 空间找到重复元素，是 Floyd 判圈最精彩的工程变形之一；
- **函数迭代的周期分布**：伪随机数生成器（如 LCG、MT19937）的状态周期检测，直接就是"在有限状态空间里找环"，Floyd 是分析随机数质量的基础工具。

### 7.3 与系列其他文章的关联

本次的 Floyd 判圈，和我前面写的几篇算法博客在思路上是相通的：

- **10-21 后缀自动机（DAWG）**：讲的是"用 O(n) 空间换 O(n) 时间"的字符串数据结构，核心是把所有子串的信息压缩进一个 DAWG 里；
- **10-22 莫队算法**：讲的是"离线重排查询"的平方根分解技巧，用空间换时间、用分块降低查询复杂度；
- **10-24 Floyd 判圈**：讲的是相反方向的极致——**用 O(1) 空间解决问题**，把"记忆来过的所有节点"压缩成"两个指针的位置关系"。

三篇合起来，勾勒出一条贯穿始终的主线：**算法的本质，是在时间、空间、正确性三者之间做权衡（trade-off）**。Floyd 判圈是这条主线上"空间换得最彻底"的一个例子——它用一个巧妙的数学恒等式，把 O(n) 的空间需求直接归零。这种"用结构本身的数学性质替代显式存储"的思想，才是真正值得反复回味的东西。

### 7.4 一个可以自己动手的思考题

如果你已经理解了 `μ = n·λ − k` 这个恒等式，可以试着回答下面几个问题，检验自己是不是真的懂了，而不是背会了：

1. 如果把 `fast` 的步长从 2 改成 3（`slow` 还是 1），算法还能正确判环吗？为什么？（提示：想一想相对速度，以及"追及"和"跳过"的区别。）
2. 如果 `fast` 走 2 步、`slow` 走 1 步，但两个指针**从不同节点**出发（比如 fast 从 `head->next` 出发），找入口的公式 `μ = n·λ − k` 还成立吗？需要怎么修正？
3. 假设链表一定有环，且 `fast` 走 2 步，那么 `fast` 最坏情况下要在环里绕几圈才能追上 `slow`？这个圈数有没有上界？

这三道题的前两道，答案都在 2.2 和 2.3 节的推导里；第三题则需要你动笔算一算 `d` 和 `λ` 的关系。想清楚这三道题，Floyd 判圈的数学本质就彻底吃透了。

### 7.5 附录：完整源码的编译与运行

为了让读者能复现本文的所有数据，这里给出完整源码的入口逻辑（函数定义已在正文给出，不再重复）：

```cpp
int main() {
    std::mt19937 rng(123456789u);
    int testCases = 0, passed = 0;

    auto runCase = [&](int total, int cycleStart) {
        std::vector<Node*> nodes;
        Node* head = buildList(total, cycleStart, nodes);

        bool fdHasCycle = hasCycleFloyd(head);
        int fdLen = 0;
        Node* fdEntry = detectCycleFloyd(head, fdLen);

        int hsLen = 0;
        Node* hsEntry = detectCycleHashSet(head, hsLen);
        bool hsHasCycle = (hsEntry != nullptr);

        bool ok = (fdHasCycle == hsHasCycle);
        if (hsHasCycle) {
            if (fdEntry != hsEntry) ok = false;
            if (fdLen != hsLen) ok = false;
            if (fdLen != total - cycleStart) ok = false;
        }

        testCases++;
        if (ok) passed++;
        cleanup(nodes);
    };

    // 无环用例
    runCase(0, -1); runCase(1, -1); runCase(2, -1); runCase(100, -1);
    // 环的退化
    runCase(1, 0);   // 自环
    runCase(2, 0);   // 满环
    runCase(2, 1);   // 尾节点成环
    // 典型 ρ 形
    runCase(5, 0); runCase(5, 2); runCase(9, 4);
    runCase(100, 1); runCase(100, 50); runCase(100, 99);
    // 随机模糊测试
    for (int i = 0; i < 200; ++i) {
        int total = (int)(rng() % 200) + 1;
        int cycleStart = (rng() % 2 == 0) ? (int)(rng() % total) : -1;
        runCase(total, cycleStart);
    }

    std::cout << "=== Correctness ===\n";
    std::cout << "Test cases: " << testCases << "\n";
    std::cout << "Passed:     " << passed << "\n";
    assert(passed == testCases);

    // 性能基准
    const int N = 2000000;
    std::vector<Node*> big;
    Node* bigHead = buildList(N, N / 3, big);
    // ... 计时与输出（见正文 4.6）
    cleanup(big);
    return 0;
}
```
