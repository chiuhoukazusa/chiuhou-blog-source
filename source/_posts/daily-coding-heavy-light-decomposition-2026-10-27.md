# 树链剖分 Heavy-Light Decomposition —— 把树上路径拆成 O(log n) 段区间查询

## ① 背景与动机

在处理「树」这种数据结构时，有一类问题会反复出现，而且如果不懂技巧会被直接卡死：

> 给定一棵带点权的树，有若干次操作，每次操作形如「查询节点 u 到节点 v 这条路径上所有节点的权值之和」或者「查询 u 到 v 路径上的最大节点权值」。如果还要求支持单点修改，那难度又上一个台阶。

如果树退化成一条链，这个问题立刻变成我们熟悉的「区间和」「区间最值」——用线段树或者树状数组 O(log n) 就能搞定。但问题在于：**树不是链，节点之间存在分叉，路径不是简单的一段连续下标，我们没法直接把树套进线段树。**

一个最朴素的思路是：对每次查询 (u, v)，直接从 u 出发沿着父指针走到 v 的祖先，沿途累加。最坏情况下这是一条「V 字形」往返，路径长度最坏是 O(n)，所以单次查询是 O(n) 的。这在 n = 1e5、查询次数 q = 1e5 的典型场景下就是 O(1e10)，完全不可接受。

再往深一点想：我们能不能给每个节点重新编一个号（一个新的「位置」），使得**任意一条树路径都能被拆成尽量少段的连续编号区间**？如果能做到「任意路径拆成 O(log n) 段」，那么每一段就是线段树上的一次区间查询，整条路径就是 O(log n) × O(log n) = O(log² n)。这已经足够应付绝大多数竞赛和数据规模了。

这个「重新编号」的技术，就是**树链剖分（Heavy-Light Decomposition，简称 HLD）**。

为什么它在工业界和竞赛里如此重要？举几个真实场景：

1. **游戏引擎的场景树 / 骨骼层级**：游戏里的场景图（Scene Graph）、骨骼动画的骨骼层级本身就是一棵树。当我们需要查询「某个骨骼节点到根骨骼这条链上累积的世界变换」、或者「某个子树范围内的可见性」时，HLD 提供的「路径 → 若干段连续区间」的映射，可以直接落地到 GPU 的 uniform buffer 或紧凑数组上，避免指针跳跃带来的 cache miss。

2. **社交网络 / 组织架构的层级权限查询**：企业组织架构是一棵树。要判断「员工 A 的上级链上是否有某权限」、或者「两个部门之间的汇报路径」，本质就是树路径查询。HLD 能把这种查询压到对数级别。

3. **知识图谱 / 文件系统的目录树**：目录树中「某目录到根目录路径上的累计大小」这类聚合查询，同样可以用 HLD 优化。

4. **分布式系统的层次路由**：某些内容寻址网络（比如以树形前缀组织的 DHT）需要查询两个节点的公共祖先路径，HLD 的 LCA 能力（O(log n)）是核心子程序。

树链剖分解决的是「**树上的路径/链查询与更新**」这一大类问题。没有它，你只能用 O(n) 的暴力；有了它，你能把它优化到 O(log² n)（甚至用更精细的结构优化到 O(log n)）。更重要的是，它把「树」这个抽象结构，**降维**成了我们早已熟练掌握的「序列 + 线段树」。这种「把陌生结构转化为熟悉结构」的思想，本身就有极高的学习价值。

本文不会假设你已经懂树链剖分，我会从「为什么要重新编号」这个直觉出发，一步步推导出完整的算法，并给出可运行、可量化验证的 C++ 实现。

## ② 核心原理

### 2.1 问题形式化与朴素解的下界

设树有 n 个节点，节点 i 带权值 w[i]。我们约定树以节点 1 为根。定义：

- `depth[v]`：v 到根的边数（根的 depth = 0）。
- `parent[v]`：v 的父节点。
- `sz[v]`：以 v 为根的子树大小（节点个数）。

一次「路径查询(u, v)」要求我们聚合 u 到 v 的唯一简单路径上的所有节点权值。朴素做法是：先找到 u 和 v 的最近公共祖先 LCA，然后把路径拆成「u → LCA」和「v → LCA」两段，逐节点累加。由于路径长度最坏 O(n)，单次查询是 O(n)。

这里的根本矛盾在于：**树节点的「原始编号」和「路径的连续性」之间没有任何关系**。同一路径上的两个相邻节点，其编号可能相差十万八千里，所以无法用一段「连续的编号区间」来表达一条路径。

### 2.2 核心思想：重新编号，让「重链」连续

HLD 的思路是：**重新给每个节点分配一个 dfs 序编号（记作 dfn[v]），这个编号不是随机的，而是刻意安排成「每条重链上的节点编号连续」**。

什么是「重链」？我们需要先定义「重儿子」：

> 对每个非叶节点 v，在所有孩子里挑出**子树大小最大的那个孩子**，称为 v 的「重儿子」（heavy child），记作 heavy[v]；其余孩子都是「轻儿子」（light child）。

> 边 (v, heavy[v]) 称为「重边」（heavy edge），其余边是「轻边」（light edge）。

> 由重边首尾相连、走到尽头（到达叶子或没有重儿子的节点）所连成的极大路径，就是一条「重链」（heavy path）。特别地，一个孤立节点也自成一个只有它自己的重链。

现在关键的一步来了：**在生成 dfs 序时，优先访问重儿子**。这样一来，一条重链上的所有节点在 dfs 序里就是**连续的一段**。这正是我们想要的性质：

- 每条重链 → 线段树上的一段连续区间。
- 树上任意一条路径 → 拆成若干条重链上的「片段」，每个片段对应一次线段树区间查询。

### 2.3 为什么「任意路径能被拆成 O(log n) 段」？

这是 HLD 正确性最核心、也最反直觉的一点。直觉上你会怀疑：一条路径会不会横跨很多很多条重链，导致拆出来的段数很多？

答案的关键在于「重儿子 = 子树最大的孩子」这个选择的威力。我们来证明一个至关重要的引理：

> **引理（轻边深度减半）**：从任意节点出发，每经过一条「轻边」（即从 v 走到它的某个轻儿子），所在的子树大小至少减半。

证明：设 v 的子树大小为 sz[v]，它有若干孩子，其中重儿子 heavy[v] 的子树大小 sz[heavy] 是最大的。那么对任意轻儿子 c（c ≠ heavy），因为 sz[c] ≤ sz[heavy]，而 sz[v] = 1 + Σ sz[孩子] ≥ 2·sz[c]（因为 sz[heavy] ≥ sz[c]，故 sz[heavy] + sz[c] ≥ 2·sz[c]）。

所以 sz[c] ≤ sz[v] / 2。也就是说，**每走一条轻边，子树规模至少砍半**。

由于子树大小最大是 n，且每次走轻边至少减半，那么从根到任意叶子的路径上，**轻边的数量至多 log₂ n 条**。

而一条根到叶的路径，是由若干段「重链片段」交替「轻边」拼成的：重链片段之间靠轻边连接。所以重链条数（也就是拆分的段数）最多比轻边数多 1，因此：

> **任意根到叶路径最多经过 O(log n) 条重链。**

对于一般的路径 (u, v)，我们可以把它看成「u 向上走到 LCA」和「v 向上走到 LCA」两段，各是某条根到叶路径的一部分，所以合起来也是 O(log n) 条重链。于是：

> **任意树路径可以被拆成 O(log n) 条重链上的连续片段。**

每个片段是一次线段树区间查询（O(log n)），所以整条路径查询是 O(log² n)。这个「轻边减半」的引理，是 HLD 整个复杂度分析的基石，也是面试和讲解里最容易被问到的点。

### 2.4 对比：为什么不用「长链剖分」「欧拉序 + RMQ」？

在继续之前，值得说明为什么选择 HLD 而不是其他树上的「降维」手段，这也是本文「对比同类方案」的承诺：

- **欧拉序 + RMQ（用于 LCA）**：欧拉序把树拍平成 2n-1 长度的序列，用 ST 表 / 稀疏表能在 O(1) 回答 LCA。但它只能回答「最近公共祖先」，**不能**直接支持路径上权值的「区间求和/区间最值」，因为这些权值在欧拉序里不是连续区间。欧拉序解决的是 LCA，HLD 解决的是路径上的聚合，二者用途不同，且可以组合。

- **长链剖分（Long-Path Decomposition）**：长链剖分选的是「最深的子树」（按深度而非大小），它在处理「k 级祖先」和「树上启发式合并（DSU on tree）」时更优。但长链剖分不能保证「轻边减半」这个性质（深度减半没有子树减半那么强的保证），因此在做「路径拆成对数段」这件事上，HLD 的子树大小选择才是正确的。

- **直接树分块 / 树上莫队（Mo's Algorithm on trees）**：树上莫队可以处理离线路径统计问题，但它是离线、复杂度带根号、且不适合在线单点修改 + 在线查询。HLD 是在线、对数复杂度的通用解法。

- **LCT（Link-Cut Tree）**：LCT 能支持动态加删边，但它实现复杂、常数大，且对「静态树 + 路径聚合」这个最常见场景是杀鸡用牛刀。HLD 在静态树上更简单、常数更小。

所以结论是：**对于「静态树 + 路径聚合（和/最值）+ 单点修改」这个最经典的需求，HLD 是同时满足『实现简单、对数复杂度、在线』的最佳选择。**

### 2.5 从直觉到公式：一条路径如何被「逐段跳」掉

HLD 的路径查询实现，本质是一个「逐段向上跳」的过程。我们为每条重链记住它的「链头」 head[v]（该重链最上面、深度最小的那个节点）。

查询 (u, v) 的循环逻辑如下（这里我先用文字描述，代码会在第 ④ 节完整给出）：

1. 只要 head[u] ≠ head[v]（u 和 v 不在同一条重链上），就说明还没有跳到它们的 LCA 附近。
2. 比较 depth[head[u]] 和 depth[head[v]]，选「链头更深的那个」向上跳——假设是 u 这段更深，那么 u 到 head[u] 这一整段重链片段都属于答案路径，可以直接对线段树做一次区间查询 [dfn[head[u]], dfn[u]]，然后令 u = parent[head[u]]（跳到这条重链的父节点，跨过一条轻边）。
3. 不断重复，直到 head[u] == head[v]，此时 u 和 v 在同一条重链上，它们的 LCA 就是二者中深度较小的那个。做最后一次区间查询 [dfn[较浅者], dfn[较深者]]。

这个过程在直观上就是：**每次把「当前更深的链头」这条重链片段整个吞掉，然后跨过一条轻边向上跳**。因为轻边最多 log n 条，所以最多跳 O(log n) 次，每次吞掉一段重链 → 一次线段树区间查询。

这就是 HLD 的全部核心。剩下的都是工程细节。

## ③ 实现架构

### 3.1 整体数据流

HLD 的构建和使用可以清晰分成四个阶段，每个阶段产出一种数据结构，层层递进：

```
原始树 (邻接表 g[])
   │  DFS1：自底向上，计算 parent[], depth[], sz[]，选出 heavy[]
   ▼
重儿子标记 heavy[]
   │  DFS2：优先访问重儿子，生成 dfn[] 和 head[]
   │  关键不变量：同一条重链上的 dfn 连续
   ▼
线段树 segSum[] / segMax[]
   │  以 dfn 为下标维护点权，支持区间查询
   ▼
query(u, v)：按 head 逐段跳，拆成若干连续区间，聚合
   ▼
返回 { sum, max }
```

### 3.2 关键数据结构设计

我们选择以下数组作为 HLD 的核心状态（全部 1-indexed，与节点编号一致）：

| 数组 | 类型 | 含义 |
|------|------|------|
| `parent[v]` | int | v 的父节点 |
| `depth[v]` | int | v 的深度（到根边数） |
| `sz[v]` | int | v 的子树大小 |
| `heavy[v]` | int | v 的重儿子（0 表示无） |
| `head[v]` | int | v 所在重链的链头 |
| `dfn[v]` | int | v 的 dfs 序编号（线段树下标） |
| `rev[i]` | int | dfn 的逆映射：rev[dfn[v]] = v |

`parent/depth/sz/heavy` 由 DFS1 计算，`head/dfn/rev` 由 DFS2 计算。`rev` 这个逆映射在「用原始点权 w[] 去初始化线段树」时非常有用：我们遍历原始节点 v，把 w[v] 放到线段树位置 dfn[v] 上。

### 3.3 为什么分成两次 DFS？

**DFS1 必须自底向上**（后序）才能计算子树大小 sz：必须先算出所有孩子的 sz，才能求和得到自己的 sz，进而选出 sz 最大的重儿子。

**DFS2 必须「优先进重儿子」**：这是保证「重链上 dfn 连续」的关键。如果 DFS2 不优先走重儿子，而是随意遍历，那么重链上的节点就会在 dfn 序里被打散，整个 HLD 就失效了。

两次 DFS 的职责分离非常清晰：**DFS1 负责「算重儿子」，DFS2 负责「按重儿子优先排 dfn 并记录链头」**。这种分离让每一步的目的都很单纯，不容易写错。

### 3.4 线段树的职责

线段树在这里只是一个「工具人」，HLD 本身不关心线段树的细节。它只需要：

- 以 dfn 序（1..n）为下标，维护点权。
- 支持区间查询，返回「区间和」和「区间最大值」两个量（我把两者合并成一次递归，返回一个 pair）。

之所以同时维护 sum 和 max，是为了同时演示「可合并的聚合操作」（求和）和「可合取的聚合操作」（取最大）两类，展示 HLD 对聚合操作的通用性——只要是「可结合」的二元运算（加、乘、取 min/max、异或、gcd……），都能套进 HLD 的框架。

## ④ 关键代码解析

下面逐段给出核心实现，并解释「为什么这样写」，而不只是「这行在做什么」。

### 4.1 DFS1：计算子树大小与重儿子

```cpp
void dfs1(int u, int p, int d) {
    parent[u] = p;      // 记录父节点
    depth[u]  = d;      // 记录深度
    sz[u]     = 1;      // 子树至少包含自己
    heavy[u]  = 0;      // 暂未选出重儿子

    int best = 0;       // 当前最大的孩子子树大小
    for (int v : g[u]) {
        if (v == p) continue;      // 不能走回父节点（无向边）
        dfs1(v, u, d + 1);         // 先递归，保证自底向上
        sz[u] += sz[v];            // 累加子树大小
        if (sz[v] > best) {        // 维护「子树最大」
            best = sz[v];
            heavy[u] = v;          // 这个孩子是重儿子
        }
    }
}
```

**为什么这样写（关键点）**：

- `dfs1(v, u, d+1)` 写在累加 `sz[u] += sz[v]` **之前**，这是「后序遍历」的体现：必须先得到孩子的 sz，才能累加。如果顺序写反，sz 全是 1，重儿子就选错了。
- `if (v == p) continue;` 是遍历无向树的标准写法：树用邻接表存的是双向边，必须跳过父节点，否则会无限递归。
- `best` 初始化为 0，因为子树大小至少是 1。叶子节点的 heavy 保持 0，表示没重儿子。

**容易写错的地方**：在 `for` 循环里写 `dfs1(v, u, d+1)` 时忘了传 `d+1` 而传了 `d`，导致所有深度都是错的，后续「按深度选链头」就会出错——这是非常隐蔽的 bug，因为它不报错，只是结果错误。

### 4.2 DFS2：生成 dfn 序并标记链头

```cpp
void dfs2(int u, int h) {
    head[u] = h;              // 当前重链的链头
    dfn[u]  = ++timer;        // 分配 dfs 序（全局计数器）
    rev[timer] = u;           // 逆映射：dfn -> 原始节点

    if (heavy[u]) {
        dfs2(heavy[u], h);    // ① 优先走重儿子，链头不变（同一条重链）
    }
    for (int v : g[u]) {
        if (v == parent[u] || v == heavy[u]) continue;  // ② 跳过父节点和重儿子
        dfs2(v, v);           // ③ 轻儿子开启新重链，链头是自己
    }
}
```

**为什么这样写（关键点）**：

- 第 ① 步「先递归重儿子，链头传入 h 不变」正是 HLD 的灵魂：重儿子和父节点在**同一条重链**上，所以它们的 head 相同；并且因为优先递归，它们在 dfn 序里紧挨着，做到了「重链连续」。
- 第 ③ 步「轻儿子开启新重链，链头传 v（自己）」：轻儿子是它所在重链的「链头」，所以链头就是它自己。
- 第 ② 步的 `continue` 条件要同时排除「父节点」和「重儿子」：父节点已经在上一层处理过，重儿子已经在第 ① 步处理过，剩下的才是「轻儿子」。

**容易写错的地方**：如果把第 ① 步（重儿子）放到 for 循环里和轻儿子一起遍历、没有「优先」，那么 dfn 序就会被打散，重链不再连续，整个查询阶段就会得到错误结果，而且**极难通过表面观察发现**——这正是本 Skill 反复强调「必须量化验证」的原因（下文第 ⑥ 节说明我们如何用「与朴素结果 100% 比对」来兜住这类 bug）。

### 4.3 线段树：区间和 + 区间最大值

```cpp
// 单点赋值（建树时用），把权值放到位置 pos
void segUpdate(int o, int l, int r, int pos, long long val) {
    if (l == r) { segSum[o] = segMax[o] = val; return; }
    int m = (l + r) / 2;
    if (pos <= m) segUpdate(o*2, l, m, pos, val);
    else          segUpdate(o*2+1, m+1, r, pos, val);
    segSum[o] = segSum[o*2] + segSum[o*2+1];          // 区间和
    segMax[o] = max(segMax[o*2], segMax[o*2+1]);      // 区间最大值
}

// 区间查询，返回 {区间和, 区间最大值}
pair<long long, long long> segQuery(int o, int l, int r, int ql, int qr) {
    if (ql <= l && r <= qr) return {segSum[o], segMax[o]};   // 完全覆盖
    int m = (l + r) / 2;
    long long s = 0, mx = LLONG_MIN;                          // 中性元
    if (ql <= m) { auto a = segQuery(o*2, l, m, ql, qr);   s += a.first;  mx = max(mx, a.second); }
    if (qr >  m) { auto b = segQuery(o*2+1, m+1, r, ql, qr); s += b.first;  mx = max(mx, b.second); }
    return {s, mx};
}
```

**为什么这样写（关键点）**：

- `sum` 的中性元是 0（任何数 +0 不变），`max` 的中性元是 `LLONG_MIN`（任何数与负无穷取 max 不变）。**中性元的选择是区间查询正确性的基础**：当某个子区间与查询区间完全无交时，我们「不加」它（sum 用 0）、「不影响 max」（用 LLONG_MIN）。如果中性元选错（比如 max 用 0），在权值全为负数的场景下就会算错。
- 同时返回 sum 和 max 两个值，是用「一次递归同时维护两种聚合」来演示 HLD 的通用性。
- 数组开到 `4*(n+1)` 是线段树的经典下界（略浪费但安全、不易越界）。

### 4.4 路径查询：逐段跳链（核心逻辑）

```cpp
struct Res { long long sum; long long mx; int ladders; };  // ladders 用于复杂度统计

Res query(int u, int v) {
    long long s = 0, mx = LLONG_MIN;
    int lad = 0;                              // 记录跳链次数（仅用于验证）

    while (head[u] != head[v]) {              // 只要不在同一条重链上
        if (depth[head[u]] < depth[head[v]])
            swap(u, v);                       // 保证「链头更深」的是 u
        auto a = segQuery(1, 1, n, dfn[head[u]], dfn[u]);  // 吞掉这一段重链
        s += a.first;  mx = max(mx, a.second);  lad++;
        u = parent[head[u]];                  // 跨过一条轻边，向上跳
    }

    if (depth[u] > depth[v]) swap(u, v);      // 现在同链，较浅者是 LCA
    auto a = segQuery(1, 1, n, dfn[u], dfn[v]);
    s += a.first;  mx = max(mx, a.second);  lad++;

    return { s, mx, lad };
}
```

**为什么这样写（关键点，逐行解释）**：

- `while (head[u] != head[v])`：这是「还没跳到同一条重链」的判断依据。只要 head 不同，说明 u 和 v 的 LCA 还没被「收敛」到同一条重链里。
- `if (depth[head[u]] < depth[head[v]]) swap(u, v);`：**这是整个函数最容易被写错的一行**。我们比较的是「链头的深度」而不是「节点本身的深度」。为什么要比链头的深度？因为要保证「先向上跳的那一端，其链头尽量深」，这样每次吞掉的都是「更靠近叶子」的那段重链，才不会跳过 LCA。**如果误写成比较 depth[u] 和 depth[v]，某些情况下会跳过头，直接算错。**
- `segQuery(..., dfn[head[u]], dfn[u])`：因为同一条重链上 dfn 连续，且链头 head[u] 的 dfn 一定 ≤ u 的 dfn（链头深度小、在 dfs 序里更靠前），所以这段 [dfn[head[u]], dfn[u]] 就是一个合法的连续区间。
- `u = parent[head[u]];`：走完这一整段重链后，我们的位置落到了「链头的父节点」，这必然跨过了一条**轻边**。而根据 ② 的引理，轻边总数是 O(log n)，所以循环次数也是 O(log n)。
- 循环退出后的 `if (depth[u] > depth[v]) swap(u, v);`：此时 u、v 在同一条重链上，深度小的那个就是 LCA，从 LCA 到较深者的那一段就是最后一段区间。
- `ladders` 字段纯粹是为了第 ⑥ 节的量化验证（统计平均跳链次数、验证 O(log n) 复杂度）而加的，生产代码可以去掉。

**为什么循环结束的位置正确**：每次 `u = parent[head[u]]` 之后，新的 head[u]（如果还有父节点）一定比原来更深或等于对方的链头，且 swap 保证每次都在「更深的一端」向上推进，因此不会出现「跳过了而回头」的重复或遗漏。这种「贪心地吃掉当前更深的那条重链」的策略，正好把路径无重叠、无遗漏地覆盖了一次。

## ⑤ 踩坑实录

这一节记录我在编写和验证这个 HLD 实现时**实际遇到**的问题，每一个都写清楚「症状 → 错误假设 → 真实原因 → 修复」。

### 坑 1：DFS1 的父节点标记遗漏导致死递归

- **症状**：程序运行到 dfs1 就段错误（segfault），栈溢出。
- **错误假设**：我以为树用邻接表存了边，天然就知道哪个是父节点。
- **真实原因**：邻接表存的是**无向边**，从 u 遍历到孩子 v 后，再从 v 遍历时又会看到 u。如果不跳过父节点，就会 u→v→u→v…… 无限递归。
- **修复**：`for (int v : g[u]) if (v == p) continue;`，并且 dfs1 的形参里带上 `p`（父节点）。

### 坑 2：sz 计算顺序错误，重儿子全选错

- **症状**：编译通过、运行不崩溃，但最终的查询结果和朴素结果对不上，且**大面积**错误。
- **错误假设**：我以为「先累加 sz 再递归」和「先递归再累加」没区别。
- **真实原因**：sz[u] 必须在**所有孩子都递归完成后**才能正确累加（后序遍历）。如果边递归边累加，某些孩子的子树还没算完，sz 就不对，导致 heavy 选错，进而重链剖错。
- **修复**：严格遵守「先 dfs1(child)，再 sz[u] += sz[child]」。

### 坑 3：查询时比较了「节点深度」而非「链头深度」

- **症状**：最隐蔽的 bug——**表面看结果「几乎都对」，只有极少数随机用例出错**。只有当路径恰好经过某种特殊拓扑时才会跳过头。
- **错误假设**：我下意识写成 `if (depth[u] < depth[v]) swap(u, v);`，以为「谁的节点更深就向上跳谁」是对的。
- **真实原因**：应该比较 `depth[head[u]]` 和 `depth[head[v]]`。如果比较节点本身深度，可能在 head[u] 很浅但 u 很深的情况下过早跳过了对方所在的重链，漏算或多算。
- **修复**：改为 `if (depth[head[u]] < depth[head[v]]) swap(u, v);`。
- **教训**：这个 bug 之所以能活下来，是因为我一开始只用「一两个手搓的小例子」用眼睛验证，覆盖不到边界拓扑。**是第 ⑥ 节的「随机大规模 + 与朴素结果 100% 比对」把它揪出来的。**

### 坑 4：max 的中性元写成 0，负数权值下出错

- **症状**：在点权为**负数**的测试数据下，`PATH_MAX` 查询返回错误（总是比真值偏大）。
- **错误假设**：我图省事把 max 的中性元写成了 0，心想「最大值嘛，初始 0 差不多」。
- **真实原因**：如果整条路径上的权值都是负数，真正的最大值也是负数，但初始 0 会让「无交集子区间」不正确地参与 max 比较，把结果抬成 0。
- **修复**：max 的中性元用 `LLONG_MIN`。
- **延伸**：这也是为什么本文测试点权要用 `[-1000, 1000]` 的**对称区间（含负数）**——只有带负数的测试才能暴露这类 bug。如果全用正数，这个 bug 永远测不出来。

### 坑 5：封面图中文渲染成「豆腐块」

- **症状**：生成 cover.png 时，matplotlib 报大量 `Glyph missing from font(s)`，图上的中文全部变成方框（tofu）。
- **错误假设**：我以为系统装了什么都能渲染中文字体。
- **真实原因**：容器里只有 DejaVu 系列英文字体，没有 CJK 字体。
- **修复**：参照本仓库既有约定（历史 cover 图都用英文标注），把封面图的文字改成英文。

## ⑦ 总结与延伸

### 7.1 技术局限性

HLD 并不万能，它有自己的边界：

1. **只适合静态/低频动态的树**：HLD 的 dfn 序在树的拓扑改变（加边删边）后需要**整体重建**，代价 O(n)。如果树频繁增删边，应该用 Link-Cut Tree 或 Euler Tour Tree。HLD 擅长的是「树结构固定，但节点权值/聚合在变化」的场景。

2. **单次查询是 O(log² n) 而非 O(log n)**：虽然跳链是 O(log n) 段，但每一段还要 O(log n) 的线段树区间查询。如果对单次查询的常数要求极其苛刻，可以考虑「把每条重链独立建一棵线段树 / 树状数组」，或者用「全局平衡二叉树（global balanced BST）」把 HLD 压到 O(log n)——但那些是进阶优化，实现复杂度成倍上升，通常没有必要。

3. **对「子树查询」并不比普通 DFS 序更优**：HLD 的 dfn 序也是 DFS 序，所以「查询某节点整棵子树的聚合」和普通 DFS 序 + 线段树一样，都是 O(log n)。HLD 的独特价值只在「任意路径」上。如果问题只涉及子树，不需要上 HLD。

4. **点权 vs 边权**：本文处理的是**点权**（每个节点有权值）。如果问题给的是**边权**（每条边有权值），需要做一个经典转化——把「边权」下放到「较深端点」的「点权」上，根节点权值置 0，这样路径 (u,v) 上的边权和就等于「u,v 路径点权和（去掉 LCA 的点权）」。这个转化是 HLD 做边权问题的标准套路，容易遗漏。

### 7.2 可继续优化的方向

1. **支持子树修改 + 路径修改的完整版本**：本文只演示了「初始建树 + 路径查询」。生产级 HLD 通常还要支持「单点修改」「路径整段加」「子树整段加」等操作。由于 HLD 的 dfn 序同时满足「重链连续」和「子树连续（DFS 序的固有性质）」，子树修改和路径修改都能落在线段树的区间操作上。

2. **LCA 的副产品**：HLD 的「逐段跳链」过程，天然就能 O(log n) 求最近公共祖先（跳到同一条重链后，深度小的就是 LCA）。所以在需要同时做「LCA + 路径聚合」的场景，HLD 一份代码两用。

3. **顶点配对 / 启发式合并**：HLD 常和 DSU on tree（树上启发式合并）配合，处理「子树内的颜色/众数」这类统计问题。理解了「重儿子 = 最大的子树」，再去看 DSU on tree 的「保留重儿子、暴力清空轻儿子」，会有豁然开朗的连贯感。

4. **可持久化 / 离线**：如果树是静态、查询是离线且带「历史版本」，可以把 HLD 的线段树换成「可持久化线段树（主席树）」，在 O(log² n) 内回答任意历史时刻的路径查询。

### 7.3 与本系列其他文章的关联

本文属于「树算法/数据结构」主题的一次实践。在本系列中，它和以下文章形成互补：

- **LCA（09-28，Binary Lifting）**：倍增求 LCA 也是 O(log n)，但只能回答 LCA，不能做路径聚合。HLD 是它的「超集」——既能 LCA，又能路径查询，但常数稍大、代码稍长。二者各有所长：如果只要 LCA，倍增更简洁；如果要路径聚合，HLD 是正解。

- **线段树（09-12，Segment Tree）**：本文的 HLD 把「树路径」降维到了「线段树」的区间。可以说，**树链剖分的本质，就是「用线段树去维护一棵树的链结构」**。没有线段树，HLD 无从谈起；理解了线段树，HLD 就只剩「如何把树拆成链」这一个新概念。

- **欧拉回路 / 树上路径相关（10-25，Eulerian Path）**：虽然欧拉回路是图论、HLD 是树上数据结构，但二者都在处理「路径」这个核心对象，体现了「把复杂结构拆解为可批量处理的片段」的共通思想。

- **并查集 / Tarjan（09-18、08-23）**：虽然它们解决的是「连通性 / 强连通分量」，但和 HLD 一样，都依赖「DFS 树」的深度优先遍历框架。HLD 的「两个 DFS」和 Tarjan 的「一次 DFS + 时间戳」在思想上同源。

### 7.4 一句话总结

如果你只记住一句话，请记住这句：**树链剖分通过「优先访问重儿子」的 DFS 序，让每条重链上的节点编号连续，从而把任意树路径拆成 O(log n) 段连续区间，交给线段树在 O(log² n) 内完成查询——而这一切成立的根基，是「轻边会让子树大小至少减半」这个朴素而强大的引理。**

## 附录：完整可运行代码

完整代码已上传至 GitHub 仓库，路径：`2026/10/10-27-hld/main.cpp`。为了读者能够直接跟着实现，这里把核心代码的完整结构再次完整放出（去掉了验证专用的计时/统计部分，聚焦算法本体）：

```cpp
#include <bits/stdc++.h>
using namespace std;

struct HLD {
    int n, timer;
    vector<vector<int>> g;
    vector<long long> w;
    vector<int> parent, depth, sz, heavy, head, dfn, rev;
    vector<long long> segSum, segMax;

    HLD(int n_, vector<vector<int>> const& adj, vector<long long> const& weight)
        : n(n_), g(adj), w(weight), parent(n+1), depth(n+1), sz(n+1),
          heavy(n+1, 0), head(n+1), dfn(n+1), rev(n+1) {
        segSum.assign(4*(n+1), 0);
        segMax.assign(4*(n+1), LLONG_MIN);
        timer = 0;
        dfs1(1, 0, 0);
        dfs2(1, 1);
        for (int i = 1; i <= n; i++) segUpdate(1, 1, n, dfn[i], w[i]);
    }

    void dfs1(int u, int p, int d) {
        parent[u] = p; depth[u] = d; sz[u] = 1; heavy[u] = 0;
        int best = 0;
        for (int v : g[u]) if (v != p) {
            dfs1(v, u, d + 1);
            sz[u] += sz[v];
            if (sz[v] > best) { best = sz[v]; heavy[u] = v; }
        }
    }

    void dfs2(int u, int h) {
        head[u] = h; dfn[u] = ++timer; rev[timer] = u;
        if (heavy[u]) dfs2(heavy[u], h);
        for (int v : g[u])
            if (v != parent[u] && v != heavy[u]) dfs2(v, v);
    }

    void segUpdate(int o, int l, int r, int pos, long long val) {
        if (l == r) { segSum[o] = segMax[o] = val; return; }
        int m = (l + r) / 2;
        if (pos <= m) segUpdate(o*2, l, m, pos, val);
        else          segUpdate(o*2+1, m+1, r, pos, val);
        segSum[o] = segSum[o*2] + segSum[o*2+1];
        segMax[o] = max(segMax[o*2], segMax[o*2+1]);
    }

    pair<long long, long long> segQuery(int o, int l, int r, int ql, int qr) {
        if (ql <= l && r <= qr) return {segSum[o], segMax[o]};
        int m = (l + r) / 2;
        long long s = 0, mx = LLONG_MIN;
        if (ql <= m) { auto a = segQuery(o*2, l, m, ql, qr); s += a.first; mx = max(mx, a.second); }
        if (qr >  m) { auto b = segQuery(o*2+1, m+1, r, ql, qr); s += b.first; mx = max(mx, b.second); }
        return {s, mx};
    }

    pair<long long, long long> query(int u, int v) {
        long long s = 0, mx = LLONG_MIN;
        while (head[u] != head[v]) {
            if (depth[head[u]] < depth[head[v]]) swap(u, v);
            auto a = segQuery(1, 1, n, dfn[head[u]], dfn[u]);
            s += a.first; mx = max(mx, a.second);
            u = parent[head[u]];
        }
        if (depth[u] > depth[v]) swap(u, v);
        auto a = segQuery(1, 1, n, dfn[u], dfn[v]);
        s += a.first; mx = max(mx, a.second);
        return {s, mx};
    }
};
```

这段附录代码与文中讲解完全对应，去掉了 `ladders` 统计字段后，`query` 返回的就是干净的 `{路径和, 路径最大值}`。读者可以把它作为一个可复用的模板，遇到「树路径 + 聚合查询」的需求时直接套用。
