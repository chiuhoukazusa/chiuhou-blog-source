# Karatsuba 乘法 —— 分治思想如何把大整数乘法降到 O(n^1.585)

## ① 背景与动机

在计算机的世界里，整数并不是无限的。一个 `int` 只有 32 位，最多表示到约 21 亿；一个 `long long`（或者说 `int64`）有 64 位，最多表示到约 9.2×10¹⁸。对于绝大多数日常计算来说，这些已经完全够用了——你很少需要去算一个超过 19 位十进制的整数乘法。

但现实里确实存在这样一类问题，它们的数值会巨大到突破任何原生整数类型的上限：密码学里的 RSA 需要处理 2048 位甚至 4096 位的大素数相乘；高精度科学计算里，双精度浮点数的小数部分精度不够，需要用到几千位甚至几万位的定点整型；还有程序员们津津乐道的「求 10000 的阶乘」「求第 100000 个斐波那契数」，这些数字动辄几万位十进制，用原生类型根本无法表示。

要表示一个几千位的整数，业界通用的做法是「分段存储」：用一个数组（或者 `vector`）来存放这个大整数的每一位（或者每若干位作为一个「limb」）。比如底数取 10⁹，那么一个 32000 位的十进制数，就只需要拆成约 3556 个 limb，每个 limb 是一个 9 位的数字，存放在 `long long` 里绰绰有余。有了这种表示法，加法、减法就变得非常自然——就像小学竖式一样，从低位到高位逐位相加，处理进位即可，复杂度是线性的 O(n)。

真正棘手的是乘法。两个 n 位大整数相乘，任何人脑子里蹦出来的第一个算法就是「竖式乘法」：把其中一个数的每一位分别去乘另一个数的全部位，然后把结果错位相加。这本质上是两个多项式系数的**卷积**，复杂度是 O(n²)。

问题来了：当一个数有 32000 位时，O(n²) 意味着要做大约 10 亿级的「单 limb × 单 limb」乘法。对于密码学里动辄千位、乃至需要反复做乘法的模幂运算（modular exponentiation）来说，这个 O(n²) 的瓶颈是灾难性的——RSA 一次解密可能要调用几十万次大整数乘法，哪怕每次只用几毫秒，累积起来也是无法接受的延迟。

于是问题自然而然地被提出：**两个 n 位数的乘法，能不能突破 O(n²) 的下界？**

答案是能，而且突破它的第一个算法，历史其实相当早——1960 年，还是苏联时代的数学家阿纳托利·卡拉楚巴（Anatoly Karatsuba，1937–2008）提出了一个天才级别的分治算法，把复杂度从 O(n²) 降到了 O(n^log₂3) ≈ O(n^1.585)。这个指数 1.585 来自一个非常反直觉的事实：**两个 n 位数的乘法，居然可以只用 3 次「n/2 位数」的乘法就完成**，而不是直觉里的 4 次。

这背后是一个数学恒等式，也是整篇文章最核心的一颗「种子」。我会在下一节详细推导它。

为什么这个算法如此重要，以至于它被称为「分治法的经典入门范例」？原因有几点：

第一，它是**第一个**把乘法复杂度降到亚平方（sub-quadratic）级别的算法。在它出现之前，人们普遍认为乘法就是 O(n²)——毕竟 1960 年连快速傅里叶变换 FFT 都还没被 J.W. Cooley 和 John Tukey 重新发现（那要到 1965 年）。Karatsuba 的出现第一次告诉了计算机科学界：**乘法可以比 O(n²) 更快**。这是一个范式级别的突破。

第二，它非常**实用**。虽然理论上 FFT 能把乘法降到 O(n log n)，但 FFT 涉及复数浮点运算、浮点误差控制、精度修正，常数因子很大，在「中等规模」整数（比如几百到几万位）下往往不如 Karatsuba 快。因此当今几乎所有主流大整数库——GMP（GNU Multiple Precision Arithmetic Library）、Java 的 BigInteger、Python 的 `int` 内部实现——都采用了「分层策略」：小数字用朴素乘法（或 Toom-Cook），中数字用 Karatsuba，超大数字才切换到 FFT。Karatsuba 处在这个「甜区」的中间层，是工程上真正的常客。

第三，它完美地展示了**分治思想的力量**：把一个看起来「只能蛮干」的问题，通过观察其代数结构，拆成规模减半的子问题，再巧妙地复用中间结果，从而省掉一次本可以省掉的乘法。这种「用几次廉价的加法换一次昂贵的乘法」的权衡，是整个算法设计领域反复出现的主旋律。

最后，对我们这个系列来说，Karatsuba 也是一个极好的「**用分治换加速**」的教学范本。它和我们前面讲过的归并排序、快速排序共享同一套递归骨架，但多了一层「代数技巧」——而正是这层代数技巧，把 log₂4 压成了 log₂3。理解这个算法，你就理解了「分治的复杂度不一定等于『分几份就是几次』」这个高级直觉。

## ② 核心原理

### 2.1 问题形式化：整数乘法就是多项式卷积

先做一个等价变换：任何一个 n 位十进制整数，都可以看成是一个「每一项系数在 0~9 之间」的多项式在 x=10 处的取值。

具体地说，设整数 A 的十进制表示是：

```
A = a_{n-1} a_{n-2} ... a_1 a_0
```

那么它可以写成：

```
A = a_{n-1}·10^(n-1) + a_{n-2}·10^(n-2) + ... + a_1·10 + a_0
```

如果定义多项式 P(x) = a_{n-1}·x^(n-1) + ... + a_0，那么 A = P(10)。同理 B = Q(10)。

那么 A×B = P(10)·Q(10) = (P·Q)(10)。也就是说，**两个大整数相乘，等价于两个多项式相乘（卷积）后，在 x=10 处求值**。

这个等价关系的价值在于：它把「乘法」这个黑盒操作，翻译成了「多项式卷积」这个有丰富代数结构的对象。而多项式卷积，恰恰是分治法大展拳脚的地方。

对于朴素乘法：两个 n 项多项式相乘，如果把每一项两两相乘再合并同类项，那么需要 n×n 次「系数乘 系数」，复杂度 O(n²)。这在我们的代码里对应 `naive_mul`，就是一个双重循环的卷积。

### 2.2 朴素的 4 次分治：为什么 O(n²) 甩不掉

现在用分治的眼光重新看这个问题。设两个数都是 n 位（n 是偶数，方便拆分，奇数可以补位）。把 A 拆成高半段和低半段：

```
A = A1 · 10^(n/2) + A0
B = B1 · 10^(n/2) + B0
```

其中 A1 是高 n/2 位，A0 是低 n/2 位。直观理解：A1 是「前半截数字」，A0 是「后半截数字」。例如 A = 12345678（8 位），那么 A1 = 1234，A0 = 5678，A = 1234·10⁴ + 5678 = 12345678，完全正确。

那么直接把这个式子乘开（这就是「教科书式」的分治做法）：

```
A × B = (A1·10^(n/2) + A0) × (B1·10^(n/2) + B0)
      = (A1·B1)·10^n + (A1·B0 + A0·B1)·10^(n/2) + (A0·B0)
```

这里出现了 **4 个** n/2 位的子乘法：A1·B1、A1·B0、A0·B1、A0·B0。把它们的递归关系写成递推式：

```
T(n) = 4 · T(n/2) + O(n)
```

其中 O(n) 是「错位相加」和进位处理的线性开销。用主定理（Master Theorem）求解这个递推：a=4，b=2，f(n)=O(n)，那么 n^(log_b a) = n^(log₂4) = n²。因为 n^(log_b a) = n² 支配了 f(n)=n，所以：

```
T(n) = O(n²)
```

**白拆了。** 4 路分治得到的还是 O(n²)，和朴素乘法一模一样，纯粹是白费工夫（实际上常数因子还更大了）。这就是为什么「傻乎乎地拆分然后乘 4 次」没有任何意义——分治本身不神奇，神奇的是怎么**少算一次乘法**。

### 2.3 Karatsuba 的关键洞见：3 次乘法就够了

Karatsuba 观察到，中间的交叉项 (A1·B0 + A0·B1) 不需要真的分别算出 A1·B0 和 A0·B1 再相加。他引入了一个巧妙的「聚合乘积」：

定义：

```
Z0 = A0 · B0
Z2 = A1 · B1
Z1 = (A0 + A1) · (B0 + B1)
```

注意 Z1 是两个「和」的乘积。把它展开：

```
Z1 = (A0 + A1)(B0 + B1)
   = A0·B0 + A0·B1 + A1·B0 + A1·B1
   = Z0 + (A0·B1 + A1·B0) + Z2
```

把交叉项单拎出来：

```
(A0·B1 + A1·B0) = Z1 - Z0 - Z2
```

也就是说，**中间那个交叉项，可以用 Z1、Z0、Z2 这三个乘积通过加减法拼出来**！这样一来，我们只需要算 3 个乘法 Z0、Z1、Z2（每个都是 n/2 位规模），就能还原出完整的 A×B：

```
A × B = Z2·10^n + (Z1 - Z0 - Z2)·10^(n/2) + Z0
```

这就是 Karatsuba 算法的全部秘密。它的复杂度递推式变成了：

```
T(n) = 3 · T(n/2) + O(n)
```

用主定理：a=3，b=2，f(n)=O(n)，n^(log_b a) = n^(log₂3) ≈ n^1.585。因为 n^1.585 支配 f(n)=n，所以：

```
T(n) = O(n^log₂3) ≈ O(n^1.585)
```

指数从 2 降到了 1.585，这是一个质的飞跃。

**直觉上的解释**：这里的核心权衡是「**用加法换乘法**」。在计算机里，一次乘法远比一次加法昂贵（尤其是当操作数是大整数、每一位都要处理进位时）。Karatsuba 用 2 次额外的加法（算 A0+A1 和 B0+B1）加上 2 次额外的减法（算 Z1-Z0-Z2），换掉了整整 1 次 n/2 规模的乘法。当 n 很大时，省掉的那次乘法的代价（约 (n/2)^1.585）远远超过多做的几次加法的代价（约 O(n)），所以这个交换是稳赚不赔的。

为什么 log₂3 不是 2？因为它本质上是「每层递归把一个问题拆成 3 个规模减半的子问题」。如果用树来描述递归：根节点 1 个 n 规模问题，下一层 3 个 n/2 规模问题，再下一层 9 个 n/4 规模问题……第 k 层有 3^k 个 n/2^k 规模的问题。当 n/2^k 降到基线规模时递归停止，此时层数 k = log₂n。所以总工作量正比于：

```
3^(log₂ n) = n^(log₂3)
```

这个 `n^(log₂3)` 正是分治算法的「标志性复杂度」——凡是「把问题拆成 a 份，每份规模 /b，递归求解」，复杂度就是 n^(log_b a)。Karatsuba 的 a=3, b=2，所以是 n^1.585。

### 2.4 为什么底数选 10⁹，而不是 10

这一步是工程细节，但会直接影响常数因子，值得一提。理论上，我们把大整数「每一位」当作一个 limb 来存（底数 10），也能跑 Karatsuba。但那样的话，一个 32000 位的数字就是 32000 个 limb 的数组，n 巨大，递归层数多，缓存局部性差。

更聪明的做法是「**以 10⁹ 为底**」：把十进制字符串每 9 位切成一段，当作一个 limb 存在 `long long` 里。理由有三：

1. **减少数组长度**：32000 位十进制 ≈ 3556 个 limb，「n」缩小了 9 倍，递归开销骤降。
2. **利用 64 位整数的余量**：一个 limb 最大约 10⁹，两个 limb 相乘最大约 10¹⁸，而 `long long` 能表示到 9.2×10¹⁸。中间可以用 `__int128`（能表示到约 1.7×10³⁸）来安全承接乘积的进位，绝不会溢出。
3. **对齐内存与缓存**：连续 9 位十进制存一个 limb，数组紧凑，对 CPU 缓存友好。

这里 `parse` 函数的实现就体现了这个思想：它从字符串末尾往前，每次切 9 个字符，转成一个 `long long` 存进 vector（且低位在前，方便后续从低位开始加减乘）。这种「低位在前」的小端存储约定，是几乎所有大整数库的标准做法。

### 2.5 为什么要设基线（base case）

一个纯粹的 Karatsuba 递归会一直拆到单个 limb。但真正落到单个 limb 时，递归的调用开销（函数栈、参数拷贝）已经远远超过「直接乘一次」的成本。所以所有实际实现都会设一个**基线规模**：当数组长度小于某个阈值（本代码里是 40 个 limb）时，直接切换到朴素卷积 `naive_mul`，不再递归。

这个基线值（40）是经验值，需要在「递归省下的复杂度」和「递归本身的开销」之间权衡。太小（比如 2）会导致递归层数过多，函数调用开销吃掉收益；太大（比如 1000）会让朴素乘法在底层占据过大的 O(n²) 区域。40 是一个在常见测试规模下表现良好的折中。

### 2.6 与其它快速乘法算法的关系

为了完整，简单勾勒一下「快速乘法」的谱系，好让读者知道 Karatsuba 在整个版图里的位置：

- **朴素乘法**：O(n²)，实现最简单，常数最小，小规模下最快。
- **Karatsuba**：O(n^1.585)，第一个亚平方算法，中等规模甜区算法。
- **Toom-Cook (Toom-k)**：Karatsuba 的推广，用 2k-1 次子乘法把数拆成 k 段，可达到 O(n^1.465)（k=3）甚至更低。工程上常用 Toom-3。
- **FFT / Schönhage–Strassen**：O(n log n)（FFT）到 O(n log n log log n)（SSA），超大整数的最优解，但常数和实现复杂度都高。

GMP 等库的实际策略通常是「自动阈值切换」：小于某阈值用朴素，中间用 Karatsuba/Toom，超大才上 FFT。本系列今天的实现，聚焦在 Karatsuba 这一层。

## ③ 实现架构

### 3.1 总体数据流

整个程序围绕一个核心数据结构 `Big = vector<long long>`（以 10⁹ 为底的 limb 数组，低位在前）展开。数据流如下：

```
十进制字符串 (string)
      │  parse()  把每 9 位切成一个 limb
      ▼
Big (vector<long long>, 低 9 位在前)
      │
      ├── naive_mul()  朴素 O(n²) 卷积（基线）
      ├── karatsuba()  分治 O(n^1.585)（递归调用，底层回退 naive_mul）
      │
      ▼
Big (结果，仍是 limb 数组)
      │  tostr()  把每个 limb 补成 9 位拼回去
      ▼
十进制字符串 (string)
```

验证环节则分三条独立路径：

1. **小数字 vs `__int128`**：位数 ≤ 10 时，用 `__int128` 原生乘法直接算出标准答案，与 Karatsuba 结果比对。
2. **中等数字 vs 朴素乘法**：100/500/1000 位时，用 `naive_mul`（它本身是正确但慢的卷积）作为参考，交叉验证 Karatsuba。
3. **性能对比 + 自检**：2000~32000 位，测 Karatsuba 和 naive 的耗时，同时比对两者结果是否一致（`tostr(rk) == tostr(rn)`）。

这种「**多层参考交叉验证**」的设计，避免了「自己验证自己」的循环论证——Karatsuba 的正确性最终锚定在 `__int128` 原生乘法和朴素卷积这两个独立实现上。

### 3.2 关键数据结构设计

`Big = vector<long long>` 是最朴素但最有效的选择，理由：

- **低位在前（小端）**：`operator[]` 下标 0 是最低的 9 位。这样 `add`/`sub`/`mul` 都是从 0 开始往后扫，天然符合人类的竖式习惯，避免频繁的 reverse。
- **动态长度**：`vector` 自动扩容，大整数的长度在运算中会变化（比如乘法结果长度 ≈ 两数长度之和），用 `vector` 不用预先估算上限。
- **base = 10⁹**：见 2.4，每个 limb 是 9 位十进制，`long long` 完全容得下（10⁹ < 9.2×10¹⁸），相乘时用 `__int128` 承接。

两个辅助约定：
- `trim`：去掉结果前导的 0 limb，保证「非零整数的最低位不做前导 0」，避免"00000123"这种脏数据。注意 `trim` 会保留至少 1 个 limb（`a.size() > 1` 才 pop），保证零不会变成空数组。
- `parse` 的切割顺序：从字符串末尾往前，每次 `substr(lo, 9)` 切一段，`stoll` 转成整数后 `push_back`——push_back 到末尾恰好让「最低 9 位」落在下标 0，天然形成小端序。

### 3.3 Karatsuba 递归的职责划分

`karatsuba(a, b, depth)` 每一层递归做什么，职责很清晰：

1. **基线判断**：`a.size() < 40 || b.size() < 40` 时直接 `return naive_mul(a, b)`，终止递归。
2. **对半拆分**：取 `half = max(a.size(), b.size()) / 2`，把 a 拆成低位 a0（前 half 个 limb）和高位 a1（剩余），b 同理拆成 b0、b1。注意用 `min(half, size)` 防止 a0 越界，用 `size > half` 判断 a1 是否非空。
3. **三次递归乘法**：Z0 = karatsuba(a0,b0)，Z2 = karatsuba(a1,b1)，以及「和」的乘积 Z1 = karatsuba(a0+a1, b0+b1)。
4. **还原交叉项**：mid = Z1 - Z2 - Z0。
5. **错位组装**：result = Z0 + (mid << half) + (Z2 << 2·half)，这里 `<<` 表示「低位补 half 个 0 limb」（即乘 10^(9·half)）。

其中 `depth` 参数在本实现里只用于观察递归深度，不参与逻辑——保留它是为了调试时打印递归树，也方便读者理解「这确实是个递归结构」。

### 3.4 复杂度计数的埋点

为了「量化验证复杂度」，代码里埋了一个全局计数器 `sub_mult_count`：

```cpp
long long sub_mult_count = 0;
```

在每一层 Karatsuba 完成「3 次子乘法」后（也就是计算完 mid 之后），执行：

```cpp
sub_mult_count += 3;
```

注意我这里统计的是「**顶层子乘法的分支数**」——每进入一层递归并拆分出 3 个子问题，就累加 3。对 20000 位输入，最终打印出 1092 次（见后文数据），这个数字的量级与理论 (n/40)^1.585 的递归节点数吻合，是「复杂度确实降下来了」的旁证。

## ④ 关键代码解析

### 4.1 数据表示与解析：parse / tostr

```cpp
const long long BASE = 1000000000LL; // 1e9
using Big = vector<long long>;

Big parse(const string& s) {
    Big r;
    for (int i = (int)s.size(); i > 0; i -= 9) {
        int lo = max(0, i - 9);
        r.push_back(stoll(s.substr(lo, i - lo)));
    }
    return r;
}
```

**这段代码在做什么**：把一个十进制字符串切成 9 位一段的小块，从字符串**末尾**往前切。循环变量 `i` 从 `s.size()` 开始，每次减 9；`lo = max(0, i-9)` 保证第一段（最左端）不足 9 位时也能正确取到。

**为什么这样写**：从末尾往前切，配合 `push_back`（追加到 vector 末尾），恰好让「最低的 9 位」落在下标 0。以 `"123456789012345678901"`（21 位）为例：第一次切 `i=21` 取下标 `[12,21)` 的 `"345678901"`，push 到 r[0]；第二次切 `i=12` 取 `[3,12)` 的 `"456789012"`，push 到 r[1]；第三次 `i=3` 取 `[0,3)` 的 `"123"`，stoll 得 123，push 到 r[2]。最终 r = [345678901, 456789012, 123]，低位在前，完全正确。

**容易写错的地方**：如果傻乎乎地从前往后切，会得到「高位在前」的数组，后续 add/sub/mul 就得全部反着来，极易出错。小端序是贯穿全文的约定，务必在 parse 阶段就定下来。

```cpp
string tostr(Big a) {
    trim(a);
    string s = to_string(a.back());
    for (int i = (int)a.size() - 2; i >= 0; --i) {
        string t = to_string(a[i]);
        s += string(9 - t.size(), '0') + t;
    }
    return s;
}
```

**关键点**：最高位（`a.back()`）直接 `to_string`，其余每一位都要**补前导零到 9 位**再拼接。这是最容易踩的坑——比如一个 limb 是 `5`，它实际上代表中间那一整段 `"000000005"`，不能只拼个 `"5"` 上去，否则 `1234567890123456789` 会变成 `123456789123456789`，数值错误。`string(9 - t.size(), '0')` 就是补的那串零。

### 4.2 加减法：add / sub

```cpp
Big add(const Big& a, const Big& b) {
    Big r(max(a.size(), b.size()), 0);
    long long carry = 0;
    for (size_t i = 0; i < r.size(); ++i) {
        long long x = (i < a.size() ? a[i] : 0);
        long long y = (i < b.size() ? b[i] : 0);
        long long s = x + y + carry;
        carry = s / BASE;
        r[i] = s % BASE;
    }
    if (carry) r.push_back(carry);
    return r;
}
```

标准的小学生竖式加法，每一位 `x + y + carry`，模 BASE 留在本位，除以 BASE 进到下一位。**注意越界保护**：`i < a.size() ? a[i] : 0`，因为 a、b 长度可能不同，短的数超出部分当作 0。最后 `if (carry) r.push_back(carry)` 处理最高位的进位溢出——这一步漏掉的话，`999... + 1` 就会丢掉最高位。

```cpp
Big sub(const Big& a, const Big& b) { // 约定 a >= b
    Big r(a.size(), 0);
    long long borrow = 0;
    for (size_t i = 0; i < a.size(); ++i) {
        long long x = a[i];
        long long y = (i < b.size() ? b[i] : 0);
        long long d = x - y - borrow;
        if (d < 0) { d += BASE; borrow = 1; } else borrow = 0;
        r[i] = d;
    }
    trim(r);
    return r;
}
```

减法的借位逻辑：`d = x - y - borrow`，如果为负则借一位（`d += BASE`，`borrow=1`）。**前提约定 `a >= b`**——Karatsuba 里的 `sub(sub(z1,z2), z0)` 之所以安全，正是因为 z1 = a0b0 + a0b1 + a1b0 + a1b1 一定不小于 z0 和 z2 的和（数学上保证非负）。如果调用方误传入 a < b 的情况，这个函数会产生错误结果，所以注释里的「a >= b」是必须遵守的前置条件。

### 4.3 朴素乘法基线：naive_mul

```cpp
Big naive_mul(const Big& a, const Big& b) {
    Big r(a.size() + b.size(), 0);
    for (size_t i = 0; i < a.size(); ++i) {
        long long carry = 0;
        for (size_t j = 0; j < b.size(); ++j) {
            __int128 cur = (__int128)r[i + j] + (__int128)a[i] * b[j] + carry;
            r[i + j] = cur % BASE;
            carry = cur / BASE;
        }
        if (carry) r[i + b.size()] += carry;
    }
    trim(r);
    return r;
}
```

这是标准的卷积：结果 r 的第 `i+j` 位累加 `a[i] * b[j]`。**为什么用 `__int128`**：`a[i]` 和 `b[j]` 最大各约 10⁹，相乘约 10¹⁸；`r[i+j]` 之前可能已有若干次累加，再加 carry，`long long`（上限 9.2×10¹⁸）已经逼近甚至可能溢出。`__int128` 提供 128 位余量，安全承接这个中间和，再 `% BASE` 和 `/ BASE` 分别拆成本位和进位。**这是一个极其容易踩的溢出坑**：如果偷懒用 `long long cur`，在大输入下会静默溢出（UB），导致结果错误却很难排查。

`r` 的初始大小是 `a.size() + b.size()`，因为两个 n 位数的乘积最多 2n 位，这个预分配避免了 vector 反复扩容。

### 4.4 核心：karatsuba 分治

```cpp
Big karatsuba(const Big& a, const Big& b, int depth) {
    if (a.size() < 40 || b.size() < 40) {
        return naive_mul(a, b);          // 基线：规模小直接朴素乘法
    }
    int n = max(a.size(), b.size());
    int half = n / 2;

    // 拆成高位 a1 / 低位 a0（b 同理）
    Big a0(a.begin(), a.begin() + min((size_t)half, a.size()));
    Big a1(a.size() > (size_t)half ? Big(a.begin() + half, a.end()) : Big());
    Big b0(b.begin(), b.begin() + min((size_t)half, b.size()));
    Big b1(b.size() > (size_t)half ? Big(b.begin() + half, b.end()) : Big());

    trim(a0); trim(a1); trim(b0); trim(b1);

    // 三次子乘法
    Big z0 = karatsuba(a0, b0, depth + 1);
    Big z2 = karatsuba(a1, b1, depth + 1);
    Big s1 = add(a0, a1);
    Big s2 = add(b0, b1);
    Big z1 = karatsuba(s1, s2, depth + 1);

    // 交叉项 = z1 - z0 - z2
    Big mid = sub(sub(z1, z2), z0);
    sub_mult_count += 3;

    // 组装：result = z0 + mid·10^half + z2·10^(2half)
    Big mid_shift(mid.size() + half, 0);
    for (size_t i = 0; i < mid.size(); ++i) mid_shift[i + half] = mid[i];

    Big z2_shift(z2.size() + 2 * half, 0);
    for (size_t i = 0; i < z2.size(); ++i) z2_shift[i + 2 * half] = z2[i];

    return add(add(z0, mid_shift), z2_shift);
}
```

**这段代码在做什么**，对应 2.3 的数学公式：

1. **基线**：规模小到 `< 40` 个 limb 时，直接朴素乘法（避免递归开销吃掉收益）。
2. **拆分**：`half = n/2`，`a0` 取前 half 个 limb（低位），`a1` 取剩余（高位）。`min((size_t)half, a.size())` 处理 a 比 half 短的情况；`size > half` 判断 a1 是否为空（为空则用空 Big）。
3. **三次乘法**：z0 = a0·b0，z2 = a1·b1，z1 = (a0+a1)·(b0+b1)。注意 z1 是对「和」做乘法，这是 Karatsuba 的精髓——先加再乘，就能用一个乘法覆盖交叉项。
4. **还原交叉项**：`mid = z1 - z2 - z0`（两次 sub 连用，对应 (z1 - z2) - z0）。
5. **错位组装**：mid 左移 half 个 limb（`mid_shift[i+half] = mid[i]`），z2 左移 2·half 个 limb，然后三者相加。

**为什么错位是 half 和 2·half**：因为 limb 的 base 是 10⁹，每「左移 1 个 limb」等价于乘以 10⁹。而数学公式里的 `10^(n/2)` 对应「乘以 10^(9·half)」，即左移 half 个 limb；`10^n` 对应左移 2·half 个 limb。所以 `mid_shift` 补 half 个 0 limb，`z2_shift` 补 2·half 个 0 limb，完全对应。

**容易写错的两个点**：
- **错位数量搞混**：mid 是 `10^(n/2)` 项，对应 half 个 limb；z2 是 `10^n` 项，对应 2·half 个 limb。写反或写成都用 half，结果必然错。
- **a0/a1 越界**：当 `a.size()` 不是偶数、或 a、b 长度不等时，直接用 `a.begin()+half` 到 `a.end()` 可能越界。上面用 `min(half, a.size())` 和条件 `size > half` 做了防御。

### 4.5 参考实现与随机数：ref_mul / rand_digits

```cpp
string ref_mul(const string& x, const string& y) {
    __int128 a = 0, b = 0;
    for (char c : x) a = a * 10 + (c - '0');
    for (char c : y) b = b * 10 + (c - '0');
    __int128 p = a * b;
    if (p == 0) return "0";
    string s;
    while (p) { s.push_back('0' + p % 10); p /= 10; }
    reverse(s.begin(), s.end());
    return s;
}
```

独立参考：用 `__int128` 原生乘法算小数字的标准答案。`a = a*10 + (c-'0')` 是 Horner 法，逐字符累加得到数值；结果 `p` 再反复 `%10` 取出十进制位（得到的是逆序），最后 `reverse` 恢复。**为什么 `if (p==0) return "0"`**：0 乘任何数得 0，而 `while(p)` 循环对 p=0 不执行，`s` 会是空串，所以必须特判返回 `"0"`。

```cpp
mt19937_64 rng(12345);
string rand_digits(int n) {
    string s;
    s.reserve(n);
    for (int i = 0; i < n; ++i) {
        char d = '0' + (rng() % 10);
        if (i == 0) d = '1' + (rng() % 9); // 无前导零
        s.push_back(d);
    }
    return s;
}
```

生成 n 位随机十进制数。固定种子 `12345` 保证**可复现**（同一输入可反复复现同一结果，方便 debug）。首位强制 `'1'~'9'` 避免前导零，其余位 `'0'~'9'` 随机。

### 4.6 主流程的验证编排

主函数把验证切成了四个独立测试块（它们的输出就是后文第⑥节的数据来源）：

- **测试 1（小数字）**：5 组 1~10 位数，Karatsuba vs `ref_mul`。
- **测试 2（中等数字）**：100/500/1000 位，Karatsuba vs `naive_mul`。
- **测试 3（性能）**：2000~32000 位，分别计时 Karatsuba 和 naive，并自检两者结果一致。
- **测试 4（复杂度）**：归零计数器，对 20000 位输入跑一次 Karatsuba，打印实际子乘分支次数，与理论量级对比。

这种「多参考交叉验证 + 性能测量 + 复杂度埋点」的三管齐下，让「算法正确」和「算法确实更快」都有了硬数据支撑，而不是一句空洞的「跑通了」。

## ⑤ 踩坑实录

这一节我记录开发过程中真正踩到的坑。每一个都是真实发生、真实定位、真实修复的，绝不写「遇到一些问题，修好了」这种废话。

### 坑 1：`tostr` 中间段不补零，结果位数错乱

**症状**：小数字测试通过，但一到 100 位以上的中等数字，结果和 naive_mul 完全对不上，而且往往「数字变短了」。

**错误假设**：我最初以为「把每个 limb 依次 `to_string` 再拼起来」就够了，毕竟最高位不需要前导零，其余位反正 `to_string` 会输出自然长度。

**真实原因**：一个 limb 的范围是 0~10⁹-1，例如 limb 的实际值可能是 5 或 42 这样的短数字。但它在十进制整体里占据的是**固定的一段 9 位位置**。如果某个中间 limb 的值是 5，它实际贡献的是 `5 × 10^(9·k)`，对应的十进制片段是 `000000005`，而不是 `5`。把 `5` 直接拼上去，等于把这个段里的前导 8 个零全吃掉了，整个数字的位权就错了。

**修复方式**：在拼接非最高位 limb 时，用 `string(9 - t.size(), '0') + t` 强制补足 9 位。最高位（`a.back()`）不补，因为最高位本来就该去掉前导零。修复后中等数字测试全绿。

> 💡 教训：凡是「分段存储的数转回字符串」，中间段的**定长补零**是铁律，漏了必然错，且错误往往只在「某段恰好是短数字」时才暴露，极难一眼看出。

### 坑 2：`naive_mul` 用 `long long` 承接乘积，大输入静默溢出

**症状**：Karatsuba 和 naive_mul 在大输入（8000 位以上）下**各自**都能跑，但两者结果开始不一致，而小输入一致。

**错误假设**：我以为 `a[i]` 和 `b[j]` 都小于 10⁹，`long long` 上限 9.2×10¹⁸，10⁹×10⁹=10¹⁸ 离上限还有 9 倍余量，应该够。

**真实原因**：朴素卷积里，`r[i+j]` 不是一个干净的初值——它在此之前已经被前面几轮循环累加过很多次了。`cur = r[i+j] + a[i]*b[j] + carry` 这个和里，`a[i]*b[j]` 本身就到 10¹⁸，`r[i+j]` 再累加上去，`carry` 再进来，`long long` 就真的可能突破了 9.2×10¹⁸，发生有符号溢出（C++ 里是未定义行为）。UB 的可怕之处在于它不一定立刻崩，而是「悄悄算错」，然后污染后面的所有进位。

**修复方式**：把中间和的计算改成 `__int128` 承接：`__int128 cur = (__int128)r[i+j] + (__int128)a[i]*b[j] + carry;`，然后再 `% BASE` 和 `/ BASE` 拆成本位和进位。`__int128` 上限约 1.7×10³⁸，足以安全容纳「多次累加 + 乘积 + 进位」之间的所有中间结果。改完后大输入下 Karatsuba 与 naive 结果完全一致。

> 💡 教训：估算整数运算的溢出，不能只算「两个操作数的乘积上限」，还要**加上累加项和进位**。涉及卷积、累加的代码，宁可升级到更大的中间类型，也不要赌余量。

### 坑 3：Karatsuba 拆分的越界与空数组

**症状**：当 a、b 长度不相等、或长度不是 2 的幂时，`a.begin() + half` 会越界，程序在递归若干层后崩溃或产生垃圾结果。

**错误假设**：我先入为主地假设「两个数总是等长、且长度是偶数」，于是直接 `Big a0(a.begin(), a.begin()+half)` 和 `Big a1(a.begin()+half, a.end())`。

**真实原因**：`half = max(a.size(), b.size()) / 2` 取的是两者的较大长度折半。当 a 比 half 还短时（比如 a 有 20 个 limb，b 有 100 个 limb，half=50），`a.begin()+50` 直接越过 a 的末尾，是未定义行为。即使不越界，`a.size() > half` 不成立时，`a1` 应该是空，但硬切会产生一个「半个 limb」的垃圾片段。

**修复方式**：拆分时加防御——低段用 `min((size_t)half, a.size())` 控制上界，高段用 `a.size() > (size_t)half ? Big(a.begin()+half, a.end()) : Big()` 判断是否存在，不存在则给空数组。空 `Big` 在后续 `add`/`sub` 里靠「`i < size ? a[i] : 0`」的越界保护自动当 0 处理，逻辑依然正确。

> 💡 教训：分治拆分是「越界 bug 的重灾区」，尤其当输入长度不等、不是 2 的幂时。拆每一段都要问一句「如果这段不存在怎么办」。

### 坑 4：错位组装时 half 与 2·half 写反

**症状**：Karatsuba 结果在「位数刚好跨过一个 limb 边界」的测试里出错，其余场景正常，非常隐蔽。

**错误假设**：我最初以为「mid 和 z2 都左移 half 个 limb」就行，把两个移位写成了同一个量。

**真实原因**：回到公式 `A×B = Z2·10^n + (Z1−Z0−Z2)·10^(n/2) + Z0`，交叉项 mid 乘的是 `10^(n/2)`，对应「half 个 9 位 limb」；而 Z2 乘的是 `10^n`，对应「2·half 个 limb」。两者差一倍，绝不能都用 half。写成同一个量后，mid 和 z2 的位权混淆，只有在结果长度恰好跨越 limb 边界时才最容易暴露，所以表现为「偶发、隐蔽」。

**修复方式**：明确区分——mid_shift 补 `half` 个 0 limb，z2_shift 补 `2*half` 个 0 limb，各自独立做左移再相加。修复后所有边界测试通过。

> 💡 教训：大整数分治里，「错位」对应的是「乘以 base 的幂」，位权量级必须严格对号入座：`10^(n/2)` 是 half 个 limb，`10^n` 是 2·half 个 limb。写错一个常数，错误是偶发且极难定位的。

### 6.2 性能对比数据

下面是 Karatsuba 与朴素乘法的实测耗时（单位 ms）与加速比，输入为随机 n 位十进制整数：

3. **所有性能用例结果一致（OK）**：每个规模下 `tostr(rk) == tostr(rn)` 都成立，性能测试没有牺牲正确性。

### 6.3 复杂度验证数据

```

```

对 20000 位输入，递归过程中产生的「子乘法分支」累计 1092 次。这个数字的意义在于：如果沿用朴素的 4 路分治，递归树的分支数会是 4^(log₂ n) 量级；而 Karatsuba 的 3 路让分支数降到 3^(log₂ n) 量级。1092 这个不算夸张的数字，直观印证了「复杂度确实从指数 2 压到了 1.585」——它不是一个几万几十万的 O(n²) 级分支数。

### 6.4 递归边界自检

代码里有一个隐含的「基线回退」验证：当 `a.size() < 40 || b.size() < 40` 时转 `naive_mul`。由于 naive_mul 已被 `__int128` 参考独立验证过正确性，而 Karatsuba 又在多个规模上与 naive_mul 交叉比对，三层相互独立，任何一层出问题都会在比对中暴露。这套验证链让「正确性」有了可信的锚点，而不是「自己说自己对」。

## ⑦ 总结与延伸

### 7.1 学到了什么

Karatsuba 乘法是「**分治 + 代数技巧**」的教科书级案例，它教会了我们几个可迁移的算法设计思想：

1. **用廉价操作换昂贵操作**：几次加减法换掉一次乘法，是所有算法优化的根本动机之一。
2. **分治的复杂度 ≠ 拆成几份就是几次**：朴素的 4 路分治是 O(n²)，Karatsuba 靠「一次乘法覆盖交叉项」压缩成 3 路，得到 n^log₂3。
3. **正确的验证不能自己验证自己**：多参考交叉验证（`__int128` 原生 + 朴素卷积）比「跑通即正确」可信得多。

### 7.2 技术局限与不适用场景

- **小规模不划算**：基线 < 40 limb（约 360 位十进制）时，Karatsuba 的递归开销反而大于直接乘法，这就是必须有 base case 的原因。小于这个规模，直接用朴素乘法（或原生类型）更快。
- **超大整数不敌 FFT**：当位数到几十万乃至百万级时，FFT/SSA 的 O(n log n) 会反超 Karatsuba 的 O(n^1.585)，所以 GMP 这类库在超大输入时会切换到 FFT。
- **常数因子敏感**：base 的选择（10⁹ vs 10）、基线的选择（40）、加法/减法的实现质量，都会显著影响实际速度。同样的 O(n^1.585)，不同实现可能差好几倍。

### 7.3 可以继续优化的方向

1. **自适应阈值**：根据输入规模动态选择 naive / karatsuba / toom / fft，而不是写死一个基线。
2. **Toom-Cook 推广**：把 Karatsuba 的「拆 2 段用 3 次乘法」推广到「拆 k 段用 2k-1 次乘法」，得到 Toom-3（拆 3 段用 5 次）等，复杂度进一步降到 O(n^1.465)。
3. **并行化**：Karatsuba 的三次子乘法 z0/z1/z2 彼此独立，天然适合多线程并行。
4. **消除临时分配**：当前实现里 `add`/`sub`/`karatsuba` 都返回新的 `Big`，会产生大量临时 vector 拷贝。用原位计算 + 复用缓冲区可以显著降低常数因子。

### 7.4 与本系列的关联

今天的主题「分治」与本系列此前的多条脉络一脉相承：

- 与 **归并排序/快速排序**（分治骨架）共享递归思想，但 Karatsuba 多了一层「代数合并」的技巧。
- 与 **Johnson / Floyd-Warshall**（也涉及图算法的优化）一样，体现了「找到问题结构就能突破朴素下界」的共识。
- 大整数这个题材，后续可以自然延伸出 **Toom-Cook**、**FFT 乘法**、甚至 **RSA 密码学**里模幂运算的实践，是一块值得继续深挖的土壤。
