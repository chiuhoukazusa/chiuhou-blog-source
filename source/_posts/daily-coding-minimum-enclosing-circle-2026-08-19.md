## 一、背景与动机

给定二维平面上的一组点，找出一个**能覆盖所有点、且半径最小**的圆。这就是经典的**最小包围圆（Minimum Enclosing Circle，简称 MEC）**问题。表面上看它很简单——"画个圈把这些点都框住不就行了"——但它背后隐藏着一个在计算几何、游戏开发和机器人领域反复出现的核心问题：**如何在保证"最小"的同时，让算法足够快**。

### 1.1 问题为什么重要

最小包围圆不是一个纯粹的理论玩具，它在工业界有大量真实落地场景。列举几个典型的：

1. **游戏引擎的包围体计算**：在碰撞检测的第一步（broad phase），引擎需要为大量顶点（如一个可破坏的几何体、一组散落的碎片）计算一个紧凑的包围体。包围球（sphere）是最常用的一类包围体，而"紧密包围一组点的球"本质上就是三维最小包围球问题——是我们今天二维问题的直接推广。包围体越紧，"误报"的碰撞对越少，后续精确检测的负担越轻。

2. **移动机器人与物流**：一个仓库里有若干需要取货的点，机器人（或基站）应该部署在哪里，才能用最小的覆盖半径服务所有这些点？这就是"最小覆盖圆"的设施选址问题。物流中心选址、消防站布点、5G 基站的覆盖半径优化，本质都是同一类几何覆盖问题。

3. **地图与可视化**：地图应用要自动缩放视图，使得一组 POI（兴趣点）都能显示在屏幕上且尽量放大。这个"能把所有 POI 框住的最紧视野"就是最小包围圆的半径与圆心。

4. **计算机视觉与目标检测**：在一张图像中检测到若干关键点后，若要为某个目标（比如人脸、手部）画一个紧凑的轮廓框，最小包围圆提供了一种旋转无关的紧凑描述。

### 1.2 朴素解法的困境

如果只是"随便一个能框住的圆"，那太简单了——取所有点的平均值为圆心，取最远点到圆心的距离为半径即可。但这样得到的圆往往远大于最优解。

如果要求"最小"的圆，最容易想到的暴力做法是**枚举**。关键观察到的是：最小包围圆的边界上，一定至少有两个点（否则圆可以缩小半径，或向远离某点的方向平移）。更精确地说，最小包围圆必然由边界上的 2 个点（构成直径）或 3 个点（构成外接圆）确定。

于是暴力枚举的思路是：

1. 枚举所有**点对** `(i, j)`，构造以 `ij` 为直径的圆，检查它是否覆盖所有 n 个点。若覆盖，则是一个候选解。
2. 枚举所有**三元组** `(i, j, k)`，构造经过这三点的外接圆（圆的边界上有这三个点），同样检查是否覆盖所有点。

枚举点对是 `O(n²)` 个候选，枚举三元组是 `O(n³)` 个候选，而每个候选圆都要花 `O(n)` 时间检查"是否覆盖全部点"。所以点对部分是 `O(n³)`，三元组部分是 `O(n⁴)`。整体复杂度 `O(n⁴)`。

对于 n = 60 个点，`n⁴ = 12,960,000`，常数稍大一点就要跑几十毫秒；对于 n = 1000 个点，`n⁴ = 10¹²`，完全不可行。这就是朴素解法的痛点：**正确，但慢得无法用于实时场景**。

### 1.3 我们要解决的问题

所以今天的目标很明确：

1. 实现一个**期望线性时间 O(n)** 的最小包围圆算法（Welzl 随机增量算法）。
2. 用**量化的方式**证明它正确——不能只看图"看起来对"，而是要和暴力 O(n⁴) 的精确解在数百次随机试验中逐一对比半径，误差必须为零。
3. 测量它相对暴力解法的实际加速比，验证线性复杂度在真实运行中的体现。

这三点分别对应了正确性、精度、性能三个维度，缺一不可。

## 二、核心原理

Welzl 算法是 Emo Welzl 在 1991 年提出的一个用于求解最小包围球（任意维度）的随机增量算法。它之所以优雅，是因为它把一个看似"全局枚举"的问题，转化成了"增量插入 + 递归修复"的过程，并且通过**随机化**把最坏情况的时间复杂度从指数级降到了期望线性。

### 2.1 一个决定性的几何事实

整个算法的正确性建立在一个简单但强大的事实上：

> **最小包围圆的边界由至多 3 个点确定。**

具体来说，如果把一个点集 P 的最小包围圆记作 MEC(P)，那么存在一个大小至多为 3 的子集 R ⊆ P，使得 `MEC(P) = MEC(R)`，且 R 中的每个点都恰好落在圆的边界上（即都"贴着"圆周）。

这个事实的直觉是：一个圆由 3 个自由参数（圆心 x、圆心 y、半径 r）确定。要让"半径最小"且"覆盖所有点"，这个最优圆必然被某些点"顶住"——就像你把一个气球吹到刚好包住一堆钉子，气球表面最多被 3 根钉子顶住（三维空间里是 4 个）。如果边界上只有 0 个或 1 个点，那这个圆显然还可以缩小；如果边界上超过 3 个点，由于 3 点已经唯一确定一个圆，超过 3 个点"同时"落在圆周上是一种巧合（或者说，其中至少有 3 个点已经足以确定这个圆）。

- **1 个边界点** → 圆心就是这个点，半径 0（仅当点集只有一个点时成立）。
- **2 个边界点** → 这两个点构成圆的**直径**（圆心在中点）。
- **3 个边界点** → 这三点构成圆的**外接圆**（圆心是三角形外心）。

这给了我们一个递归求解的抓手：问题的解要么由 2 点确定，要么由 3 点确定，要么是平凡情况。

### 2.2 增量的直觉

Welzl 算法的核心是一个增量过程。假设我们已经求出了前 `k` 个点的最小包围圆 `C`，现在来了第 `k+1` 个点 `p`，分两种情况：

1. **如果 `p` 已经在 `C` 内部**：那么前 `k+1` 个点的最小包围圆仍然是 `C`，什么都不用做。这是最常见的情况——大多数点都被当前圆覆盖，直接跳过。

2. **如果 `p` 在 `C` 外部**：这说明当前圆不行了，新的最小包围圆**必须让 `p` 落在边界上**（这是可以证明的：如果最小包围圆不让 `p` 在边界上，那它就能进一步缩小，或者 `p` 本来就应该在圆内——矛盾）。于是我们递归地求解一个**受约束的子问题**："最小包围圆，且 `p` 必须在边界上"。

这个"必须让某个点在边界上"的约束，就是整个算法递归的核心。我们把"必须在边界上"的点集合记作 `R`（boundary set），其大小永远不会超过 3。

### 2.3 递归的定义与终止条件

设函数 `welzl(P, R)` 求解以下问题：

> 求一个最小圆，使得它覆盖 P 中的所有点，并且 R 中的每个点都在边界上。

其中 `R` 是"边界点集合"，`|R| ≤ 3`。递归的终止条件是：

- 若 `P` 为空，或 `|R| == 3`：此时解由 R 唯一确定：
  - `R` 空 → 半径 0 的退化圆。
  - `|R| == 1` → 圆心为该点，半径 0。
  - `|R| == 2` → 以这两点为直径的圆。
  - `|R| == 3` → 过这三点的外接圆。

`|R| == 3` 时为什么可以停止？因为 3 个边界点已经唯一确定了圆（除非三点共线，此时退化为直径圆），再多一个点也不会改变结果——如果某个点在这 3 点确定的圆外，那说明"这 3 点都在边界"这个约束本身无解，但这种情形在前面已经被排除了（我们只在"当前圆不覆盖某点"时才把它加入 R）。

### 2.4 递归展开的步骤

`welzl(P, R)` 的实现（随机增量版本）：

1. 从 P 中随机选一个点 `p`（这一步是随机化的关键）。
2. 先递归求解 `welzl(P \ {p}, R)`，得到圆 `C`（先忽略 `p`）。
3. 判断 `p` 是否在 `C` 内：
   - 在 → 返回 `C`。
   - 不在 → 把 `p` 加入 R，递归求解 `welzl(P \ {p}, R ∪ {p})`，返回结果。

这里的妙处在于：每次"某点在外"触发的那次更深层递归，都会把 R 的大小加 1。而 R 最多到 3，所以**递归深度受限于 3**，不会无限加深。

### 2.5 为什么复杂度是期望线性 O(n)

这是最反直觉的部分。如果运气不好，每次新加入的点都落在当前圆外、每次都触发递归，那不是可能退化到很慢吗？

答案是：**随机化打乱了输入顺序，使得"新点落在圆外"这件事发生的期望次数很少**。

可以证明（Welzl 1991 的经典结论）：在随机打乱后，第 `k` 个点触发"落在当前圆外"（从而需要更新圆、并把该点加入边界集）的概率是 `O(1/k)`。直觉是：在一个已包含 `k` 个点的最小包围圆里，边界上只有至多 3 个点；当随机挑选一个点作为"下一个插入"时，它恰好是那少数几个"关键顶点"之一的概率非常小。

于是期望的总工作量是：

```
Σ_{k=1}^{n} O(1/k) 次"边界更新" × O(每次更新的代价)
```

而每次边界更新触发的递归深度 ≤ 3，代价是常数级（只需检查至多 3 个边界点的圆）。所以整体期望 `O(n)`。

对比一下：暴力是 `O(n⁴)`（三元组枚举 + 覆盖检查），Welzl 是期望 `O(n)`——从四次方降到线性，这是巨大的跨越。即使不考虑随机化、只保留"增量 + 递归"的结构，最坏情况也不过 `O(n³)` 左右（因为递归深度 ≤ 3，每层 O(n)），依然远好于暴力。

### 2.6 随机化的作用与一个常见误区

一个容易踩的误区是：**误以为"必须用真正的随机数"**。实际上，Welzl 算法的正确性**不依赖**随机数——无论以什么顺序插入点，算法最终都会返回正确的最小包围圆。随机化的作用**仅仅是性能**：它把最坏情况（对手精心构造的输入顺序）的复杂度摊薄到期望线性。

因此，在工程实现中，为了保证"可复现"（比如验证脚本要能稳定复现结果），我们常常用一个**固定种子**的随机数发生器（deterministic，比如 `mt19937 rng(12345)`）。这样既保留了随机化的期望复杂度（对于任何固定种子的伪随机排列，输入点被"打乱"的效果依然存在），又保证了每次运行结果一致，方便断言和回归测试。

这也是我在代码里写 `mt19937 rng(seed)` 而不是裸 `rand()` 的原因——`rand()` 的实现质量在不同平台可能不同，而 `std::mt19937` 是标准库保证的实现，跨平台行为一致。

### 2.7 两点圆与三点圆的几何推导

这是代码里最需要小心计算的部分。我们推导一下这两个子过程。

**两点圆（直径圆）**：给定两点 `a(x1,y1)` 和 `b(x2,y2)`，以 `ab` 为直径的圆的圆心是中点，半径是距离的一半：

```
center = ((x1+x2)/2, (y1+y2)/2)
radius = dist(a, b) / 2
```

这个没有歧义，直接套公式即可。

**三点外接圆**：给定三个不共线的点 `a, b, c`，求过这三点的圆。核心思路是：**圆心是三角形任意两边的垂直平分线的交点**（因为圆心到三点距离相等，所以它必须同时落在 `ab` 的中垂线和 `ac` 的中垂线上）。

设圆心为 `(cx, cy)`，由"到 a 和 b 距离相等"，有：

```
(cx - a.x)² + (cy - a.y)² = (cx - b.x)² + (cy - b.y)²
```

展开并整理（平方项 `cx², cy²` 抵消）：

```
2(b.x - a.x)·cx + 2(b.y - a.y)·cy = (b.x² + b.y²) - (a.x² + a.y²)
```

这是关于 `cx, cy` 的一个线性方程。同理，对 `a` 和 `c` 再列一个方程。两个线性方程联立，解 2×2 线性方程组即可得到圆心 `(cx, cy)`。

用代码里定义的中间变量把这个方程组写清楚。令：

```
A = b.x - a.x    B = b.y - a.y
C = c.x - a.x    D = c.y - a.y
E = A·(a.x+b.x) + B·(a.y+b.y)
F = C·(a.x+c.x) + D·(a.y+c.y)
G = 2·(A·(c.y-b.y) - B·(c.x-b.x))
```

那么解为：

```
cx = (D·E - B·F) / G
cy = (A·F - C·E) / G
```

这里的 `G` 本质上是这两条中垂线方向向量的叉积的 2 倍，也就是 2×2 系数矩阵的行列式。当三点共线时，`G = 0`（矩阵奇异），此时没有唯一的外接圆——几何上，共线的三点无法确定一个普通三角形，圆心在无穷远处。

**三点共线的退化处理**：代码里检测到 `|G| < EPS` 时，退化为"取三个直径圆里最大的那个"。这是合理的——如果三点共线，最小包围圆必然是"以相距最远的两点为直径"的圆（因为三点共线时，覆盖它们的最优圆就是以最远两点的中点为圆心、半长为半径的圆）。

### 2.8 为什么要用 EPS 容差而不是严格比较

浮点数无法精确表示大多数量（比如 1/3、√2），所以在判断"点是否在圆内"时，我们用：

```
dist²(C.c, p) <= C.r² + EPS
```

而不是严格的 `<=`。这里的 `EPS` 取 `1e-9`（距离平方量级）。如果不用容差，那么一个本应"恰好在圆上"的点，可能因为浮点舍入误差被判定为"在圆外"，从而触发一次本不需要的递归，甚至在某些边界情况下导致结果略微偏离。

但这里有个微妙之处：`EPS` 是加在**距离的平方**上，而不是距离上。因为我们的距离比较都是平方比较（避免频繁开根号，既快又能减少精度损失），容差也应该在同一量纲上。`1e-9` 的平方量级容差，换算到距离上大约是 `√(1e-9) ≈ 3e-5`，对于坐标范围在 [-100, 100]、半径在 100 量级的场景，这个容差足够小，不会掩盖真实的"点在外"情况，又足够大，能吸收浮点噪声。

## 三、实现架构

在动手写代码前，先想清楚整体结构。虽然这个项目的核心算法只有几十行，但"验证"部分的工作量和重要性不亚于算法本身。我把代码分成三个清晰的层次：

### 3.1 三层架构

1. **几何原语层（Geometry Primitives）**：`Point`、`Circle` 结构体，以及距离计算 `dist`/`dist2`、点在圆内判断 `inside`、两点圆 `circle_from_2`、三点圆 `circle_from_3`。这一层是纯几何计算，不涉及任何算法逻辑，可以单独测试。

2. **算法层（Algorithm）**：`minimum_enclosing_circle`（对外入口，负责洗牌 + 调用递归）和 `welzl_inner`（递归核心，处理边界点集 R）。这一层只依赖几何原语层。

3. **验证与可视化层（Verification & Visualization）**：`brute_force_mec`（暴力基准，独立实现，用于交叉验证）、`write_ppm`（PPM 图像输出）、以及 `main` 里的验证循环（200 次随机试验 + 性能计时）。

这三层之间的依赖是**单向**的：验证层依赖算法层和原语层，算法层依赖原语层，原语层不依赖任何东西。这种单向依赖让每一层都能被独立验证，也避免了"验证代码和算法代码相互影响"的隐患——特别是暴力基准 `brute_force_mec` 必须是**完全独立**的实现，绝不能复用 Welzl 的核心逻辑，否则就是"自己验证自己"，没有任何意义。

### 3.2 关键数据结构设计

**Point 结构体**：最朴素的二维点，两个 `double` 成员 `x, y`。这里刻意不用 `float`——虽然 `float` 更快、内存更省，但在这个几何问题里，精度比速度更重要。三点外接圆的求解涉及行列式运算，`float` 的 7 位有效数字在点距很近、近乎共线时会产生明显的数值误差，导致圆心位置偏离、半径不准。用 `double`（约 15-16 位有效数字）能大幅缓解这个问题。

**Circle 结构体**：成员是圆心 `c`（一个 Point）和半径 `r`（一个 double）。这里有个设计选择：为什么用"圆心 + 半径"而不是"圆心 + 直径"或"三个边界点"来表示圆？

选择"圆心 + 半径"是因为：
- 它是最直观、最省内存的表示（总共 3 个 double）。
- 半径是我们最终要优化的目标，"比较两个圆谁更好"就是"比较半径谁更小"，直接、无歧义。
- 可视化时可以直接用圆心和半径画圆。

**边界点集 R 的表示**：R 用 `vector<Point>` 表示，`reserve(3)` 预留容量。为什么是 vector 而不是固定大小的数组？因为 R 的大小在递归过程中动态变化（0→1→2→3），vector 的 `push_back`/`pop_back` 天然表达了这种"进入边界集 / 离开边界集"的栈式语义。`reserve(3)` 则避免了递归过程中反复重新分配内存的开销。

### 3.3 数据流描述

整个程序的数据流是这样的：

```
生成随机点集 P（200 次试验，每次 2~19 个点，分三种分布模式）
        │
        ├──→ Welzl 算法 → 最小包围圆 C_welzl
        │                    │
        │                    ├─→ 检查每个点是否都在 C_welzl 内（记录最大越界距离）
        │                    └─→ 记录 C_welzl 的半径
        │
        └──→ 暴力基准 → 最小包围圆 C_brute（精确解）
                             │
                             └─→ 记录 C_brute 的半径
        │
        ├──→ 对比 |C_welzl.r - C_brute.r|，记录最大误差
        └──→ 统计 200 次试验的通过率
        │
        └──→ 性能测试（n=60 点，Welzl vs 暴力计时）
        │
        └──→ 可视化（PPM 输出，画点 + 圆 + 圆心）
```

`write_ppm` 不用任何外部库，直接写二进制 PPM（P6 格式）文件。PPM 是最简单的图像格式之一（纯 ASCII 头 + RGB 字节流），非常适合这种"手写可视化"的场景——不需要链接任何图像库，几十行就能画点、画圆。

### 3.4 职责划分：为什么"验证"和"算法"必须分离

这是整个项目里我认为最值得强调的架构决策。很多初学者写算法题，会习惯性地在算法函数里顺便 `printf` 打印结果，"眼见为实"。但"眼见"在几何问题上极不可靠——一个圆看起来"框住"了点，可能实际半径大了 5%；一个渲染结果看起来正常，可能坐标系上下颠倒了。

所以我把验证做成**独立的、量化的、自动断言的**：

- 暴力基准 `brute_force_mec` 是**独立实现**（枚举点对 + 三元组），它和 Welzl 没有任何代码共享。
- 验证循环对每次试验，同时跑 Welzl 和暴力，然后**用数值比较**两者的半径，误差必须 ≤ 1e-6。
- 可视化 `write_ppm` 只是给人眼看的辅助，程序的退出码（`return pass ? 0 : 1`）完全由数值断言决定，和图像无关。

这样，即使某天有人不小心把 `write_ppm` 改坏了（图像画错），数值验证依然能兜底，不会让错误的算法蒙混过关。

## 四、关键代码解析

这一节把核心代码逐段拆解，重点解释"为什么这样写"以及"哪里容易写错"。

### 4.1 几何原语：距离与"点在圆内"

```cpp
double dist2(const Point& a, const Point& b) {
    double dx = a.x - b.x, dy = a.y - b.y;
    return dx*dx + dy*dy;
}
double dist(const Point& a, const Point& b) { return sqrt(dist2(a,b)); }

bool inside(const Circle& C, const Point& p) {
    return dist2(C.c, p) <= C.r*C.r + EPS;
}
```

**为什么用 `dist2`（距离平方）而不是 `dist`（距离）**：因为 `sqrt` 是相对慢的运算，而且在比较"点到圆心距离 vs 半径"这个大小时，我们根本不需要真正的距离，只需要比较平方。`dist2(C.c, p) <= C.r*C.r` 和 `dist(C.c, p) <= C.r` 是**完全等价**的（因为距离和半径都非负），但前者省掉了一次开根号。

`inside` 在 Welzl 递归里会被调用极多次（每次增量都要判断新点是否在当前圆内），所以省掉 `sqrt` 是有实际意义的。

**为什么 `EPS` 加在右边而不是左边**：`+ EPS` 意味着我们略微"放宽"了"在圆内"的判断——一个恰好擦边、因浮点误差稍微越界 `1e-9` 的点，仍被视为"在圆内"。这是合理的容错方向：宁可让一个"其实在圆上"的点被判定为"在圆内"（避免无谓的递归），也不愿把"其实在圆上"的点判为"圆外"（会导致圆被迫扩大，结果不再最小）。

### 4.2 两点圆：无歧义的直径圆

```cpp
Circle circle_from_2(const Point& a, const Point& b) {
    Point c((a.x+b.x)/2.0, (a.y+b.y)/2.0);
    return Circle(c, dist(a,b)/2.0);
}
```

这四行没有太多可说的，但有一个**容易写错**的地方值得提醒：圆心是中点 `(a+b)/2`，半径是 `dist(a,b)/2`，**不是** `dist(a,b)`。如果不小心把半径写成直径长度，圆会大一倍，所有后续验证（和暴力对比）都会失败，而且这种错误很难靠"看图"发现——因为图上一个半径大了一倍的圆，视觉上依然"框住"了所有点。

### 4.3 三点圆：解线性方程组（含退化处理）

```cpp
Circle circle_from_3(const Point& a, const Point& b, const Point& c) {
    double A = b.x - a.x, B = b.y - a.y;
    double C = c.x - a.x, D = c.y - a.y;
    double E = A*(a.x+b.x) + B*(a.y+b.y);
    double F = C*(a.x+c.x) + D*(a.y+c.y);
    double G = 2.0 * (A*(c.y-b.y) - B*(c.x-b.x));
    if (fabs(G) < EPS) {
        Circle c1 = circle_from_2(a,b), c2 = circle_from_2(a,c), c3 = circle_from_2(b,c);
        Circle best = c1;
        if (c2.r > best.r) best = c2;
        if (c3.r > best.r) best = c3;
        return best;
    }
    double cx = (D*E - B*F) / G;
    double cy = (A*F - C*E) / G;
    Point center(cx, cy);
    return Circle(center, dist(center, a));
}
```

这段是代码里公式最密集的部分，逐行解释：

- `A, B` 是向量 `b - a` 的分量；`C, D` 是向量 `c - a` 的分量。
- `E = A·(a.x+b.x) + B·(a.y+b.y)` 展开后是 `(b.x² + b.y²) - (a.x² + a.y²)`——即"到 b 的距离平方减到 a 的距离平方"。这是中垂线方程 `2A·cx + 2B·cy = eb - ea`（其中 `eb = b.x²+b.y²`，`ea = a.x²+a.y²`）的右边。实际上 `E` 恰好等于 `eb - ea`（读者可以手动展开验证 `A·(a.x+b.x) = (b.x-a.x)(b.x+a.x) = b.x² - a.x²`）。
- 同理 `F = ec - ea`。
- `G` 是系数矩阵 `[[A, B], [C, D]]` 的行列式的 2 倍，即 `2(AD - BC)`。当 `G = 0`（即 `AD = BC`，向量 `b-a` 与 `c-a` 共线）时，三点共线，方程组无唯一解。

**共线退化为什么取最大直径圆**：三点共线时，它们排成一条直线，覆盖这三点的最小圆必然是"以最远两点为直径"的圆（想象一条线段上的三个点，最小覆盖圆就是这条线段为直径的圆）。所以代码遍历三个点对，取半径最大的那个直径圆，这是共线情形的正确解。

**容易写错的地方**：`G` 的符号和 `cx, cy` 公式里的正负号。`cx = (D·E - B·F)/G`，`cy = (A·F - C·E)/G`，这里分子的交叉相乘顺序如果写反，圆心会算到错误的位置。推导时要严格从"到 a、b 距离相等"和"到 a、c 距离相等"两个方程出发，用克拉默法则求解，不要凭记忆硬背公式。

### 4.4 Welzl 递归核心

```cpp
Circle welzl_inner(vector<Point>& P, vector<Point>& R, int n) {
    if (n == 0 || R.size() == 3) {
        if (R.empty())      return Circle(Point(0,0), 0);
        if (R.size() == 1)  return Circle(R[0], 0);
        if (R.size() == 2)  return circle_from_2(R[0], R[1]);
        return circle_from_3(R[0], R[1], R[2]);
    }
    int idx = rand() % n;
    Point p = P[idx];
    swap(P[idx], P[n-1]);

    Circle C = welzl_inner(P, R, n-1);
    if (inside(C, p)) return C;

    R.push_back(p);
    C = welzl_inner(P, R, n-1);
    R.pop_back();
    return C;
}
```

逐点解析这个递归：

**`n` 参数的意义**：`n` 表示"当前尚未处理的前缀长度"，即 P 的前 `n` 个元素是"待处理的点"，`n-1` 到末尾是"已选走/暂存的点"。这利用了 `swap` 的技巧：把随机选中的 `p` 换到位置 `n-1`，然后递归处理前 `n-1` 个元素（`n-1` 位置现在被 `p` 占据，但 `n` 参数减小后它就"不可见"了）。这样避免了真正地"从数组中间删除元素"的 O(n) 移动开销，用 O(1) 的 swap 就完成了"把 p 从待处理集合中暂时移除"。

**为什么选 `rand() % n`**：这是随机化打乱的核心。理论上应该在每次递归调用前用 Fisher-Yates 洗牌把整个 P 打乱，但这里用了更轻量的方式——每次递归时从"前 n 个"里随机选一个作为"本轮处理的点"，效果等价于逐步随机选择。这样整个数组的遍历顺序就是一个随机排列。

**"先递归、后判断"的结构**：`C = welzl_inner(P, R, n-1)` 先把 `p` 排除在外求解。如果 `p` 在 `C` 内，那 `C` 就是答案，直接返回。否则 `p` 必须在边界上，于是 `push_back(p)` 到 R，再递归一次（这次 `p` 被强制作为边界点），然后把 R 恢复原状（`pop_back`）。

**`R.pop_back()` 的作用**：这是"回溯"。因为 `R` 是一个共享的、在调用栈中传递的引用，如果不在返回前把 `p` 弹出，就会污染上层递归的 `R`（上层的 R 不该包含这个 `p`）。这是递归 + 引用传参的经典陷阱——忘记回溯会导致结果错误，而且错误往往只在深层递归时才显现，非常隐蔽。

### 4.5 入口函数：洗牌 + 调用递归

```cpp
Circle minimum_enclosing_circle(vector<Point> P) {
    vector<Point> R;
    R.reserve(3);
    mt19937 rng(12345);
    shuffle(P.begin(), P.end(), rng);
    return welzl_inner(P, R, (int)P.size());
}
```

这里用 `std::shuffle` + `mt19937` 对整个 P 做一次性洗牌，然后调用递归。为什么入口处洗牌，而不是依赖递归内部的 `rand() % n`？

实际上两者是**冗余互补**的：递归内部的 `rand() % n` 已经保证了随机选择，但入口处用 `mt19937` + 固定种子洗牌，做到了**可复现**——`mt19937 rng(12345)` 的序列是确定的，所以每次运行洗牌结果一致，验证脚本才能稳定复现。同时，入口洗牌让 `rand() % n` 的随机选择建立在"已经是随机排列"的基础上，进一步确保期望复杂度的成立。

**注意参数是 `vector<Point> P`（按值）而不是引用**：这是刻意的。因为 `welzl_inner` 会原地 swap 打乱 P 的顺序，如果传引用，调用方的 P 会被破坏。按值传递（拷贝一份）虽然多一次 O(n) 拷贝，但保证了调用方的点集不被修改，语义更清晰。对于 n ≤ 60 的场景，这个拷贝开销可以忽略。

### 4.6 暴力基准：独立实现，用于交叉验证

```cpp
Circle brute_force_mec(const vector<Point>& pts) {
    int n = pts.size();
    Circle best(Point(0,0), 0);
    if (n == 0) return Circle(Point(0,0),0);
    if (n == 1) return Circle(pts[0],0);
    if (n == 2) return circle_from_2(pts[0], pts[1]);

    double best_r = 1e18;
    for (int i = 0; i < n; i++) {
        for (int j = i+1; j < n; j++) {
            Circle c2 = circle_from_2(pts[i], pts[j]);
            bool ok = true;
            for (int t = 0; t < n; t++) if (!inside(c2, pts[t])) { ok=false; break; }
            if (ok && c2.r < best_r) { best_r = c2.r; best = c2; }
            for (int k = j+1; k < n; k++) {
                Circle c3 = circle_from_3(pts[i], pts[j], pts[k]);
                ok = true;
                for (int t = 0; t < n; t++) if (!inside(c3, pts[t])) { ok=false; break; }
                if (ok && c3.r < best_r) { best_r = c3.r; best = c3; }
            }
        }
    }
    if (best_r > 1e17) { /* 全共线兜底 */ /* 遍历点对取最小半径圆 */ }
    return best;
}
```

这个暴力基准的思路非常直白：枚举所有点对（直径圆候选）和所有三元组（外接圆候选），对每个候选圆检查它是否覆盖全部 n 个点，在"覆盖"的前提下取半径最小的。

**为什么暴力基准必须"独立"**：如果暴力基准复用了 `minimum_enclosing_circle` 的逻辑，那两者必然得到相同答案，验证就变成了"自己和自己比"，毫无意义。这里暴力基准虽然复用了 `circle_from_2`/`circle_from_3`/`inside` 这些**几何原语**（这部分是绝对可靠、可独立验证的），但**枚举逻辑完全是另一套**（O(n⁴) 的全枚举），和 Welzl 的增量递归没有任何共享。这样，如果 Welzl 的递归逻辑写错了，暴力基准依然能给出正确解，差异就会被验证循环捕捉到。

**`best_r > 1e17` 的兜底**：理论上，如果所有点都共线，那么前面"三元组"枚举里，`circle_from_3` 会退化为直径圆（因为 `G=0` 走退化分支），而"点对"枚举已经覆盖了所有直径圆，所以 `best_r` 一定会被更新。这个兜底分支是为防御性的边界情况保留的，正常情况下不会触发。

### 4.7 验证循环：量化断言

```cpp
const int TRIALS = 200;
for (int t = 0; t < TRIALS; t++) {
    int n = 2 + rand() % 18;  // 2..19 个点
    vector<Point> pts;
    int mode = t % 3;         // 三种分布模式轮换
    for (int i = 0; i < n; i++) {
            double x = (rand()%20001)/100.0 - 100.0;   // [-100,100]
            double y = (rand()%20001)/100.0 - 100.0;
            if (mode == 0)      { x *= 0.1; y *= 0.1; }          // 紧密簇
            else if (mode == 1) { /* 均匀散布 */ }
            else { double ang = (rand()%6283)/1000.0;            // 近似圆环
                   double rad = 80 + (rand()%500)/100.0;
                   x = rad*cos(ang); y = rad*sin(ang); }
            pts.push_back(Point(x,y));
        }
        Circle welzl = minimum_enclosing_circle(pts);
        Circle brute = brute_force_mec(pts);

        // 断言 1：Welzl 圆必须覆盖所有点
        double worst = 0;
        for (auto&p : pts) worst = max(worst, dist(p, welzl.c) - welzl.r);
        max_violation = max(max_violation, worst);
        if (worst <= 1e-6) all_inside_ok++;

        // 断言 2：Welzl 半径必须等于暴力精确解
        double diff = fabs(welzl.r - brute.r);
        max_radius_diff = max(max_radius_diff, diff);
        if (diff <= 1e-6) radius_match++;
    }
```

逐段解释这个验证循环的设计：

**三种分布模式（mode = t % 3）**：这是为了让测试覆盖足够多样化的几何形态，而不是只测"均匀随机点"这种单一情形。三种模式分别是：

1. **mode 0（紧密簇）**：把坐标乘以 0.1，让所有点挤在一个很小的区域里。这种情形下最小包围圆的半径很小，容易暴露"半径计算精度"和"容差设置"的问题。
2. **mode 1（均匀散布）**：坐标在 [-100, 100] 里均匀随机，是"最普通"的情形。
3. **mode 2（近似圆环）**：点大致分布在一个圆环上（半径 80~85）。这种情形下几乎每个点都"贴着"最优圆边界，最能考验算法"边界点确定"的正确性——因为边界上的点很多，算法必须在众多"候选边界点"里精准挑出真正决定圆的那 2~3 个。

**两个独立的断言**：`all_inside_ok`（覆盖性）和 `radius_match`（最优性）是两个**正交**的检查维度。

- "覆盖性"只保证"Welzl 的圆能框住所有点"，但一个"框住所有点"的圆不一定是"最小"的——它可能比最优圆大很多。
- "最优性"通过和暴力精确解对比半径来保证：如果 Welzl 的圆和暴力解半径一致（误差 ≤ 1e-6），且暴力解是"所有覆盖圆里半径最小的"，那么 Welzl 的圆就是真正的最小包围圆。

两个维度合起来，才能完整证明"Welzl 给出的是最小包围圆"。

**为什么容差是 1e-6 而不是 0**：Welzl 和暴力解在理论上应该得到**完全相同**的半径（它们解的是同一个数学问题），但由于两者走的计算路径不同（Welzl 是递归增量，暴力是全枚举），浮点误差的累积方式不同，最后一位可能略有差异。用 1e-6 的容差吸收这种"最后一位"的差异，是正确的工程选择。从实际运行结果看，最大误差只有 `2.84e-14`，远小于 1e-6 的容差，说明两个实现都足够稳定。

### 4.8 可视化：手写 PPM 输出

```cpp
void write_ppm(const vector<Point>& pts, const Circle& C, const string& path) {
    const int W = 800, H = 800;
    vector<unsigned char> img(W*H*3, 255);  // 白色背景

    // 把世界坐标映射到像素坐标
    double minx=1e18,maxx=-1e18,miny=1e18,maxy=-1e18;
    for (auto&p:pts){ minx=min(minx,p.x);maxx=max(maxx,p.x);
                      miny=min(miny,p.y);maxy=max(maxy,p.y); }
    minx=min(minx,C.c.x-C.r); maxx=max(maxx,C.c.x+C.r);
    miny=min(miny,C.c.y-C.r); maxy=max(maxy,C.c.y+C.r);
    double pad = 0.05*(max(maxx-minx,maxy-miny)+1e-9);
    minx-=pad; maxx+=pad; miny-=pad; maxy+=pad;

    auto to_px = [&](double x,double y)->pair<int,int>{
        int px = (int)((x-minx)/(maxx-minx)*W);
        int py = (int)((y-miny)/(maxy-miny)*H);
        return {max(0,min(W-1,px)), max(0,min(H-1,py))};
    };

    // 画圆（用参数方程采样 3600 个点，足够密）
    // 画圆心（红色十字）
    // 画点（蓝色）
    // 写 P6 二进制 PPM
    FILE* f = fopen(path.c_str(),"wb");
    fprintf(f,"P6\n%d %d\n255\n",W,H);
    fwrite(img.data(),1,img.size(),f);
    fclose(f);
}
```

这里有两个值得注意的细节：

**边界自适应（bounding box auto-fit）**：不是固定用某个坐标范围，而是先扫描所有点和圆的范围，算出 `minx/maxx/miny/maxy`，再加上 5% 的 padding。这样无论点集是紧密簇还是大范围散布，图像都能自动适配，圆心和圆不会跑出画面，也不会小得看不见。

**参数方程画圆**：圆没有像素级的"画圆"算法（不像中点 Bresenham 圆），而是用参数方程 `(cx + r·cos θ, cy + r·sin θ)` 对 θ 采样 3600 个点。3600 个点对于 800×800 的图像来说足够密，视觉上是连续的圆。为了加粗圆的线宽，每个采样点会画一个 5×5 的十字（`put(px±1, py)`、`put(px, py±1)`），让圆看起来更清晰。

**为什么可视化不是验证的一部分**：再次强调，`write_ppm` 产出的图只是给人眼看的辅助，它**不参与任何正确性判断**。程序的退出码完全由数值断言（`pass` 变量）决定。这是本项目贯穿始终的设计原则——图可以漂亮，但正确性必须靠数字说话。

## 五、踩坑实录

这一节记录我在实现过程中实际遇到的、或者深刻意识到容易踩的坑。有些是我这次真的踩到并修掉的，有些是"如果没想清楚就会踩"的隐患。

### 5.1 坑一：`R.pop_back()` 忘记回溯

**症状**：在最初的草稿里，我写递归时，在"p 在圆外"的分支里 `push_back(p)` 后递归，但忘记在递归返回后 `pop_back()`。结果对于某些点集，返回的圆偏大——因为 R 里残留了不应该在边界上的点，导致后续的圆被这些"幽灵边界点"错误约束。

**错误的假设**：我当时以为"反正 R 传引用，push 进去的 p 就是边界点，不用弹出来"。

**真实原因**：R 是**共享引用**，在调用栈的每一层都指向同一个 vector。如果不回溯，下层的 R 修改会"泄漏"到上层——上层递归返回后，R 里多了一个本不该存在的点，影响上层"以 R 为边界点集"的计算。这是递归 + 引用传参最经典的陷阱。

**修复方式**：在递归返回前 `R.pop_back()`，让 R 恢复到进入该层递归前的状态。这是标准的"回溯"模式，和 DFS 里"访问完恢复现场"是同一个道理。

### 5.2 坑二：半径写成直径

**症状**：`circle_from_2` 里，我一度把半径写成了 `dist(a,b)`（忘了除以 2）。结果所有圆的半径都是正确的 2 倍，和暴力解对比时误差巨大，验证 100% 失败。

**错误的假设**：直觉上"直径圆"容易让人把"直径"直接当成"半径"写进去。

**真实原因**：两点构成直径，圆心在中点，半径是**直径的一半** = `dist(a,b)/2`。这是"直径圆"这个名字带来的心理暗示陷阱。

**修复方式**：明确写出 `dist(a,b)/2.0`，并且在心里默念"圆心在中点，半径是半长"。

### 5.3 坑三：三点圆公式的符号

**症状**：三点外接圆的圆心坐标 `cx, cy` 计算公式里，分子交叉相乘的顺序很容易写反。一旦写反，圆心会偏到错误位置，半径也随之错误，且这种错误不是"稍微偏差"而是"完全错误"，在和暴力解对比时一眼就能看出异常。

**错误的假设**：凭记忆或"感觉"写克拉默法则的分子，而不是从方程严格推导。

**真实原因**：`cx = (D·E - B·F)/G` 这个式子的分子顺序，来源于 2×2 线性方程组 `[[2A,2B],[2C,2D]]·[cx,cy] = [E,F]`（其中 E、F 是右边常数项的 2 倍）。用克拉默法则，`cx` 的分子是把系数矩阵第一列换成常数项后的行列式 `[[E,B],[F,D]] = ED - BF`。如果手滑写成 `B·F - D·E`，符号就反了。

**修复方式**：不背公式，每次从"到 a、b 距离相等"和"到 a、c 距离相等"两个方程出发，用克拉默法则现推。或者干脆用矩阵求逆的通用方法（针对 2×2），减少手写符号出错的机会。

### 5.4 坑四：共线三点的退化没处理

**症状**：如果三点恰好共线，`circle_from_3` 里的 `G = 0`，直接除会发生除零错误（得到 inf 或 nan），圆心变成无穷远，半径变成 nan，后续所有点都会被误判为"在圆内"（因为 `nan` 比较总是 false），导致结果混乱。

**错误的假设**：以为"随机生成的点几乎不可能共线，所以不用处理"。

**真实原因**：虽然随机点严格共线的概率是 0，但**近乎共线**的点（三点几乎在一条直线上，G 非常接近 0 但不为 0）会导致 `G` 很小，除法结果数值不稳定，圆心剧烈跳动。而"严格共线"虽然概率为 0，但浮点数世界里"数值上共线"（G 的绝对值小于 EPS）是完全可能发生的，尤其是点分布很特殊的时候。

**修复方式**：检测 `|G| < EPS`，退化为"取三个直径圆里半径最大的那个"。这个退化分支既处理了严格共线，也处理了数值近似共线，是防御性编程的体现。

### 5.5 坑五：容差方向搞反

**症状**：如果把 `inside` 里的容差写成 `dist2 <= C.r*C.r - EPS`（减号而不是加号），那么"恰好擦边"的点会被误判为"在圆外"，触发不必要的递归，极端情况下会导致圆的半径略微偏大。

**错误的假设**：以为容差是"对称"的，加和减无所谓。

**真实原因**：容差的方向是有讲究的。"在圆内"的判断应该**偏向于宽松**（即把"其实在圆上"的点判为"在内"），因为：
- 把"在圆上"判为"在内"，结果是那个点不再触发递归，圆的大小保持最优——这是正确的行为。
- 把"在圆上"判为"在外"，结果是那个点被强制加入边界集，圆的求解被过度约束，可能得到一个"假装最小"但实际偏大的圆。

所以容差应该加在半径平方一侧（`+ EPS`），让判断"点在内"的范围略微扩大。

### 5.6 坑六：验证代码和算法代码耦合

**症状**：（这是我在设计阶段的"预防性反思"，而不是实际踩到的坑）如果暴力基准 `brute_force_mec` 直接调用 `minimum_enclosing_circle` 来"生成答案"，那验证就失去了意义——你在用同一条代码验证它自己。

**错误的假设**：觉得"复用现成代码更省事、更不容易出错"。

**真实原因**：验证的本质是**交叉验证（cross-validation）**，必须用**独立实现**的参照物。暴力枚举和 Welzl 递归是两种完全不同的算法思路，只有让它们各自独立实现、分别求解、再对比结果，才能互相印证。如果共用代码，两者会共享同一个 bug，验证形同虚设。

**修复方式**：暴力基准只用几何原语（`circle_from_2`/`circle_from_3`/`inside`），枚举逻辑完全独立手写。这样即使 Welzl 的递归有 bug，暴力解的独立性也能保证它自己是正确的参照物。

## 六、效果验证与数据

这一节放实际运行结果，全部是量化数据，不是"截图看起来正确"。

### 6.1 数值验证结果

运行 `./output`，输出如下（节选关键部分）：

```
================ 量化验证结果 (Welzl 最小包围圆) ================
试验次数            : 200
所有点在圆内        : 200 / 200  (100.0%)
最大越界距离        : 2.842171e-14 (应 ~0)
半径与暴力基准一致  : 200 / 200  (100.0%)
最大半径误差        : 2.842171e-14 (应 ~0)
----------------------------------------------------------------
✅ 全部量化验证通过
----------------------------------------------------------------
点数 n=60 : Welzl=0.023 ms, 暴力=0.431 ms, 加速比=19.09x
已生成可视化: welzl_mec_output.ppm (中心=(6.62,-0.69), 半径=116.995)
```

逐项解读这些数据：

**覆盖性**：200 次试验，每次 2~19 个点，Welzl 圆覆盖了**所有**点（200/200 = 100%），最大越界距离 `2.84e-14`，这是浮点误差量级（10⁻¹⁴），在实际意义上就是 0。说明 Welzl 圆确实"框住"了所有点，没有遗漏。

**最优性**：200 次试验里，Welzl 的半径和暴力 O(n⁴) 精确解**完全一致**（200/200 = 100%），最大半径误差 `2.84e-14`。这说明 Welzl 圆不仅是"一个覆盖圆"，而且是"最小覆盖圆"。这一点尤其关键——因为"覆盖"容易，"最小"才难，而数据证明 Welzl 在 200 次随机试验里从未给出过一个"不够小"的圆。

**性能**：n=60 时，Welzl 耗时 0.023ms，暴力耗时 0.431ms，加速比约 19 倍。这个加速比看起来"只有 19 倍"，但要注意：这是 n=60 的小规模对比，暴力 O(n⁴) 在这个规模还"跑得动"。当 n 增大到 100、200、1000 时，Welzl 是 O(n) 线性增长，而暴力是 O(n⁴) 四次方增长，加速比会指数级拉大。n=60 就有 19 倍，n=200 时 Welzl 只需几毫秒而暴力要几秒，n=1000 时暴力已经需要数小时甚至数天。

### 6.2 可视化输出

程序输出的 `welzl_mec_output.ppm`（已转换为 PNG 作为封面图）：

- 蓝色点：输入点集。
- 红色圆：Welzl 算法求出的最小包围圆。
- 红色十字：圆心。

对于 n=60 的点集，圆心在 `(6.62, -0.69)`，半径 116.995。这个圆恰好把所有点包住，且边界上至少有 2~3 个点"贴着"圆周——这正是最小包围圆的几何特征。

### 6.3 验证的充分性说明

为什么 200 次试验足够让人放心？几个理由：

1. **三种分布模式覆盖了退化边界**：紧密簇（考验精度）、均匀散布（常规）、近似圆环（考验边界点确定），而非单一随机分布。
2. **点数量覆盖了边界情形**：从 2 个点（最小非平凡情形）到 19 个点，覆盖了"两点直径"和"三点外接"两类解。
3. **独立参照物**：每一轮都和暴力精确解交叉验证，而不是自证。
4. **误差量级**：所有误差都在 10⁻¹⁴ 量级，远小于 10⁻⁶ 容差，说明算法稳定，没有在容差边缘危险的摇摆。

当然，严格的证明需要数学推导（Welzl 1991 的论文），这里的数值验证是**工程层面的正确性保障**，用于捕捉实现 bug 已经足够——如果实现有错，200 次随机对比里几乎必然会出现至少一次半径不一致。

## 七、总结与延伸

### 7.1 技术局限性

最小包围圆（以及 Welzl 算法）并不总是最优选择，它有几个明确的局限：

1. **只适合"点集"输入**：如果输入不是离散点，而是一堆多边形、曲线或不确定形状的区域，最小包围圆问题就变成了更难的最小包围体问题，Welzl 算法不能直接套用。

2. **维度扩展的代价**：Welzl 算法可以推广到任意维度（最小包围球、最小包围超球），但维度越高，边界点的上限越大（d 维需要 d+1 个边界点），递归深度和常数因子随之增长。在高维（比如特征空间的聚类）场景下，常数因子的膨胀可能抵消线性复杂度的优势。

3. **对浮点精度敏感**：三点外接圆的求解涉及行列式，当点近乎共线（行列式接近 0）时，数值稳定性会急剧恶化。本文用 `double` + EPS 容差缓解了这个问题，但在超高精度或极端病态的输入下仍需额外注意。

4. **"最小"未必是"最好"**：在实际工程里（比如包围体），有时一个"稍大但形状更规则"的包围体（比如轴对齐包围盒 AABB）反而更有用，因为 AABB 的相交测试比球体更便宜。最小包围圆是"最紧"，但未必是"最划算"。

### 7.2 可继续优化的方向

1. **非递归实现**：当前的 `welzl_inner` 是递归的，虽然递归深度 ≤ 3（因为 R ≤ 3），但在极端的点集下，递归的调用栈开销可以优化成显式迭代（用栈模拟），进一步降低常数因子。

2. **消除 `rand()` 依赖 `mt19937` 的统一**：代码里递归内部用 `rand()`，入口用 `mt19937`，两者混用略显不统一。可以彻底统一为 `mt19937`（从入口传入 rng 引用），既保证跨平台一致性，也让随机性来源单一、可追踪。

3. **增量更新（在线版本）**：当点集动态变化（点被加入/删除）时，与其每次重新算一遍最小包围圆，不如维护一个"动态最小包围圆"结构。这在游戏中（比如角色移动导致包围球需要更新）是一个真实的优化方向。

4. **扩展到三维**：把 `circle_from_2`/`circle_from_3` 推广到 `sphere_from_2/3/4`，Welzl 的递归框架几乎不变（只是边界点上限从 3 变成 4），就能得到最小包围球，用于游戏引擎的包围球生成。

### 7.3 与本系列其他文章的关联

这个项目属于"计算几何"专题。回顾本系列近期做过的相关项目：

- **08-17 最近点对（Closest Pair）**：同样是"看似简单、朴素 O(n²) 太慢"的计算几何问题，用分治降到 O(n log n)。两个项目共同体现了"用算法结构代替暴力枚举"的核心思想。
- **08-03 旋转卡尺最小包围矩形（Rotating Calipers）**：和"最小包围圆"是"最小包围体"家族的兄弟——一个求最小矩形，一个求最小圆。旋转卡尺用了"对踵点"技巧，Welzl 用了"随机增量"技巧，都是计算几何里精巧的算法设计。
- **08-14 Marching Squares**：另一个几何问题（等值线提取），共同点在于都需要处理"退化情形"（共线、共点等）——这是计算几何里反复出现的主题。

这些项目串起来，形成了一条清晰的脉络：**计算几何问题的难点往往不在"基本想法"（暴力枚举谁都会），而在"如何用巧妙的算法结构把复杂度降下来，同时正确处理各种几何退化情形"**。Welzl 算法通过"随机化 + 增量 + 递归（深度受限）"实现了从 O(n⁴) 到期望 O(n) 的跨越，是这条脉络上一个漂亮的里程碑。
