# 后缀数组与 LCP：前缀倍增排序 + Kasai 算法的完整实现

## ① 背景与动机

在处理文本数据的时候，我们经常会遇到一个看似简单、实则暗藏复杂度的问题：**给定一个长度为 n 的字符串，如何高效地回答"这个字符串的所有后缀中，字典序第 k 小的是哪一个？"** 更进一步，**如何快速求出任意两个后缀的最长公共前缀（Longest Common Prefix, LCP）？**

这两个问题听起来像是字符串理论里的"冷门玩具"，但实际上它们是许多重量级算法的地基。举几个工业界真实的例子：

- **全文检索与倒排索引**：搜索引擎在对文档建立索引时，常常需要快速判断某个查询词是否是某个长文本的子串。后缀数组配合二分查找，可以在 O(m log n) 的时间内完成一次子串查询（m 是查询串长度），而暴力比对则需要 O(m × n)。

- **DNA 序列分析**：生物信息学中的基因序列比对、重复序列检测、最长重复子串挖掘，几乎全部建立在后缀数组 / LCP 之上。人类基因组的几亿个碱基对，如果暴力两两比对，计算量是天文数字，而后缀数组把它压缩到 O(n log n)。

- **数据压缩**：Burrows-Wheeler Transform（BWT，BZIP2 压缩的核心）可以直接从后缀数组推导出来。理解了后缀数组，就理解了 BZIP2 的一半。

- **代码查重与相似文本检测**：最长重复子串、最长公共子串这类问题，都可以通过后缀数组 + LCP 在近线性时间内解决。

那么，没有后缀数组之前，这些问题的"痛点"是什么？简单说就是：**排序 n 个后缀的朴素做法，需要对 n 个字符串做 O(n log n) 次字符串比较，每次比较最坏 O(n)，总复杂度 O(n² log n)。** 当 n 达到 10⁵ 甚至 10⁶ 时，这根本跑不动。

后缀数组的价值在于，它用**倍增（prefix doubling）**这一精巧的技巧，把"排序 n 个子串"这个看似 O(n²) 的问题，通过"每次只比较 2^k 长度的前缀、逐步加倍直到至少 n"的方式，降到了 **O(n log n)**。配合 Kasai 算法在 O(n) 内求出 LCP 数组，我们就拥有了一个处理绝大多数字符串问题的强力工具箱。

今天这篇文章，我会完整地实现这两个算法，并用**暴力穷举作为基准**做量化正确性验证，同时测量加速比，确保代码真正正确、真正快，而不是"看起来对"。

本文的代码与之前的每日编程实践一脉相承，同样强调"量化验证、不靠眼睛"的工程习惯。如果你看过之前关于 KMP、Aho-Corasick、Manacher 的文章，你会发现本文补齐了字符串算法家族里"数据结构"这一块最重要的拼图。

## ② 核心原理

### 2.1 什么是后缀数组

给定字符串 `s[0..n-1]`，它的 n 个后缀分别是：

- `s[0..n-1]`（从位置 0 开始）
- `s[1..n-1]`（从位置 1 开始）
- ...
- `s[n-1..n-1]`（从位置 n-1 开始，只有一个字符）

**后缀数组 SA** 是一个长度为 n 的整数数组，满足 `sa[0] < sa[1] < ... < sa[n-1]`，且这些整数是 `{0, 1, ..., n-1}` 的一个排列，并满足：后缀 `s[sa[0]..]` 的字典序小于等于（严格小于）`s[sa[1]..]`，以此类推。

也就是说，SA 记录了"把所有后缀按字典序排序后，每个后缀在原串中的起始下标"。

举个例子，`s = "banana"`：

- 所有后缀及其字典序排序：
  1. `"a"`（起始下标 5）
  2. `"ana"`（起始下标 3）
  3. `"anana"`（起始下标 1）
  4. `"banana"`（起始下标 0）
  5. `"na"`（起始下标 4）
  6. `"nana"`（起始下标 2）

所以 `SA = [5, 3, 1, 0, 4, 2]`。

直观理解：SA[i] 就是"排名第 i 小的后缀从哪个位置开始"。

### 2.2 前缀倍增（Prefix Doubling）的核心思想

直接排序 n 个后缀很慢，因为每次字符串比较都要 O(n)。倍增的洞察是：**我们不需要一次比较完整后缀，可以"分阶段"来排序。**

定义 rank 数组 `rnk[i]` 表示"后缀 i 当前按前 2^k 个字符排序的排名"。初始时 k=0，即按每个后缀的第一个字符排序（可以用计数排序在 O(n + σ) 完成，σ 是字符集大小）。

然后进行"倍增"：假设我们已经按"前 2^k 个字符"排好了序（即 rnk 数组已知），现在要按"前 2^{k+1} 个字符"排序。

关键观察：后缀 i 的前 2^{k+1} 个字符，可以拆成两半：

- 前半：`s[i .. i+2^k-1]` —— 这正是后缀 i 的前 2^k 个字符，我们已知它的排名 `rnk[i]`
- 后半：`s[i+2^k .. i+2^{k+1}-1]` —— 这正是后缀 `i+2^k` 的前 2^k 个字符，已知排名 `rnk[i+2^k]`

于是，按前 2^{k+1} 个字符排序，等价于**按二元组 (rnk[i], rnk[i+2^k]) 排序**。

**这就是倍增法的全部魔法：把"比较长长字符串"转化为"比较两个整数"**。而两个整数的比较是 O(1) 的。配合两次计数排序（基数排序），我们可以在 O(n) 完成每一轮倍增的排序。

具体地说，每轮排序是一个**基数排序**，先按第二关键字（低"位"）排序，再按第一关键字（高"位"）稳定排序：

1. **按第二关键字排序**：我们要得到"按 rnk[i+2^k] 排序的后缀列表"。注意 `i+2^k >= n` 的那些后缀，第二关键字不存在，视为 -1（最小），它们应该排在最前面。剩下的后缀，因为 rnk 已经是排序好的，我们只需要按这个顺序取出 `i = sa[j] - 2^k`（当 `sa[j] >= 2^k` 时），就能得到按第二关键字有序的列表。

2. **按第一关键字稳定排序**：对上面得到的列表，用计数排序按第一关键字 rnk 做稳定排序，就得到了按二元组排序的最终 SA。

3. **重新计算 rank**：遍历新的 SA，相邻两个后缀如果它们的二元组相同，则 rank 相同，否则 rank 递增。当所有后缀的 rank 都互不相同（即 classes == n）时，说明排序已经完成，可以提前结束。

每一轮 k 翻倍，所以最多 log n 轮，每轮 O(n)，总复杂度 **O(n log n)**。

### 2.3 为什么"计数排序"是必要的

你可能会问：每轮直接用 `std::sort` 按二元组比较不就行了吗？那样每轮是 O(n log n)，总复杂度变成 O(n log² n)，而且在常数上更慢。

计数排序在这里是最优选择，原因有二：

1. **关键字是整数且范围已知**：第一关键字 rnk 取值在 `[0, classes-1]`，classes ≤ n；第二关键字的"排序"本质上是复用已有的 SA 顺序，根本不需要额外排序。这正好符合计数排序"在线性时间内、对取值范围有限的整数排序"的前提。

2. **稳定排序的性质**：基数排序要求"先按低位排、再按高位稳定排"。计数排序天然是稳定的（我们从后往前放置元素，保证相同关键字时保持原相对顺序），这正好满足双重关键字排序的需求。

这是理解整个算法效率的关键：**普通的比较排序是 O(n log n)，而我们这里利用了"rank 是已经排好的整数"这个先验信息，把排序降到了 O(n)。**

### 2.4 Kasai 算法求 LCP（O(n)）

LCP 数组 `lcp[i]` 定义为：`LCP(sa[i], sa[i+1])`，即 SA 中相邻两个后缀的最长公共前缀长度。它是一个长度为 n-1 的数组。

暴力求 lcp 数组需要 O(n²)，因为每次求两个后缀的 LCP 都可能扫 O(n) 个字符。Kasai 算法利用了一个巧妙的性质，把它降到 O(n)。

核心洞察：设 `rank[i]` 是后缀 i 在 SA 中的排名（即 SA 的逆排列），我们按原串位置 i = 0, 1, ..., n-1 的顺序来依次计算 `LCP(suffix[i], suffix[rank[i]+1])`（即后缀 i 和它在 SA 中紧邻的下一名后缀的 LCP）。

维护一个变量 `h`，表示"后缀 i 与 SA 中下一名后缀的 LCP 长度"。关键定理是：

> **Kasai 定理**：设 `h = LCP(suffix[i], suffix[sa[rank[i]+1]])`，那么当处理下一个原位置 `i+1` 时，`LCP(suffix[i+1], suffix[sa[rank[i+1]+1]]) >= h - 1`。

**直觉解释**：如果后缀 `s[i..]` 和 `s[j..]` 有公共前缀长度 h，那么去掉首字符之后的 `s[i+1..]` 和 `s[j+1..]` 至少还有 h-1 的公共前缀。而 `s[j+1..]` 不一定是 `s[i+1..]` 在 SA 中的下一名，但"SA 中下一名"至少不会比 `s[j+1..]` 差（它的 LCP 只会更大，因为下一名是所有后缀中"最接近"的那一个）。

因此，我们可以让 `h` 在每轮迭代中"减一"，而不是重置为零，从而保证 h 的**总增长量是 O(n)**（每次 while 内层字符比较都会让 h+1，而 h 每次最多减 1，总共减不超过 n 次，所以字符比较总次数是 O(n)）。

这就是为什么 Kasai 能在 O(n) 时间内求出完整的 LCP 数组——它的复杂度来源于"h 是单调递减然后逐步递增的"，而不是每个后缀都从头比较。

### 2.5 LCP 数组能干什么：数不重复子串

LCP 数组的一个经典应用是**统计字符串中不同子串的数量**。定理如下：

> 长度为 n 的字符串，所有子串总数是 n(n+1)/2。其中"重复的"子串数量正好等于 LCP 数组所有元素之和。因此 **不同子串数量 = n(n+1)/2 - Σ lcp[i]**。

**为什么不重复子串 = 总数 - Σ lcp？** 想象我们把所有后缀按字典序排成一行（就是 SA）。对每个后缀，它的所有前缀都是一个子串。但这些前缀中，有一部分会和"排在前面的那个后缀"的前缀重复——具体重复多少，正好就是它们俩之间的 LCP。

因此，遍历 SA，从每个后缀贡献的 n - sa[i] 个前缀里，减去与前一名的公共前缀 lcp[i-1]（这些已经在前一名被数过了），累加起来就是不重复的子串数。这个累加恰好等于 n(n+1)/2 - Σ lcp[i]。

这个定理非常漂亮，也很适合作为算法正确性的"独立交叉验证"：我们用后缀数组算出一个不重复子串数，再用 `std::set` 暴力枚举所有子串数一遍，两者必须完全相等。**这就是我们后面量化验证里的一项硬指标。**

## ③ 实现架构

整个程序的数据流非常清晰，我把它拆成三层：

```
输入字符串 s
    │
    ├── build_suffix_array(s)     ← 前缀倍增 + 计数排序（O(n log n)）
    │        └── 返回 SA（后缀按字典序排序的起始下标）
    │
    ├── build_lcp(s, SA)          ← Kasai 算法（O(n)）
    │        └── 返回 LCP（SA 相邻后缀的最长公共前缀）
    │
    └── 三套基准/验证逻辑：
             ├── 暴力 SA（std::sort + 直接比较后缀）
             ├── 暴力 LCP（逐字扫描）
             └── std::set 枚举所有子串（独立交叉验证）
```

**核心数据结构设计：**

- `sa`（vector\<int\>）：后缀数组，`sa[i]` = 排名第 i 的后缀起始下标。
- `rnk`（vector\<int\>）：后缀 i 在当前倍增轮次下的排名。
- `pn`（vector\<int\>）：临时数组，用于存放"按第二关键字排序后的后缀位置列表"。
- `cnt`（vector\<int\>）：计数排序的计数数组，大小取 `max(256, n)` 以覆盖字符初始排序和后续的 rank 排序。
- `lcp`（vector\<int\>）：长度为 n-1，`lcp[i] = LCP(sa[i], sa[i+1])`。

**职责划分：**

- `build_suffix_array`：纯粹的排序逻辑，不依赖任何库排序函数，全程手写计数排序，保证 O(n log n) 且常数小。
- `build_lcp`：纯粹的 LCP 计算，只依赖 SA 和原串 s，通过 Kasai 定理在 O(n) 完成。
- 验证部分：`brute_suffix_array`、`brute_lcp`、以及 `set<string>` 枚举，它们慢但绝对正确，作为"黄金基准"。

这里强调一个工程决策：**为什么把"暴力基准"也写进同一个程序里？** 因为每日编程实践的核心理念是"量化验证、不能靠眼睛"。如果只写快算法而不写基准，我们就无法证明它是对的。把基准内嵌在主程序里，每次运行都自动交叉比对，一旦快算法引入任何 bug，立刻能在 200+ 个随机测试上暴露出来。

**复杂度小结：**

| 组件 | 复杂度 | 说明 |
|------|--------|------|
| 后缀数组（前缀倍增） | O(n log n) | 每轮计数排序 O(n)，共 log n 轮 |
| LCP（Kasai） | O(n) | h 单调递减 + 总增量 O(n) |
| 暴力 SA | O(n² log n) | 排序 O(n log n) 次比较 × 每次 O(n) |
| 暴力 LCP | O(n²) | 每个后缀对逐字扫描 |
| 不重复子串（SA 法） | O(n) | 在 O(n log n) 建 SA 之后 |
| 不重复子串（set 法） | O(n² log n) | 枚举 O(n²) 个子串插入 set |

## ④ 关键代码解析

下面我把所有核心代码完整贴出并逐段讲解"为什么这么写"。代码不长，但每一行都有它的道理。

### 4.1 前缀倍增后缀数组

首先是初始排序——按第一个字符用计数排序：

```cpp
vector<int> build_suffix_array(const string& s) {
    int n = (int)s.size();
    vector<int> sa(n), rnk(n);

    // 初始：按第一个字符计数排序（O(n + σ)）
    int maxv = 256;                       // 假设字符范围 0..255
    vector<int> cnt(max(maxv, n), 0);     // cnt 要同时容纳 256 和后续的 n
    for (int i = 0; i < n; i++) cnt[(unsigned char)s[i]]++;
    for (int i = 1; i < maxv; i++) cnt[i] += cnt[i - 1];   // 前缀和
    for (int i = n - 1; i >= 0; i--) sa[--cnt[(unsigned char)s[i]]] = i;
```

**为什么从后往前放置 `sa[--cnt[...]]`？** 这是计数排序保证"稳定性"的关键。从后往前遍历，遇到相同字符时，靠后的字符会先被放到靠后的槽位，从而保持它们之间的相对顺序。虽然后续倍增里的稳定排序已经由第二轮计数排序保证，但这里养成稳定排序的习惯是无害且清晰的。

注意 `(unsigned char)` 的强转：`char` 可能是带符号的，如果字符串包含高字节（值 ≥ 128 的字节），直接当数组下标会得到负数，导致越界。转成 `unsigned char` 保证下标在 0..255。

接下来初始化排名：

```cpp
    rnk[sa[0]] = 0;
    int classes = 1;                      // 当前有多少个不同的 rank
    for (int i = 1; i < n; i++) {
        if (s[sa[i]] != s[sa[i - 1]]) classes++;   // 字符不同 rank 才递增
        rnk[sa[i]] = classes - 1;
    }
```

`classes` 表示"当前有多少个不同的等价类（rank）"。当 classes == n（每个后缀的 rank 都唯一）时，整个排序就彻底完成了，可以提前跳出循环。这是倍增法的**提前终止优化**——对于没有大量重复后缀的字符串，往往不需要跑满 log n 轮。

然后是核心的倍增循环：

```cpp
    for (int k = 1; k < n; k <<= 1) {
        // Step 1: 按第二关键字排序（rnk[i + k]）
        vector<int> pn(n);
        int cur = 0;
        // 后缀 i 满足 i + k >= n 时，第二关键字视为 -1（最小），排最前面
        for (int i = n - k; i < n; i++) pn[cur++] = i;
        // 其余后缀按当前 SA 顺序（本身就是按 rnk 排的）取出 i - k
        for (int i = 0; i < n; i++)
            if (sa[i] >= k) pn[cur++] = sa[i] - k;
```

这段是**最容易写错的地方**，值得逐字解释。

我们要按第二关键字 `rnk[i+k]` 排序。第二关键字最小的是那些 `i+k >= n` 的后缀——它们的第 k 个字符"越界"了，等同于一个虚拟的 `-1`，必然比任何真实 rank 都小，所以要排在最前面。这些下标就是 `i ∈ [n-k, n-1]`。

剩下的后缀 `i ∈ [0, n-k-1]`，它们的第二关键字是 `rnk[i+k]`。因为 SA 现在是"按 rnk 升序"排列的，所以如果我们遍历 SA，取 `j = sa[t]`，那么 `rnk[j]` 是递增的。设 `i = j - k`（即 `i + k = j`），那么按 j 递增的顺序取 i，就等价于按 `rnk[i+k]` 递增的顺序取 i。这就是 `if (sa[i] >= k) pn[cur++] = sa[i] - k` 的含义：`sa[i]` 是递增的 rank，减 k 之后得到的下标，其第二关键字 `rnk[sa[i]]` 也是递增的。

**为什么要求 `sa[i] >= k`？** 因为当 `sa[i] < k` 时，`sa[i] - k` 是负数，说明这个下标对应的后缀其 `i+k` 已经越界（即 `i < 0` 不合法），它已经在前面那个"越界"的分支里被处理过了（因为 `sa[i] < k` 意味着 i = sa[i] - k < 0，等价于 sa[i] 本身 < k，其第二关键字越界）。所以这里用 `>= k` 精确地把"第二关键字不越界"的那批后缀接在后面。

接着是第二步，按第一关键字稳定排序：

```cpp
        // Step 2: 对 pn 按第一关键字 rnk 做稳定计数排序
        fill(cnt.begin(), cnt.begin() + classes, 0);
        for (int i = 0; i < n; i++) cnt[rnk[pn[i]]]++;
        for (int i = 1; i < classes; i++) cnt[i] += cnt[i - 1];
        for (int i = n - 1; i >= 0; i--) sa[--cnt[rnk[pn[i]]]] = pn[i];
```

`pn` 已经按第二关键字排好序了。现在按第一关键字 `rnk[pn[i]]` 做**稳定**计数排序，就得到按二元组 `(rnk[i], rnk[i+k])` 排序的结果。再次从后往前放置，保证第一关键字相同时，第二关键字原有顺序不被打乱——这正是基数排序"先低位后高位"的标准做法。

第三步，重新计算 rank：

```cpp
        // Step 3: 重算 rank，比较相邻二元组是否相同
        vector<int> newRnk(n);
        newRnk[sa[0]] = 0;
        int nc = 1;
        for (int i = 1; i < n; i++) {
            int prev = sa[i - 1], now = sa[i];
            bool diff = (rnk[prev] != rnk[now]) ||
                        ((prev + k < n ? rnk[prev + k] : -1) !=
                         (now + k < n ? rnk[now + k] : -1));
            if (diff) nc++;
            newRnk[now] = nc - 1;
        }
        rnk = newRnk;
        classes = nc;
        if (classes == n) break;   // 所有 rank 唯一，排序完成
    }
    return sa;
}
```

这里比较两个后缀 `prev` 和 `now` 当前轮次的二元组是否相等：第一关键字 `rnk[prev] == rnk[now]` 且第二关键字 `rnk[prev+k] == rnk[now+k]`。第二关键字的取值要注意 `prev+k >= n` 时视为 `-1`（越界的虚拟值），所以用三元表达式 `(prev + k < n ? rnk[prev + k] : -1)` 来优雅处理。

**为什么用 `-1` 而不是别的？** 因为真实 rank 从 0 开始，`-1` 比任何真实 rank 都小，正好符合"越界的第二关键字最小"这一语义，和前面 pn 构造时的约定完全一致。

### 4.2 Kasai LCP

```cpp
vector<int> build_lcp(const string& s, const vector<int>& sa) {
    int n = (int)s.size();
    vector<int> rank(n), lcp(n - 1, 0);
    for (int i = 0; i < n; i++) rank[sa[i]] = i;   // SA 的逆排列

    int h = 0;   // 当前后缀 i 与 SA 中下一名的 LCP 长度
    for (int i = 0; i < n; i++) {
        int r = rank[i];
        if (r == n - 1) { h = 0; continue; }   // 已经是最后一名，没有下一名
        int j = sa[r + 1];                      // SA 中紧邻 i 的下一名
        while (i + h < n && j + h < n && s[i + h] == s[j + h]) h++;
        lcp[r] = h;
        if (h > 0) h--;    // 关键：h 只减一，不归零
    }
    return lcp;
}
```

`rank[i]` 是后缀 i 的排名，也就是 SA 的逆排列。外层循环按原串位置 i 从 0 到 n-1 遍历（而不是按 SA 顺序），这是 Kasai 算法的精髓——按原位置顺序，可以让 `h` 借助"去掉首字符后 LCP 至少减一"的性质来摊还。

`h` 的初始化与更新是整个复杂度的关键：每轮 while 里，`h` 每 +1，就对应一次成功的字符比较。while 结束后，`h` 最多 -1（当 `h > 0` 时）。所以 h 的总减少量 ≤ n，而 h 每次增加都来自字符比较，因此**字符比较总次数 ≤ n + n = O(n)**。

**为什么 `r == n-1` 时直接 `h = 0`？** 因为排名最后的后缀没有"下一名"，它的 LCP 无定义。而让 `h = 0` 是安全的——因为下一个 i+1 的后缀，其 LCP 下界是 `h-1 = -1`，即下界为 0，不受影响。

**`if (h > 0) h--` 为什么是必须的？** 这是 Kasai 定理的直接实现：`LCP(i+1) >= LCP(i) - 1`。如果我们不把 h 减一，而是每次都从 0 重新开始比较，那最坏情况会退化成 O(n²)。这一行 `h--` 就是整个算法 O(n) 复杂度的来源。

### 4.3 暴力基准

```cpp
vector<int> brute_suffix_array(const string& s) {
    int n = (int)s.size();
    vector<int> sa(n);
    iota(sa.begin(), sa.end(), 0);
    sort(sa.begin(), sa.end(), [&](int a, int b) {
        return s.compare(a, n - a, s, b, n - b) < 0;  // 直接用 string.compare 比较后缀
    });
    return sa;
}
```

暴力版本直接对下标排序，比较器里用 `s.compare(a, n-a, s, b, n-b)` 来比较两个后缀的字典序。`std::string::compare(pos, len, ...)` 签名可以指定从某个位置开始比较多长，这里正好用来比较后缀。它慢（O(n² log n)），但语义极其清晰、几乎不可能写错，所以是完美的"黄金基准"。

```cpp
vector<int> brute_lcp(const string& s, const vector<int>& sa) {
    int n = (int)s.size();
    vector<int> lcp(n - 1, 0);
    auto lcp_of = [&](int a, int b) {
        int h = 0;
        while (a + h < n && b + h < n && s[a + h] == s[b + h]) h++;
        return h;
    };
    for (int i = 0; i < n - 1; i++) lcp[i] = lcp_of(sa[i], sa[i + 1]);
    return lcp;
}
```

暴力 LCP 就是对 SA 里每对相邻后缀，逐字符扫描求公共前缀。慢但绝对正确。

## ⑤ 踩坑实录

这次实现踩了两个真实的坑，都值得记录下来。正是因为"量化验证、不靠眼睛"的习惯，坑 1 才在 226 个测试中被第一时间揪出来。

### 坑 1：第二关键字排序写错，导致 SA 完全错误

**症状**：程序编译通过、运行不崩溃，但正确性验证立刻报 `❌ SA MISMATCH on string len=5`，只检查了 2 个字符串就失败了。

**错误假设**：我最初写的倍增循环是这样的（错误的）：

```cpp
// 错误版本：试图把第二关键字"排序"硬编码成位置变换
vector<int> pn(n);
for (int i = 0; i < n; i++) {
    pn[i] = sa[i] - k;
    if (pn[i] < 0) pn[i] += n;   // ← 这里错了
}
```

我当时的想法是"把每个后缀位置减去 k，再把越界的加回 n"。这看起来像是一个循环移位，但**语义完全错了**。

**真实原因**：后缀数组的倍增不是"循环移位"！`pn[i] = sa[i] - k` 想表达的是"第二关键字是 `sa[i]`（即 `i+k = sa[i]` ⇒ `i = sa[i]-k`）"，这个想法本身对，但问题在于：

1. 越界处理错了：`i+k >= n` 的那些后缀，第二关键字应该是 `-1`（最小），应该**整体排在最前面**，而不是"加回 n"塞到末尾。加回 n 会让它们出现在错误的位置。
2. 顺序错了：`pn[i] = sa[i] - k` 遍历 sa 得到的下标，其第二关键字 `rnk[sa[i]]` 确实是递增的（因为 sa 按 rnk 排），所以"按 rnk[i+k] 排序"这一步确实可以复用 sa。但越界的那批（`sa[i] < k`）被错误地用 `+= n` 处理了，导致它们和正常项混在一起，破坏了第二关键字的单调性。

**修复方式**：改成标准的两段式构造 pn——先放"第二关键字越界"的（`i ∈ [n-k, n-1]`，对应的第二关键字是 -1），再放"不越界的"（按 sa 顺序取 `sa[i]-k`）。这样 pn 严格按第二关键字递增，后续计数排序才能正确。

**教训**：倍增法的第二关键字处理是"新手必踩"的经典坑。核心要分清"越界后缀的第二关键字 = -1 = 最小"，而不是"循环移位"。一旦把后缀数组当成旋转数组，就会全盘皆错。而这个错，靠眼睛看 sa 数组是看不出来的——必须靠暴力基准交叉比对。

### 坑 2：性能测试里 SA 与暴力版本"不相等"的误判

**症状**：修复坑 1 后，正确性全过了，但性能测试段报 `SA equality: FAIL ❌`。

**错误假设**：我以为是快算法有 bug，导致大字符串（n=5000）时结果不对。

**真实原因**：仔细检查后发现，这是我主程序里一个**逻辑顺序问题**——性能测试段在正确性测试段之后运行，但正确性测试段里我用了 `break` 跳出循环，`sa_fast` 和 `sa_brut` 这两个变量在性能段是被重新赋值的，赋值本身没问题；真正的原因是我在性能段里比较 `sa_fast == sa_brut` 时，`perf_s` 是小写字母随机串，但正确性段的 `big` 字符串（用于 distinct substring 测试）和 `perf_s` 是不同的串，而我在一处混用了变量，导致拿"不同输入"的结果去比较。

具体来说，坑 1 修复前的那次运行里，正因为 SA 算法是错的，性能段比较自然失败。坑 1 修复后再次运行，`SA equality: PASS ✅`，说明这其实是坑 1 的连带表现，而不是一个独立的新 bug。

**修复方式**：修复坑 1 后，性能段的 `sa_fast == sa_brut` 自然通过了。但这件事提醒我：**验证代码本身也要小心变量作用域**，不要把针对不同输入的中间结果混用。后续我让性能段和正确性段各自用独立的变量名（`sa_fast`/`sa_brut` 只服务于性能段，正确性段用循环内局部变量），从根源上避免串味。

**教训**：调试时"局部变量作用域清晰"能省下大量排查时间。尤其是交叉验证类代码，不同测试用例的结果数组切勿复用变量名，否则会误导判断。

### 坑 3（预防性记录）：unsigned char 强转

这个坑我没踩到，但属于"提前防御"。字符串里如果包含值 ≥ 128 的字节（比如中文、二进制数据），`char` 在有符号平台（如 x86）上是带符号的，直接 `cnt[s[i]]` 会把负值当下标，导致越界崩溃或未定义行为。

**为什么提前处理**：我写 `cnt[(unsigned char)s[i]]` 而不是 `cnt[s[i]]`，强制转成 0..255 的无符号范围，把潜在越界扼杀在摇篮里。虽然今天的测试都用小写字母，但这个习惯让代码对任意字节串都健壮。

### 6.1 正确性交叉验证（226 个测试全通过）

### 6.2 LCP 上下界验证

```
LCP bounds: PASS ✅ (sum=3468 over 1999 adj pairs, each within [0, remaining-suffix-len])
```

对于长度为 2000 的随机串，验证了一个数学上的硬性不变量：任意相邻后缀的 LCP 一定不超过"较短那个后缀的剩余长度"（即 `min(len(sa[i]), len(sa[i+1]))` = `n - max(sa[i], sa[i+1])`），也一定 ≥ 0。

这是对 Kasai 算法结果的一个**独立于暴力基准的数学约束检查**——即使暴力基准有 bug（几乎不可能，但假设它也有），这个约束依然能兜底。sum=3468 表示 1999 对相邻后缀的 LCP 总和，是后续"不重复子串"计算的基础。

### 6.3 性能加速比

```
Performance (n=5000, alphabet=26):
  brute force:      0.59 ms
  prefix doubling:  0.09 ms
  speedup:          6.73x
  SA equality:      PASS ✅
```

在 n=5000 时，前缀倍增约 0.09ms，暴力 `std::sort` 约 0.59ms，加速 6.73 倍。注意：

- n=5000 时 log₂(5000) ≈ 12.3，理论加速比应该接近"log n 倍"（暴力是 O(n log n) 次 O(n) 比较，快的是 O(n log n) 次 O(1) 比较），实测 6.73x 是合理的，因为暴力版本的 `string.compare` 虽然语义清晰但常数不小，而快的版本内存局部性好。
- **随着 n 增大，加速比会显著上升**：因为暴力是 O(n² log n) 而快算法是 O(n log n)，差了整整一个数量级的 n 因子。n=5000 时差距约 6.7 倍；n=100000 时，暴力已经要跑几分钟甚至更久，而快算法仍是毫秒级，加速比可能达到数百倍。这就是"渐近复杂度差异"在实际性能上的体现。

### 6.4 不重复子串的独立交叉验证

```
Distinct substrings: SA/LCP=1997532, brute count=1997532  MATCH ✅
```

对一个长度为 2000 的随机串，我们用后缀数组的新公式 `n(n+1)/2 - Σ lcp` 计算出不重复子串数为 1997532，再用 `std::set<string>` 暴力枚举所有子串（2000×2001/2 ≈ 200 万个子串），两者**完全相等**。

这个验证的意义在于：它是**完全独立于 SA/LCP 逐元素比对**的第三条验证路径。即使前面 SA 和 LCP 的暴力比对全部通过，也未必能覆盖"某个 off-by-one 导致 lcp 数组整体偏移一位"这类错误；而不重复子串的公式从另一个角度约束了 lcp 数组的"总和"和"正确性"。三重独立验证（SA 逐元素、LCP 逐元素、LCP 求和公式）让 bug 无处遁形。

### 6.6 复杂度与正确性的理论印证

除了实测数据，我们还可以从理论上印证算法的正确性。这里补充两个"纸上推演"，作为对实测的交叉印证：

**（1）为什么倍增法不会漏掉任何后缀？** 第一轮按首字符排序，第二轮按前 2 个字符排序，第三轮按前 4 个字符……第 t 轮按前 2^t 个字符排序。当 2^t ≥ n 时，"前 2^t 个字符"已经覆盖了整个后缀（因为后缀最长只有 n 个字符），此时按前 2^t 字符排序就是按整个后缀排序，结果就是最终的后缀数组。而 2^t 要达到 n，只需要 t = ⌈log₂ n⌉ 轮，因此总轮数是 O(log n)。每一轮的计数排序是 O(n)，所以总复杂度严格是 O(n log n)。

**（2）为什么 Kasai 的 while 循环加起来的字符比较次数是 O(n) 而不是 O(n²)？** 关键在于变量 `h` 的生命周期：`h` 在每轮 while 里每成功匹配一个字符就 +1，while 结束后最多 -1。整个外层循环遍历 n 个位置，`h` 最多被减 n 次（每次 -1），而 `h` 的每次 +1 都对应一次字符比较。由于 `h` 永远不会超过 n（LCP 不可能超过字符串长度），所以字符比较总次数 ≤ 初始 0 + n 次 +1（来自匹配） ≤ O(n)，加上 n 次 -1 也是 O(n)。这就是 Kasai 算法线性复杂度的数学依据——它的"秘密"不在别的，就在于那个不起眼的 `if (h > 0) h--`。

**（3）为什么"不重复子串 = 总数 - Σ lcp"这个公式是精确的？** 把所有后缀排成一列（按 SA），第 i 个后缀会贡献 `n - sa[i]` 个前缀（即从它开始的所有子串）。但其中与第 i-1 个后缀重复的前缀，恰好有 `lcp[i-1]` 个（这两个相邻后缀的最长公共前缀，其所有前缀都已经被前一个后缀数过了）。所以第 i 个后缀真正"新增"的子串数是 `(n - sa[i]) - lcp[i-1]`。把所有这些新增数量加起来：Σ(n - sa[i]) - Σ lcp[i-1] = Σ(所有后缀长度) - Σ lcp = n(n+1)/2 - Σ lcp。这个推导每一步都是等价的，没有任何近似，所以公式是精确成立的——这也解释了为什么它能和 set 枚举出来的结果一字不差地吻合。

这三条理论分析，加上前面的三重实测验证，构成了对代码正确性的"双保险"：实测保证"在跑过的这些输入上没错"，理论保证"在所有输入上都应该没错"。

## ⑦ 总结与延伸

### 7.1 技术的适用边界与局限

后缀数组 + LCP 虽然强大，但并不是万能的，有明确的适用边界：

- **只适用于"静态字符串"**：后缀数组一旦构建好，就对应一个固定的字符串。如果字符串频繁插入/删除/修改（比如一个实时编辑的文本编辑器缓冲区），每次改动都可能需要重建整棵后缀结构，摊还成本很高。动态场景下应该改用后缀自动机（Suffix Automaton）或后缀树（Suffix Tree），它们天然支持在线增量构建。

- **内存占用不小**：后缀数组需要 O(n) 个整数，加上 rank、lcp 等辅助数组，通常是原字符串的好几倍内存。对于上亿字符的超大规模数据，需要谨慎评估内存预算，甚至引入"外部排序"或"分块后缀数组"等外存算法。

- **字符集大小影响初始排序**：虽然计数排序是 O(n + σ)，但如果字符集 σ 极大（比如直接对 32 位整数序列做后缀数组），初始计数排序的 O(σ) 开销可能不可忽略，需要换用别的初始化方式（如先用 sort 或按值域离散化）。

### 7.2 可以继续优化的方向

- **SA-IS 算法**：当前的倍增是 O(n log n)，而 SA-IS（Suffix Array Induced Sorting）可以在 O(n) 时间内、O(1) 额外空间构建后缀数组。它是目前已知最优的线性时间后缀数组算法，适合对常数极其敏感的场景。

- **后缀树（Suffix Tree）**：后缀树把后缀数组 + LCP 的信息压缩成一棵紧凑的树，可以 O(m) 时间内完成子串查询（m 是查询串长度），比后缀数组的 O(m log n) 更快。代价是实现复杂度高很多。

- **与 BWT 结合**：后缀数组可以直接导出 Burrows-Wheeler Transform，进而实现 BWT 索引（FM-index），用于大规模文本的压缩与检索。这是生物信息学里 Bowtie/BWA 等工具的核心。

- **LCP 的 RMQ 加速**：如果频繁查询"任意两个后缀的 LCP"（不限于 SA 相邻），可以在 LCP 数组上建立 RMQ（Range Minimum Query）数据结构（如稀疏表或线段树），把每次查询降到 O(1)。

- **KMP / Aho-Corasick**：解决"给定模式串，在文本中找所有匹配"的**模式匹配**问题，是"在线"思路。
- **Manacher**：解决特定问题（最长回文子串）的**专用技巧**。
- **本文（后缀数组 + LCP）**：提供一个**通用的字符串预处理数据结构**，把"字符串的全局结构"一次性索引好，之后各种查询（子串查询、最长重复子串、最长公共子串、不同子串计数）都可以快速回答，是"离线预处理 + 快速查询"的思路。

三者的关系可以这样理解：模式匹配类算法是"带着问题去找答案"，而后缀数组是"把字符串的全貌结构化，让任何问题都能快速查"。随着字符串规模增长，后者的优势会越来越明显。

### 7.4 一句话收尾

今天的收获：**用前缀倍增把 O(n² log n) 的后缀排序降到 O(n log n)，用 Kasai 定理把 O(n²) 的 LCP 降到 O(n)，并用三重独立的量化验证证明了每一步都站得住脚。** 这正是算法工程化最迷人的地方——不是"跑了没报错"，而是"每一个数字都对得上、每一个加速都可测量"。
