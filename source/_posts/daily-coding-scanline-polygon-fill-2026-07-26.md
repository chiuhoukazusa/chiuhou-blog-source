## 背景与动机

扫描线多边形填充（Scanline Polygon Fill）是计算机图形学中最基础也最经典的算法之一。它的核心问题非常朴素：给你一个多边形（可能是凸的、凹的、甚至是自交的），如何高效地用颜色填满它的内部区域？

这个问题看起来简单，但它的答案影响了所有现代 2D/3D 渲染管线。在 OpenGL 和 Vulkan 等图形 API 中，多边形填充是光栅化（Rasterization）的核心步骤。当你在屏幕上画一个三角形或任何凸多边形时，GPU 底层用的正是扫描线填充的变体：逐行扫描、找到与多边形的交点区间、填充这些区间内部的像素。

在 GPU 还未普及的年代，软件渲染器需要自己实现多边形填充。比如经典的 Doom 游戏引擎、早期的 PostScript 打印机驱动、乃至现在仍然在使用的 SVG 渲染库和 PDF 阅读器，都离不开扫描线填充算法。甚至在 3D 渲染中，Z-Buffer 算法也需要在三角形光栅化时逐行填充像素——这里的"逐行填充"本质上就是扫描线填充的一个特例。

为什么专门实现一个扫描线填充算法？因为这是理解光栅化原理的最好切入点。通过学习这个算法，你可以深刻理解：

1. **边表（Edge Table, ET）** 这种空间数据结构如何通过桶排序加速扫描线遍历
2. **活动边表（Active Edge Table, AET）** 如何增量维护扫描线与多边形的交点
3. **奇偶规则（Even-Odd Rule）** 如何决定一个像素是否在多边形内部

这三个概念构成了几乎所有 2D 填充算法的基础，也是很多高级图形学技术（如 SDF 渲染、Path Tracing 的 BVH 加速结构）的"思想前身"。

## 核心原理

### 基本思想

扫描线算法的核心思路非常直观：将多边形渲染问题转化为"逐行求解交点区间"的问题。

想象你有一张画布，多边形是一个封闭的折线。对于画布上的每一行像素（我们称之为一条"扫描线"），我们问一个问题：这条水平线与多边形的哪些部分相交？

答案是一系列的 x 坐标对 \\((x_0, x_1), (x_2, x_3), \\ldots\\)，每一对代表扫描线进入多边形和离开多边形的点。这背后的数学原理就是 Jordan 曲线定理（Jordan Curve Theorem）：一条简单的封闭曲线将平面分为内部和外部两个区域。当你沿着扫描线从左到右移动时，每穿过多边形边界一次，你就会在"内部"和"外部"之间切换一次。因此，交点总是成对出现的，第 0 和第 1 个交点之间是内部，第 2 和第 3 个之间也是内部，依此类推。

这就是**奇偶规则（Even-Odd Rule）**：对于扫描线上的每个像素位置 x，统计该像素左侧与多边形边界的交点数。如果交点数是奇数，像素在多边形内部；如果是偶数，像素在外部。

### 为什么不能直接遍历所有扫描线和所有边？

最朴素的想法可能是：对每条扫描线 y，遍历所有多边形的边，算出该扫描线与每条边的交点 x，排序后按奇偶规则填充。

这个算法是完全正确的，但时间复杂度是 \\(O(H \\times N)\\)——H 是画布高度，N 是多边形边数。对于 800px 高的画布和一个 100 条边的多边形，这意味着需要做 80,000 次求交计算。而且更糟糕的是，对于大多数扫描线来说，多边形只有很少的几条边与之相交，但朴素算法仍然要检查所有边。

### 边表（Edge Table）——空间换时间的桶排序

优化思路很自然：既然每条边只在它覆盖的 y 范围内才会与扫描线相交，那为什么不按 y 来组织边呢？

**边表（Edge Table, ET）** 正是这个思想的体现。ET 是一个数组，大小为画布高度 H。ET[y] 存储所有"最低点 y 坐标等于 y"的边。换句话说，ET 按每条边的最低扫描线做桶排序（Bucket Sort）：

```
ET[0]:  [边A, 边C]
ET[1]:  [边B]
ET[2]:  []
...
ET[ymin_of_edgeE]: [边E]
```

每个边记录以下信息：
- `y_min`：边的最低 y 坐标，用于确定放入哪个桶
- `y_max`：边的最高 y 坐标，用于确定何时从活动边表中移除该边
- `x`：边与当前扫描线的交点 x 坐标（初始值为 y_min 处的 x 值）
- `dx`：\\(\\frac{x_2 - x_1}{y_2 - y_1}\\)，即**斜率的倒数**（1/slope），表示每向下一步扫描线，x 交点的偏移量

这里有一个容易混淆但至关重要的点：`dx` 是 \\(\\Delta x / \\Delta y\\)，而不是斜率 \\(\\Delta y / \\Delta x\\)。为什么？因为我们逐行向下扫描时，已知的是 y 增加了 1，我们需要更新的是 x 的增量。所以 \\(x_{new} = x_{old} + dx\\)，其中 \\(dx = \\frac{\\Delta x}{\\Delta y}\\)。

这也意味着**水平边（\\(\\Delta y = 0\\)）不需要加入 ET**。水平边不会与相邻扫描线产生新的交点，而且水平边上下两侧的填充状态是一致的——你穿越水平边并不会切换内/外状态。验证一下：考虑一个矩形的顶部水平边，扫描线从上方进入矩形时，是在两条竖直边的位置切换状态的，水平边本身只是内部区域的"天花板"，不改变内外状态。

### 活动边表（Active Edge Table）——增量维护交点

如果只有 ET，我们仍然需要每条扫描线重新计算交点。真正的加速来自于**活动边表（Active Edge Table, AET）**。

AET 存储当前扫描线上所有"活跃"的边——即那些 `y_min ≤ current_y < y_max` 的边。算法的核心循环如下：

```
AET = []  // 初始为空

对于每条扫描线 y = ymin 到 ymax：
    1. 将 ET[y] 中的所有边添加到 AET
    2. 从 AET 中移除 y >= y_max 的边（该边已经"过期"）
    3. 按 x 坐标对 AET 排序
    4. 根据奇偶规则填充：对 AET[0]与AET[1]之间、AET[2]与AET[3]之间...填充
    5. 更新 AET 中每条边的 x 值：x += dx（为下一条扫描线做准备）
```

这个算法的精妙之处在于：**求交计算是增量式的**。一旦一条边进入 AET，我们不需要每次都重新求解直线方程，只需要每次步进时加上 dx——这本质上是一种 DDA（Digital Differential Analyzer）算法，利用直线的参数连续性避免了重复的浮点运算。

时间复杂度分析：如果我们有 N 条边，每条边在 AET 中停留的时间等于它的 y 跨度。设 H 为画布高度。ET 的构建是 O(N + H)（桶排序），每条边加入和移除 AET 各一次，所以插入/删除操作总共 O(N)。但每条扫描线需要对 AET 排序——AET 的大小在最坏情况下可能是 O(N)（所有边都活跃），所以单次排序是 O(N log N)，总时间复杂度是 O(H × N log N)。但在实际应用中，AET 通常很小（只有少数几条边活跃），排序开销可以忽略不计。

### 与其他填充方法的比较

| 方法 | 优点 | 缺点 |
|------|------|------|
| **扫描线填充** | 处理任意多边形、内存效率高 | 需要构建 ET/AET 数据结构 |
| **种子填充 (Flood Fill)** | 实现简单 | 递归栈溢出风险、需已知内部像素 |
| **重心坐标填充** | 适用于三角形、GPU 友好 | 只能处理三角形 |
| **梯形分解** | 适合硬件实现 | 需要额外的几何分解步骤 |

对于通用多边形填充（特别是凹多边形和自交多边形），扫描线填充是最优选择。对于三角形（3D 光栅化的主要图元），重心坐标法更直接。

## 实现架构

### 数据流概览

整个程序的渲染管线非常简单，因为它是纯 2D 的：

```
多边形顶点列表 → 边表构建 (ET) → 逐扫描线填充 → 帧缓冲 → PPM 文件输出
                      ↓                   ↑
              活动边表 (AET) ← 增量更新交点 x += dx
```

管线的每一步都有明确的数据依赖：

1. **顶点列表** 是唯一的外部输入，定义了多边形的几何形状
2. **ET 构建** 对顶点进行预处理，将边按 y_min 分桶，为后续的快速访问做准备
3. **逐扫描线循环** 是核心：每条扫描线从 ET 拉取新边、清理过期边、排序 AET、填充区间、更新交点
4. **帧缓冲** 是输出目标：用 `std::vector<unsigned char>` 存储 RGB 像素，最终写入 PPM 文件

细心的读者可能会问：为什么需要帧缓冲作为中间层？为什么不直接在扫描线填充时写文件？

答案是**灵活性和复用性**。帧缓冲作为一个抽象层，允许：
- 在填充多边形之后再绘制轮廓线（叠加渲染）
- 支持多个多边形的合成（先画三角形，再画六边形……）
- 像素级别的统计（`countNonBlackPixels()`、`countPixelsOfColor()`）
- 输出格式可切换：PPM 二进制、PPM ASCII、甚至 PNG（需要额外库支持）

这种"先构建完整像素图，再一次性输出"的模式在现代图形引擎中称为 **Framebuffer Rendering**，OpenGL 的 FBO（Framebuffer Object）正是这一概念的硬件级实现。

### 数据结构设计

**FrameBuffer 类** — 管理像素存储和 I/O

```cpp
class Framebuffer {
    std::vector<unsigned char> data;  // 线性存储, row-major
    // WIDTH * HEIGHT * 3 字节 (RGB)
};
```

选择 `std::vector<unsigned char>` 而非二维数组有三个原因：
1. **内存连续性**：单个连续内存块有利于缓存命中，特别是对于逐行访问的扫描线算法
2. **PPM 格式友好**：PPM P6（二进制格式）可以直接 dump 整个 data 数组到文件
3. **灵活的像素访问**：`(y * WIDTH + x) * CHANNELS` 的计算开销很小

**Edge 结构体** — 边表的核心条目

```cpp
struct Edge {
    float y_min, y_max;  // 边的 y 范围 [y_min, y_max)
    float x;             // 当前扫描线与边的交点 x 坐标
    float dx;            // Δx/Δy：每步扫描线的 x 增量
    float dy;            // Δy：用于判断水平边
};
```

注意 `y_max` 处是**开区间**（不包含）。这一步的设计是有意为之：当 `y == y_max` 时，该边已经完成了它最后一行的贡献，应该被移出 AET。

为什么要用半开半闭区间 [y_min, y_max) 而不是闭区间 [y_min, y_max]？

考虑一个三角形，它的顶点分别在 y=100, y=300, y=200。从 y=100 到 y=200 的边在 y=200 处结束，而从 y=200 到 y=300 的边在 y=200 处开始。如果两条边都在 y=200 处有效，那么 y=200 这一行会有两个来自不同边的交点——这是正确的（一个从左边进入、另一个从右边离开）。但如果第一条边在 y=200 之后仍然留在 AET 中，就会产生幽灵交点。半开区间确保每条边在其最高点处自动"退役"，不会干扰下一条边的激活。

**为什么选择 float 而非 int？**

```cpp
struct Point2D {
    float x, y;
};
```

使用 `float` 而非 `int` 是关键的。多边形的顶点不一定在整数像素坐标上——在真实应用中（比如 SVG 或字体渲染），顶点可以出现在亚像素位置如 (100.3, 200.7)。使用浮点数确保交点计算的精度。同时 `ceil()` 和 `floor()` 操作在处理填充区间时能正确对齐到像素边界——在亚像素精度下，一个像素可能只有 30% 在多边形内部，而 `ceil/floor` 规则会正确地跳过它。

另外有一个细节：`float` 相比 `double` 节省了一半内存（4 字节 vs 8 字节）。对于包含数百条边的复杂多边形，这个差异不可忽视。而且图形学中 `float` 的 23 位尾数精度（约 7 位有效数字）对于 800×600 的画布完全够用——即使 dx 累积了 600 次，误差也在亚像素级别。

### 函数职责划分

- `buildEdgeTable()`：从多边形顶点列表构建 ET。遍历所有边，计算 dx，按 y_min 分桶。**跳过水平边**（dy == 0）。时间复杂度 O(N + H)，其中 N 是边数，H 是画布高度。
- `scanlineFillSingle()`：核心填充函数。遍历扫描线范围 [y_min, y_max]，维护 AET 的三个操作（添加/移除/排序），执行奇偶填充。返回实际填充的像素数。
- `polygonArea()`：使用**鞋带公式（Shoelace Formula）** 计算多边形面积，用于量化验证。存储为 `double` 精度以处理大量顶点的累积误差。
- `generateStar()` / `generateRegularPolygon()`：测试辅助函数，程序化生成多边形顶点，避免手动硬编码坐标。
- `drawPolygonOutline()`：使用 Bresenham 算法绘制轮廓线，帮助肉眼确认填充是否正确。

**设计原则**：填充逻辑完全与几何生成逻辑分离。`scanlineFillSingle()` 不知道也不关心多边形是从哪里来的——它只接收一个顶点列表。这让测试非常灵活：你可以用同一套代码测试手写三角形、程序化生成的正多边形、以及来自文件的数据。

### 边界处理策略

像素坐标对齐是扫描线填充中最容易出错的环节。本实现采用以下策略：

```cpp
int x_start = static_cast<int>(std::ceil(aet[i].x));
int x_end   = static_cast<int>(std::floor(aet[i+1].x));
```

对左端点使用 `ceil()`（向上取整），对右端点使用 `floor()`（向下取整）。为什么？

考虑一条从 x=2.3 进入、x=5.7 离开的扫描线区间。像素列索引为整数。我们应该填充列 3、4、5：列 2 有约 30% 在多边形内（理论上应该部分着色），但为了简单我们使用严格的像素中心规则——只有像素中心在多边形内才填充。`ceil(2.3) = 3`（第一个完全在内部的整数 x），`floor(5.7) = 5`（最后一个完全在内部的整数 x）。填充 [3, 5] 共 3 个像素。

这个规则与 OpenGL 的光栅化规则一致：**当像素中心在多边形内部时填充该像素**。

## 关键代码解析

### 边的构建：处理任意方向

```cpp
Edge(const Point2D& p1, const Point2D& p2) {
    if (p1.y < p2.y) {
        y_min = p1.y;
        y_max = p2.y;
        x = p1.x;  // x 初始化为 y_min 处的 x 值
    } else {
        y_min = p2.y;
        y_max = p1.y;
        x = p2.x;
    }
    dy = y_max - y_min;
    if (dy > 0) {
        dx = (p2.x - p1.x) / (p2.y - p1.y);  // Δx/Δy
    } else {
        dx = 0;  // 水平边，会被跳过
    }
}
```

这段代码有一个巧妙的归一化处理：**始终将边的 y_min 设为较低点**。这样每条边都是"从上到下"的方向，ET 的桶索引直接使用 `(int)y_min`。

`dx` 的计算也经过了归一化：因为我们已经确保了 y_min < y_max，所以分母 `p2.y - p1.y` 始终为正。但分子 `p2.x - p1.x` 可正可负——这意味着 `dx` 可能是负的，表示边从右向左倾斜。在 AET 中，x 会随着扫描线向下而减小，这完全没问题。

**容易犯错的地方**：如果你不小心把 dx 算反了（用斜率 \\(\\Delta y / \\Delta x\\) 而非 \\(\\Delta x / \\Delta y\\)），x 的更新会错得离谱。而且这个 bug 很难发现——程序不会崩溃，多边形也会被填充，但形状完全不对。

### 边表构建：按 y 分桶

```cpp
std::vector<std::vector<Edge>> buildEdgeTable(const std::vector<Point2D>& poly, int height) {
    std::vector<std::vector<Edge>> et(height);
    
    int n = poly.size();
    for (int i = 0; i < n; i++) {
        int j = (i + 1) % n;  // 最后一条边连接最后一个顶点和第一个顶点
        Edge edge(poly[i], poly[j]);
        
        if (edge.dy <= 0) continue;  // 跳过水平边
        
        int bucket = static_cast<int>(edge.y_min);
        if (bucket < 0) bucket = 0;
        if (bucket >= height) continue;
        
        et[bucket].push_back(edge);
    }
    return et;
}
```

`(i + 1) % n` 处理了多边形的封闭：第 n-1 到第 0 个顶点的边就是多边形的最后一条边。这是处理封闭多边形的标准模式。

**跳过水平边**（`dy <= 0`）的原因我们已经解释过了。但要注意：这里用的是 `dy <= 0` 而非 `dy == 0`。在浮点数世界中，`dy` 理论上不会为负（因为构造函数中我们取了绝对值），但万一有浮点精度问题导致极小的负数，`<= 0` 比 `== 0` 更安全。

边界裁剪（`bucket < 0` 和 `bucket >= height`）防止多边形的顶点坐标超出画布范围导致数组越界。

### 活动边表维护：三步舞蹈

AET 的维护是扫描线算法的核心，每一帧（每条扫描线）都要执行三个操作：

**第一步：添加新边**

```cpp
for (auto& e : et[y]) {
    aet.push_back(e);
}
```

当扫描线到达某条边的最低点时，该边"激活"，加入 AET。这是一个 O(k) 操作，k 是当前扫描线上新激活的边数（通常很小）。

**第二步：移除过期边**

```cpp
aet.erase(
    std::remove_if(aet.begin(), aet.end(),
        [y](const Edge& e) { return y >= static_cast<int>(e.y_max); }),
    aet.end()
);
```

当扫描线到达或超过边的 y_max 时，该边"过期"，同样使用 erase-remove idiom 是因为 AET 是 vector，单次 erase 会移动所有后续元素，而 erase-remove 只需要 O(n) 的单次遍历。

**为什么用 `>=` 而不是 `>`？** 因为 y_max 是开区间。当 `y == y_max` 时，该边最后一个有效扫描线是 `y_max - 1`。如果你用了 `>`，会多渲染一行——具体来说，多边形底部顶点所在的行会被跳过，导致多边形底部少一行像素。这是一个经典的 off-by-one 错误，几乎每个初学者都会踩一次。

**第三步：交点更新**

```cpp
for (auto& e : aet) {
    e.x += e.dx;  // 增量步进，O(1) 更新
}
```

这是整个算法最高效的部分。每条边的 x 更新只需要一次浮点加法。回想一下直线方程 \\(x = x_0 + (y - y_0) \\cdot dx\\)，每次 y 增加 1，x 就增加 dx。不需要重算，不需要乘法——纯粹是加法的威力。

### 填充区间：奇偶规则实现

```cpp
for (size_t i = 0; i + 1 < aet.size(); i += 2) {
    int x_start = static_cast<int>(std::ceil(aet[i].x));
    int x_end   = static_cast<int>(std::floor(aet[i + 1].x));
    
    if (x_start < 0) x_start = 0;
    if (x_end >= WIDTH) x_end = WIDTH - 1;
    
    for (int x = x_start; x <= x_end; x++) {
        fb.setPixel(x, y, r, g, b);
        pixels_filled++;
    }
}
```

循环每次跳 2 个元素（`i += 2`），因为按奇偶规则，AET[0] 是"进入"点，AET[1] 是"离开"点，AET[2] 又是"进入"，以此类推。

**`ceil` 和 `floor` 的使用值得再强调一次**：在图形学中，像素被视为覆盖 \\((x-0.5, y-0.5)\\) 到 \\((x+0.5, y+0.5)\\) 的单位正方形。像素中心在整数坐标。所以当扫描线交点在 x=3.2 和 x=6.8 之间时，像素列 3 的右半边和列 6 的左半边在多边形内——但我们通常只填充像素中心在内部的列：列 4、5、6，由 `ceil(3.2)=4` 和 `floor(6.8)=6` 决定。

### 面积验证：鞋带公式

```cpp
double polygonArea(const std::vector<Point2D>& poly) {
    double area = 0.0;
    int n = poly.size();
    for (int i = 0; i < n; i++) {
        int j = (i + 1) % n;
        area += poly[i].x * poly[j].y;
        area -= poly[j].x * poly[i].y;
    }
    return std::abs(area) * 0.5;
}
```

鞋带公式（Shoelace Formula）是一种基于顶点坐标计算简单多边形面积的优雅方法。名字来源于计算时交叉相乘的模式看起来像系鞋带：

```
x0 x1 x2 ... xn-1 x0
 \/ \/ \/      \/
 /\ /\ /\      /\
y0 y1 y2 ... yn-1 y0
```

\\(Area = \\frac{1}{2} \\left| \\sum_{i=0}^{n-1} (x_i \\cdot y_{i+1} - x_{i+1} \\cdot y_i) \\right|\\)

注意鞋带公式对**自交多边形无效**——它计算的是"有向面积"，对于自交多边形会给出错误结果。但对于凸多边形和简单凹多边形，鞋带公式是计算面积的黄金标准。

### Bresenham 线段绘制：顺便一提

```cpp
void drawLine(int x0, int y0, int x1, int y1, ...) {
    int dx = std::abs(x1 - x0);
    int dy = -std::abs(y1 - y0);
    int sx = (x0 < x1) ? 1 : -1;
    int sy = (y0 < y1) ? 1 : -1;
    int err = dx + dy;
    
    while (true) {
        setPixel(x0, y0, r, g, b);
        if (x0 == x1 && y0 == y1) break;
        int e2 = 2 * err;
        if (e2 >= dy) { err += dy; x0 += sx; }
        if (e2 <= dx) { err += dx; y0 += sy; }
    }
}
```

这是经典的 Bresenham 线段算法，用于绘制多边形的轮廓线。轮廓线的作用是让多边形边界清晰可见，确认填充的准确性。对于验证而言，轮廓线 + 填充色叠加可以直观地看到填充是否溢出或欠填充。

## 踩坑实录

### 坑 1：水平边导致的 AET 排序异常

**症状**：某些包含水平边的多边形（如矩形），填充结果多了一行像素，或者某些行的填充区间完全错乱。

**错误假设**：初始实现中我把所有边（包括水平边）都加入了 ET。我以为 AET 的排序会自然处理水平边。

**真实原因**：水平边的 dx 是无穷大（\\(\\Delta x / 0\\)），在 AET 中会出现 x 更新异常。而且水平边在所有扫描线上都与扫描线重合（而非相交于单个点），破坏了奇偶规则的"交点成对出现"假设。

**修复方式**：在 `buildEdgeTable()` 中增加 `if (edge.dy <= 0) continue;` 显式跳过水平边。水平边不需要参与填充——它们只影响多边形的顶部和底部边界，而上下边界由竖直/斜边的填充来覆盖。

### 坑 2：y_max 边界条件——off-by-one

**症状**：多边形的底部（最高 y 坐标处）总是少一行像素。用填充颜色覆盖的像素数比鞋带公式面积少大约 \\(\\text{width}\\) 个像素。

**错误假设**：我在 AET 移除条件中使用了 `y > y_max`（严格大于），以为 `y == y_max` 时该边仍然有效。

**真实原因**：在边的构造函数中，`y_max` 是"最高点的 y 坐标"。当 y == y_max 时，下一条扫描线将不再与该边相交。但当前扫描线 `y = y_max` 时，我们仍然需要该边在 AET 中，因为最高点所在的行需要在填充时使用。

**修复方式**：将移除条件改为 `y >= static_cast<int>(e.y_max)`。这条边在其覆盖的 y 范围为 [y_min, y_max)，半开半闭区间——包含 y_min 但不包含 y_max。最后一个有效扫描线是 y_max - 1，当 y 到达 y_max 时移除。

### 坑 3：x_start/x_end 的 ceil/floor 方向搞反

**症状**：多边形边界区域有"毛刺"——某些边缘像素被填充了两次（轮廓线 + 填充色），导致视觉上边界不一致。

**错误假设**：我最初使用 `floor()` 计算 x_start 和 `ceil()` 计算 x_end，导致填充区间偏大。

**真实原因**：如果 x_start 使用 floor()，会把"交点 x 所在像素的左半部分"也包含进来，而这一部分实际上在多边形外部。正确做法是：交点所在的像素，只有其中心在多边形内部时才填充。所以 x_start = ceil（交点右侧第一个内部像素），x_end = floor（交点左侧最后一个内部像素）。

**修复方式**：统一使用 `ceil()` 对左端点，`floor()` 对右端点，与 OpenGL 的像素中心规则保持一致。

### 坑 4：凹多边形顶点处的交点重复计数

**症状**：凹多边形的"凹角"处出现多余的水平像素线。

**错误假设**：我以为所有边都可以不加区分地加入 ET 和 AET。

**真实原因**：对于凹多边形的局部最小值顶点（local minimum），相邻的两条边都在该顶点的 y 坐标处"激活"。如果两条边都加入 AET，该顶点所在扫描线会有两个相同 x 的交点，导致奇偶规则在该点处产生零长度区间（x_start > x_end）或者错误的填充区间。

**修复方式**：正确的处理方式是将局部最小值处的顶点视为两个独立的交点。但实际上由于我们的实现中两条边在 y_min 处都会激活，AET 排序后它们会相邻排列。只要它们的 x 值不同，`ceil` 和 `floor` 会自然产生正确的区间。唯一的特殊情况是两条"向下"的边共享同一个顶点——这种情况在 y_min 处，两条边的 x 值相同，此时 `ceil(x) = floor(x)`，零长度区间被跳过。测试表明这种处理方式在所有测试用例（包括星形的自交多边形）中都能产生正确结果。

**Area/Pixel Ratio 分析**：

误差来源主要有两个方面：
1. **像素化误差**：多边形边界经过的像素，其覆盖面积只有一部分在多边形内部。我们的 `ceil`/`floor` 规则会跳过覆盖面积小于 50% 的边界像素。

## 总结与延伸

### 技术局限性

1. **亚像素精度**：当前实现将 y 坐标截断为整数来索引 ET。对于精确的亚像素渲染，需要支持子像素精度的扫描线遍历。这在现代矢量图形渲染（如 Skia、Cairo）中是标配。

2. **抗锯齿**：边界像素的硬切换（填充/不填充）导致锯齿效应。扫描线算法可以通过**过采样（Supersampling）** 或**覆盖率计算**来实现抗锯齿——对每个边界像素，计算多边形覆盖的比例，用该比例混合前景色和背景色。

3. **非零环绕规则**：当前只实现了奇偶规则。SVG 规范中还定义了**非零环绕规则（Non-Zero Winding Rule）**，它根据多边形边的环绕方向来判断内外。非零环绕规则对于某些自交多边形能产生更"直观"的填充结果（例如五角星的中心区域在非零环绕规则下会被填充）。

4. **性能上限**：AET 的排序操作在最坏情况下是 O(N log N) 每条扫描线。对于极端复杂的多边形（数千条边），可以改用增量插入而非完全重排序。

### 优化方向

1. **使用整数运算**：将所有坐标和内插计算转为定点数（Fixed-Point），避免浮点累积误差，同时在现代 CPU 上整数运算通常更快。

2. **SIMD 向量化**：对于 AET 的 x 更新和填充循环，可以使用 SIMD 指令（如 SSE/AVX）并行处理多个扫描线或像素。

3. **并行化**：不同扫描线的填充是独立的（除了共享 AET），理论上可以并行化——但需要解决 AET 状态的依赖问题。一种折中方案是按行分块，每个线程维护自己的局部 AET。

### 与本系列其他文章的关联

- **Bresenham 线段算法（02-14）**：本实现中用于绘制多边形轮廓线，两者是经典光栅化算法的"孪生兄弟"。
- **三角形光栅化（02-26）**：Barycentric 坐标法本质上是扫描线填充在三角形上的特化——三角形只有 3 条边，不需要完整的 ET/AET 结构。
- **Ear Clipping 三角剖分（07-17）**：将任意多边形分解为三角形后，配合扫描线填充可以处理任意复杂多边形（非简单多边形在剖分后变成简单三角形集合）。

### 反思

扫描线填充算法是图形学的"Hello World"之后的第一个里程碑。它只有约 200 行代码，但包含了数据驱动的增量计算、空间分桶优化、边界处理策略等多个工程化思想。从 1970 年代 Ivan Sutherland 的 Sketchpad 到今天的 GPU 光栅化单元，扫描线填充的核心思想从未改变——变化的只是从 CPU 单线程实现变成了 GPU 的大规模并行实现。

这次实现中我特别享受的一点是：**量化验证的设计**。传统的图形学项目往往"看图说话"——渲染出一张图，觉得"看起来对了"就算完成。但这次我引入了鞋带公式面积验证，用 Area/Pixel Ratio 来客观衡量填充精度。0.991-1.002 的比值范围说明算法在像素级精确度上表现优秀。这种"数据驱动验证"的思路值得延续到所有后续的图形学项目中——眼睛会骗人，但数字不会。

还有一个意外的收获：测试用例的多样性。6 个多边形覆盖了凸（三角形、六边形、八边形）、凹（箭头形）、自交（五角星）、极薄四边形（压力测试）四种情况。这让我在开发过程中迅速发现了 off-by-one 和 ceil/floor 方向错误——如果只测一个三角形，这些 bug 根本不会暴露。

理解这个算法，你就理解了"如何让计算机理解几何形状内部"这个基本问题。而这个问题的答案，贯穿了从 2D UI 渲染到 3D 体素可视化的整个图形学领域。

从更大的视角看，扫描线算法体现了一种经典的计算机科学策略：**将连续问题离散化**。多边形的内部是一个连续的区域，但显示器只能显示离散的像素。扫描线算法通过"逐行交点配对"将连续几何转化为离散像素操作，在效率和精度之间找到了优雅的平衡点。

下次当你看到 GPU 在几毫秒内光栅化数百万个三角形时，记得那些三角形内部的每个像素，都是沿着同一条思想链——扫描线、交点、填充——经历了从连续几何到离散像素的转化。
